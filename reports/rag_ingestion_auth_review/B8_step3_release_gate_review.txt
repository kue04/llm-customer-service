**超出规程的部分（按 B10 标注方向：更严）**：

1. 第 5 条除 id 一致外，另断言 **`text` 与库内 chunk 逐字相同** ——
   这一条能抓到"索引里的文本与库里不一致"这类最难查的静默错位（比 id 对不上隐蔽得多）；
2. 第 4 条显式断言 `retrieval_path`，把"退回 A 轨"变成一条**会红的**断言

3. 第 8 条额外断言 `/reprocess` 产生**新的** job，而不是复用失败的那个。

═══ 三、两条刻意的设计判断 ═══

**1. 两组生产默认值都要换，且必须是同一个 embedder**

上传路由与检索路由**各自**读一组 `default_index_root` / `default_embedder` /
`default_embedding_model`。只换一组，另一组就会去加载真模型（慢且可能失败）；
换了但不是同一个 embedder，则**查询向量与索引向量不在同一空间**，分数毫无意义
（B7 已踩过同一取舍，这里保持一致）。

**2. 检索 query 取自待检索文档自己的 chunk**

测试 embedder 是词袋哈希（同词共现 → 相似度高），query 必须与 chunk 共享 token 才可能有分。
用文档自己的词构造 query ＝"用户问文档里写过的内容"，**验证的是链路通不通**，
**不是检索质量**。检索质量属 M10 Recall@k，其口径修正尚未做
（验收规范 §10.3 已把它标为「未就绪 / N/A（口径不一致）」）。

> **表述纪律**：本步**不得**被读作"检索质量已验收"。它证明的是链路连通性；
> 质量评测仍挂在 §10.5 的「不可测」清单里。两者不能互相顶替。

═══ 四、中途的弯路（已登记为踩坑 D17） ═══

第一版"坏文件"写成 `b"PK\x03\x04" + b"\x00" * 512`，被**准入层**以 **415** 拦下：
「文件内容与扩展名 .docx 不一致」。

**修正后的认识**：「坏」是**分层**的 ——
① 准入层（`content_sniff`：magic bytes + zip 内是否有 `word/` 条目）；
② 解析层（python-docx）；③ 流水线层（错误码与状态）。
我以为是"解析失败"，实际构造的是"准入拒绝"。

**解决**：用 `zipfile` 造一个**合法 zip**，内含 `[Content_Types].xml` 与
`word/document.xml`（内容是非法 XML）→ 过准入、解析必失败。
**副产品**：那次 415 是"准入校验确实在工作"的正面证据。
