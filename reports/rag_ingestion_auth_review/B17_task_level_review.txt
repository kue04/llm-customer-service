B17 —— 「Top-K 被同一段内容的副本占满」——**在检索层修掉了**，
真实聊天链路的平均有效证据从 **2.14 / 3 提升到 3.00 / 3**（7 条真实 query 实测）。

但**修法不是登记里写的那一条**。登记记的是「检索层按 parent 去重，`ChunkHit` 缺

本批先做了取证，结论是**这两个选项都不该做**：

1. **父子块在本库里 100% 文本相同**（2824 对，逐字节相同、token 数相同）——
   父子块不是「父给上下文 / 子给精确匹配」，而是同一段内容存了两遍。
   于是「按 parent 去重」和「按文本去重」在**实际数据上等价**，

2. 登记推荐的判据 `content_hash` **达不到目标**：它是原文的 sha256，

   实测只按 `content_hash` 去重 → **19 / 21（2.71 / 3）**，翻不过 3.00 那关；
   按归一化文本 → **21 / 21（3.00 / 3）**。

所以本批的实质性判断是：**去重键必须取自「下游实际使用的口径」，而不是库里现成的 hash 列**。
这条判据后来还救回一个更隐蔽的问题（见第六节）。

═══ 四、去重判据的选择（本批最关键的一个决定） ═══

证据：reports/rag_ingestion_auth_review/b17_strategy_20260925.json（可复跑：tmp/probe_b17_strategy.py）

在**真实候选池**（pool=20，与生产同口径）上模拟四种策略，看 7 条 query × limit=3
能装出多少条**互不相同**的证据：

  | 策略 | 有效证据 | 折算 | 达标? |
  | --- | --- | --- | --- |
  | S0 不去重（现状） | 15 / 21 | 2.14 / 3 | ✗ |
  | S1 仅 `content_hash` | 19 / 21 | 2.71 / 3 | ✗ |
  | **S2 归一化文本（本批采用）** | **21 / 21** | **3.00 / 3** | ✓ |
  | S3 `content_hash` + 父⊇子包含 | 19 / 21 | 2.71 / 3 | ✗ |
  | S4 归一化文本 + 父⊇子包含 | 21 / 21 | 3.00 / 3 | ✓（与 S2 相同） |

两条读法：

1. **`content_hash` 翻不过 3.00 那关**（19 < 21）。根因是口径不一致：
   `content_hash` = `services/ingestion/chunkers/models.py::hash_text`，
   对**原文**做 sha256、不压空白；而下游按 `utils.rag_context._normalize_text`
   压平空白后去重。同一份内容的 md / html 版本在空白上不逐字节相同，
   于是原文 hash 判它们「不同」，**而下游照样把它们当同一条** ——
   用 content_hash 去重，截断后仍会被下游再砍一刀，名额照样填不满。
   （这与踩坑 D23「压平空白后 R@1 差 7 条」是同一个口径裂缝的两头。）
2. **「父块 ⊇ 子块」包含规则在 limit=3 窗口内零增量**（S4 == S2，S3 == S1）。
   所以**不引入**包含判定 —— 它需要拉长文本两两比对，成本不为零、收益为零。

由此定下一条纪律，写进模块 docstring：

    检索层的去重键，必须至少与**所有下游去重口径**一样严格。

**为什么不给 `ChunkHit` 加 `parent_chunk_id`**：
* 它不是 `ManifestEntry` 的字段，加它要改 manifest 结构并**重建索引**（9229 条），
  为一条实测零增量的规则付这个代价不值得；
* 库层面「父子块同文本」有 2824 对且 **100% 逐字节相同**，
  已被归一化文本判据完全覆盖；
* `HybridHit` 连 `chunk_id` 都是包在内层 `.hit` 里的，
  再加一层字段的适配成本会摊到两条链路上。

═══ 五、保留规则：为什么必须给「同分并列」一个确定性答案 ═══

证据：tmp/probe_b17_keep_which.py + reports/rag_ingestion_auth_review/b17_keep_which_20260925.json

  * 同 `content_hash` 的命中组，**20 / 20 分数严格相等**
    （父子块同文本 → 同一向量 → 同一相似度）。
    所以「留分数高的那条」在父子块场景里**没有任何信息量** ——
    它不构成一个决定，只构成一个「看起来像决定」的排序；
  * 分数相等时若依赖 FAISS / 融合的返回顺序，结果会**在不同调用路径下不一致**
    （踩坑 **D24**），测试会随机变红（踩坑 **D26**）。

因此 `_rank_key` 用三元组：`(-score, parent ? 0 : 1, chunk_id)` ——
**分数高者优先 → 并列时 parent 优先 → 再按 chunk_id 升序**。

  说明：两者正文相同时留哪条在**语义上等价**，但必须有一个**与运行环境无关的确定答案**；
  选 parent 优先只是让「留下的那条」在元数据上更完整（父块 heading 层级更全），
  不是因为它更相关 —— 这点在测试里显式锁了「正序与逆序两种输入给出同一条结果」。

★★ 本批因此浮出一个**已知且有意不处理**的残留：

  `content_hash` 只能抓「完全相同」，**抓不到「父块 ⊇ 子块」的包含关系**。
  真实 Top-K 里确实存在这种对（探针实测：top-20 里 48 对包含 vs 22 个完全相同名额）。
  本批不处理，理由是第四节 S4 的实测（limit=3 窗口内零增量）。

═══ 九、口语化金标 7 条复核（★ 推翻了登记里的「疑似假阴性」） ═══

证据：reports/rag_ingestion_auth_review/B17_colloquial_gold_recheck_20260925.txt
可复跑：scripts/audit_colloquial_gold.py --top-k 50

B8 的审查留下了一句尾巴：

  > 30 条里 7 条两路 top-50 全捞不到，**疑似金标假阴性**，未逐条复核 ——
  > 所以「口语化场景已评测到可信」这句话不成立。

本批把这句话判掉了。判据是**二分**的，且**刻意绕开检索**：

  Q: 金标 span 到底在不在库里？
     ├─ 在库里却没被召回 → **真·检索失败**（金标有效，检索背）
     └─ 库里根本没有     → **金标假阴性**（金标背）

「在不在库里」用的是**全库 chunk 压平文本拼接后直接做子串判断**，
因此与检索能力完全解耦；命中判据**import** 评测脚本的 `span_matches`（不复刻，防口径漂移）。
配套还查 `gold_document_id` 与 `gold_heading` 是否在库（假阴性的常见形态）。

实测：

  | 项 | 数字 |
  | --- | --- |
  | 用例总数 | 30 |
  | dense top-50 命中 | 20 |
  | sparse top-50 命中 | 4 |
  | **两路都未命中** | **7** |
  | ├─ span 在库里 → 真·检索失败 | **7** |
  | └─ span 不在库里 → 金标假阴性 | **0** |

  7 条**逐条**都满足「span 在库里 / 文档在库里 / 章节在库里」，就是进不了 top-50。
  例（c024）：query「自己家卖的东西售后是按什么规矩来的」，
  金标 span 在《售后政策（自营）常见问题解答》第 3 节里**真实存在**，两路 top-50 都召不回。

★ **结论修正：登记里的猜测方向反了。** 不是金标假阴性，
  而是**口语化改写与库内表述的词面距离过大** —— 7 条全库可达的内容，两路 top-50 都捞不回来。

  影响有三条，都不许混着说：
  1. 「口语化 R@1 0.4000」**不是**被劣质金标拖低的 → **不能用"金标有问题"去解释**；
  2. 但**也不能**反过来当干净结论存档：**假阴性 0 条只说明金标有效，不说明口径已统一**
     （A 轨 intent 口径 F2 仍未修，两套数字不可互认）；
  3. 这一条给出了**下一步的真问题**：口语化查询需要的是**查询改写 / 同义扩展**，
     而不是继续调融合权重（B8 已证等权融合有害、`w_dense=10` 已是唯一不掉点的配置）。

═══ 十、延迟实测：去重 0.046 ms/次（登记要求「必须量到并如实报告」） ═══

证据：reports/rag_ingestion_auth_review/B17_latency_20260925.txt

登记里有一条硬要求：超额召回会推高延迟，**必须把延迟一起量到并如实报告**。
本批的答案分两层 —— 一层是结构性事实，一层是实测：

**结构层（为什么本批"不该"慢）**：召回条数**一条没改**。
`top_k = limit × 5`（下限 20）是 B8 **之前**就有的取值，本批只把「截断」从第 limit 条
后移到「去重之后」。有测试钉住这个常量
（`test_oversampled_recall_is_requested_from_search` 断言 `top_k == 20`）。

**实测层**（7 条 query × 3 轮 = 21 次，tenant-dev，真实索引 v4）：

  | 测什么 | 均值 | 中位 | 最大 |
  | --- | ---: | ---: | ---: |
  | 底层 `search_chunk_index(top_k=20)` | 203.21 ms | 150.27 ms | 771.48 ms |
  | `retrieve_chunk_items(limit=3)`（含去重） | 180.91 ms | 150.03 ms | 290.55 ms |
  | `select_diverse_evidence(20 候选)`（纯去重） | **0.046 ms** | 0.046 ms | 0.18 ms |

  * **去重纯开销 0.046 ms/次 ≈ 整次检索的 0.0253%** ——
    对 20 条候选做一次空白归一化 + 排序，与「FAISS 检索 + 每次重读 19.0MB manifest」
    相比完全可忽略；
  * 条目层比底层还小了 22 ms —— 这个差值落在**同一环境的正常散布**内
    （底层自己最大 771 ms vs 中位 150 ms），也就是说**它是噪声，不是信号**；
  * 结论：**本批不构成延迟劣化**，也**没有**数据支持把 F6（manifest 缓存）提前。
    真正吃掉时间的是 F6 那条「每次检索重读 19.0MB manifest」，与本批无关。
