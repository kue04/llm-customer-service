═══ 五、本批修复的缺陷（唯一让门禁红过的真缺陷） ═══

**现象**
开工基线 `2 failed, 837 passed`，两条都在 `TestIdempotency`：
  · test_redelivering_a_finished_job_changes_nothing
  · test_chunk_ids_are_stable_across_reruns
两条的共同点：都是「任务已经 succeeded 之后再跑一次」。失败阶段是 `persisted`。

**根因**（不是"幂等逻辑写错了"，而是删除原语与它自己的注释相反）

`repository.delete_chunks` 的注释写着：

    父 chunk 的复合自引用外键是 (document_version_id, parent_chunk_id)，
    删除时只要一次全量 delete 即可：外键在同一语句内整体消失，
    不需要先删子再删父（逐条删反而会中途撞外键）。

但**代码用的正是被注释否定的做法**：`session.delete(row)` 逐行删。ORM 于是发出
`DELETE FROM document_chunks WHERE id = ?` 的 executemany —— **每行一条独立语句**；
而 SQLite 对即时外键约束的检查发生在**每条语句结束时**，删父 chunk 那条语句结束时
子 chunk 还指着它：

    sqlalchemy.exc.IntegrityError: FOREIGN KEY constraint failed
    [SQL: DELETE FROM document_chunks WHERE document_chunks.id = ?]

首次执行之所以全绿，是因为**首次执行时表里没有旧行可删**（`rows` 为空，循环不执行），
这个缺陷只在"重跑"路径上暴露 —— 而幂等测试恰好是唯一会走重跑的用例。

**修复**
`delete_chunks` 改为**一条** `DELETE ... WHERE tenant_id = ? AND document_version_id = ?`
（批量 delete + `synchronize_session="fetch"`，让 session 里已删实例同步失效）。
整个版本的行在同一语句内一起消失，约束在语句结束时看到的已是"全部删完"的一致状态，
因此既不需要「先删子再删父」的拓扑排序，也不需要 `ON DELETE CASCADE`
或 `PRAGMA defer_foreign_keys`。

**验证**
  · `pytest tests/test_ingestion_pipeline.py -q` → 49 passed
  · 全量 `pytest -q` → **839 passed**
  · ruff / compileall / 体积检查 → 全绿

**面试怎么讲** → 已登记为踩坑 **B13**（四段式）。核心一句：
「ORM 的 `session.delete(row)` 循环**不等于**一条批量 DELETE；
自引用外键下前者会变成 N 条独立语句，每条都要独立满足约束。」

═══ 六、偏离计划原文的方向标注 ═══

沿用 B10 的规则：每条都标方向（**更严 / 更宽 / 换实现 / 计划外新增**），不偷改。

1. `normalized` 阶段**不做二次清洗** —— 【更窄，有意】
   计划只给了阶段名，字面像是"再归一化一遍正文"。实现把它定义成
   **归一化「输入」**（配置 + 归属上下文 + 留痕），清洗仍归切分器内部（B5 已交付且带计数）。
   理由：同一件事两个实现，清洗规则一改两处就会不同，而"少了一段内容"几乎看不出差异。

2. **不做断点续传**，改为「准备模式重算不重写 / 执行模式正常执行」 —— 【换实现】
   代价：重试要多花一次解析 + 切分的 CPU。收益：少一套「中间产物持久格式 + 生命周期 + 清理策略」。
   取舍理由：省一次解析换来一套新状态机，不划算。
   **副作用需要如实说明**：`persist=False` 的阶段仍会**重算**（纯函数、确定性），
   因此"重试 N 次"与"执行 1 次"的**最终数据相同**，但**耗时更长**。

3. **失败不抛异常，以 `status='failed'` 返回** —— 【更可测 / 更适合批处理】
   `process_job` 是"不抛业务异常"的入口；真正不可预期的异常也会被兜成
   `error_code=unexpected_error` 并保留 traceback 到日志。

4. **空文档：切分 0 chunk 是成功，且跳过索引阶段** —— 【更宽 + 更严】
   更宽：0 chunk 不判失败（内容为空是可解释的结果）。
   更严：**不为 0 向量建索引** —— 建了会让"已有生效索引"变成假象，
   而实际上检索端什么也检索不到。
   证据：TestWarningsAndEmptyDocuments::test_empty_document_publishes_without_an_index

5. **文档状态只在"确实没有任何已发布版本"时才置 failed** —— 【更宽/更保守，有意】
   若一份文档已有可用旧版本、新版本处理失败，整体标 failed 会让用户以为
   "这份文档不能用了"，而旧版本其实还在正常服务。
   证据：TestStageFailures::test_document_is_marked_failed_only_when_no_published_version_exists

6. **`list_indexable_chunks` 默认不过滤版本状态** —— 【更宽，理由见 [D-11]】
   「索引文件里有什么」与「谁能检索到」是两件事，可见性交给检索层 fail-closed filter 决定。
   若把可见性只押在"构建时过滤"上，ACL / 生效期一变就得重建整个索引，
   而且仍然挡不住"同一份索引被两个租户共用"。

7. **检索层多做的 chunk 级路径 + 强制 `access` 参数** —— 【计划外新增 + 更严】
   见第四节第 5 条。缺 filter 必须**报错**而不是默认全库：默认全库 =
   "少传一个参数就把所有租户的数据都检索出来"，而调用方写代码时根本不会注意到。

   解析警告与切分统计**同住一个数组**，不另起键。
4. 任务状态推进只走 `fail_ingestion_job()` / `update_ingestion_job()`（后者支持只改 stage）。
