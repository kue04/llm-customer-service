三、超出规格处（逐条标注方向：更严 / 更宽）
------------------------------------------------------------------------------------
1. **缓存键多带两维**（`manifest_path` + `pointer.fingerprint`）—— **更严**。
   规格只要求 `(root, index_name, index_version)`。多带指纹的原因：版本目录按设计
   不可变，但"同版本原地重写"是**不报错的**静默错配场景，指纹一变键就变，
   自动重读。代价 = 0（指针本来就要读）。有专门用例
   `test_same_version_with_new_fingerprint_is_reread` 钉住。
2. **条数上限 + 同一 (root,index_name) 只留当前生效版本** —— **更严**。
   规格未要求。不加的话，每重建一次就多留一份 19MB manifest，长跑服务会吃光内存。
3. **顺带修正 README 一处已被推翻的对外口径** —— **更严（更准确）**。
   README §3.6「不达标 / 未做」表里"口语化 7 条**疑似**金标假阴性，未逐条复核"
   是 **B17 已经推翻的结论**（B17 实测：7 条全是真·检索失败，假阴性 0 条），
   但 README 没跟着改 —— 属于把一条已被验伪的猜测留在对外文档里（D28 的同款风险）。
   本批只改这一行文字，措辞与 B17 的证据一致，**不新增任何数字**。
   （本批改 README 的另一处是 F6 自己那行 + 测试数派生值，属规格内。）

   然后才动手。**没有照着文档的"三批未提交"去写任何记录。**

2. **失效为什么不需要"显式调用钩子"（想清了才写码）**：
   索引切换 = 新版本目录 rename + `current.json` 一次 `os.replace`。缓存键含
   `pointer.index_version`，而指针**每次真读**（0.09 ms），所以：
   * **两个请求同时未命中**：都读到同一份内容，各自 insert 同一个键；
     dict 的 get/set 在 GIL 下是原子的，insert + 淘汰在锁内；
     最坏情况是**多读一次文件**，不会出现半个对象（本批已用 8 线程用例实测）。
   * **重建索引与读缓存并发**：发布是原子的 —— 指针未切之前读者一律看旧版本
     （自洽）；指针切了之后第一次读就是 miss → 读新版本。**不存在"版本已切、
     缓存还以为自己是新的"这个窗口**，因为失效判据取自指针而不是缓存自己的状态。
   * **未验证的部分**：没有做"重建进程与检索进程真并发"的端到端压测
     （单机 SQLite + 进程内缓存很难构造可信场景）。见 §五。

五、测试盲区（哪些没测、为什么、风险多大）
------------------------------------------------------------------------------------
1. **重建与检索的真并发**（未测）。已测"8 线程读同一版本"与"顺序切换后首次读"，
   但没有让一个线程持续 rebuild、另一个线程持续检索。理由：单机 SQLite +
   进程内缓存构造出的竞态不可复现，写出来只会是一条偶发红的用例。
   **风险：低**。发布路径是原子 rename + 原子指针替换，读侧只读指针 + 只读文件；
   真正的残余风险是"多次 rebuild 竞态"（交接文档 §1.6 第 7 条，**本来就未测**），
   本批没有把它变得更容易发生。
2. **多进程部署下的缓存一致性**（未测，也不适用）。缓存是**进程内**的，
   多 worker 场景下每个进程各有一份；正确性由"指针即失效信号"保证（每个进程都会
   重新读指针），代价是内存 × 进程数（每份 manifest 约 19MB）。
   **风险：内存**。这条**必须在部署时算进内存预算**，已写进交接文件。
3. **冷启动首读成本未优化**（有意）。`--label after` 里 `load_active_manifest`
   的 `first_ms` = 96.5 ms —— 进程起来第一次仍要付一次全量反序列化。
   本批**刻意不做预热**（预热要么在检索路径里触发写/读，破坏只读语义；
   要么加启动钩子，属另一批的部署话题）。已如实记在 README 与台账。
4. **`MAX_CACHED_MANIFESTS=8` 的容量**只测了"不超过上限"，没测"达到上限时被淘汰的
   是哪一个"。淘汰用的是插入序（FIFO），不是 LRU。理由：正常部署只有 1 个 root ×
   1 个 index_name，上限根本摸不到；真正需要它的是测试这类"很多临时 root"的场景。
   **风险：极低**（淘汰错对象只会导致多读一次文件，不影响正确性）。
