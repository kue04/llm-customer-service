── 3.4 ★ 计划 2.2 的「重复文件标记 duplicate」实现位置说明（阶段收尾的必要条件）★ ──

计划 2.2 的字面表述是「每份原文件计算 SHA-256；重复文件标记 duplicate，
不能创建第二份有效文档版本」，把这两件事写在同一段里，读起来像「2.2 就该实现
duplicate 标记」。**实际拆分如下，这是有意的，不是遗漏：**

* **机制在 2.2**：每份原文件的 SHA-256 由解析模板统一计算并写入
  `ParsedDocument.metadata["content_hash"]`（`REQUIRED_METADATA_KEYS` 保证它必然存在）。
  解析器只**产出** hash，不判定重复 —— 它既不接收 tenant_id，也不访问数据库，
  这两条各有测试兜底（`test_parsers_do_not_accept_tenant_id`、
  `test_parser_modules_do_not_depend_on_database`）。
* **判定在 3.3（流水线）**：流水线在 `parsed` 阶段拿到 content_hash 后调用
  `repository.find_version_by_content_hash(session, tenant_id, hash)`，
  命中则把 `documents.status` 标为 `duplicate`、**不建新版本**、job 正常结束。
  判定需要流水线上下文（同租户下已有版本、当前 job 的 document_id、事务边界），
  这些在纯函数式的解析器里根本不可得。
* **数据库级保证在阶段 1**：`uq_document_versions(tenant_id, content_hash)`
  保证「同一租户内相同内容不得产生第二份版本」。这是数据库层的兜底，
  与流水线的判定是两层防线：即使流水线判漏了，写入也会被约束拒绝，
  不会静默产生重复版本。
* **为什么不让上传接口来做判定**：上传期还不知道 content_hash（不解析就算不出来），
  若为了判定而提前解析，就把「上传只做准入 + 落对象 + 建任务」的边界打破了，
  也会让上传接口的响应时间取决于文件大小与解析器性能。见 [D-6]。

因此：**2.2 的范围是「产出 hash 的机制」，不是「duplicate 状态的判定」**；
判定与状态流转属于 3.3。本阶段（2.3）的上传接口也**不做**内容 hash 的重复判定，
这一点已由 AST 守卫测试（不 import hashlib）与 [D-6] 的决策记录双重固定。
按此口径，计划 2.2 的这条要求**不构成缺口**。

── 3.5 阶段 2 额外加固（计划未显式要求，但属于同类风险）──

  · **扩展名优先于 MIME**（parser_registry.detect_source_type），并有测试锁定。
    若反过来，攻击者可以用「报表.pdf + Content-Type: text/html」绕过基于扩展名的
    准入规则；B4 在此基础上把这条性质**在新接口上再验证了一遍**。
  · **注册表拒绝重复注册与未知来源类型**，避免「解析行为取决于注册顺序」。
  · **默认注册表懒加载**：OCR 阈值环境变量配错时在首次解析才暴露。
  · **降级兜底必须是严格改进**：HTML 结构遍历结果不足时，只有 trafilatura 抽出的
    文本**严格多于**结构结果才降级（两个失败用例都是在实现期被测试逼出来的，见风险 3）。
  · **B4 新增的三条守卫**（都是「用测试而不是纪律保证」的延续）：
    队列缓存必须有（内存队列每次请求新建会让投递内容随请求消失，有测试断言同一实例）；
    LocalObjectStore 写出前先落临时文件再 os.replace（半截文件不会被流水线读到，
    并断言不留 .tmp 残留）；审计摘要只对自由文本脱敏（见上文，是测试逼出来的修正）。

── 3.6 实现期被测试逼出来的两个真实缺陷（记录以备考）──

1. **JWT 的 sub 不是 users.id**。第一版直接拿 `auth.user_id` 去比对
   `knowledge_base_members.user_id`（该列是指向 `users.id` 的外键），
   结果是「成员关系存在也永远匹配不上」→ 写权限被无声全判 403。
   线上表现会是「加了成员也用不了」，且不报任何错。

2. **通用脱敏规则会打碎结构化 ID**（见 3.3 审计那一条），

── 3.7 回头审查：三处「超出对接文档原文」的取舍 + 一处覆盖盲区（B4 收尾后补记）──

本节是 B4 交付完成后**回头看**的产物。目的不是复述「做完了」，而是把
「本实现比对接文档字面要求**更多 / 更宽 / 更严**的地方」全部显式标注出来。
这些取舍本身没问题，但如果不写清楚，下一位执行者会误以为它们是文档要求，
从而在改动时错判约束强度（例如以为「放宽写权限」不需要额外决策记录）。

[A] 更严：写操作要求「知识库**写**成员」，而不只是「有成员关系」
    对接文档 3.1 第 2 步只要求「校验成员身份（无成员关系 403）」，未区分角色。
    实现额外收紧了：只有 owner / editor 能写（KB_WRITE_MEMBER_ROLES），
    reviewer / viewer 一律 403。
    依据：若「有成员关系即可写」，viewer 就能上传并覆盖同名文档的对象字节，
    使成员分级形同虚设；
    代价：与文档字面存在差异 —— 按文档写客户端的联调方会以为 viewer 能上传。
    故在此显式记录。已同步到 3.3 权限段与台账 [D-7] 第 4 点。

[B] 更宽：内容一致性只在「嗅探结果明确」时拒绝，且 html 前缀命中**不拒**
    对接文档 5.2 给的策略是「只在嗅探结果明确且与扩展名不一致时拒绝（415），
    None 一律放行」，但没有定义「明确」的边界。实现把它物化为**两级**：
      · 强特征（`%PDF-` → pdf；zip 内含 `word/` 条目 → docx）：不一致必拒 415；
      · 弱特征（html 的 `<!DOCTYPE html` / `<html` 前缀启发式）：即使嗅出 html，
        也不作为拒绝依据 —— Markdown 内嵌 HTML 是常见写法，
        按内容拒收会造成「正常文档传不上去」；
      · 无魔数（md / txt）：嗅探返回 None（不做近似判断），放行。
    即：相对文档，实现**更宽**之处是「html 前缀命中也不拒」，
    **更明确**之处是把「明确」定义成了可测试的两级枚举。
    文档原话「HTML…允许不确定」与本实现方向一致，
    但文档没说「嗅出 html 之后到底拒不拒」，该缺口由此决策补齐。

[C] 更严：`source_uri` 由服务端从文件名派生，**不接受客户端传入**
    对接文档 3.1 第 7 步只说「用 `get_document_by_source_uri` 命中则复用」，
    没有规定 `source_uri` 的来源。实现取「净化后的文件名」派生
    （`upload://<净化文件名>`），并忽略 body 中的同名字段。
    依据：若允许客户端自报 `source_uri`，KB-A 的成员就能传入 KB-B 文档的 URI
    给别人的库追加版本 —— 一个越权写入口。已同步到 [D-7] 第 1 点。

[D] 覆盖盲区（**已补**，属于「实现正确但没测到」，不是「已知未实现」）
    成员角色矩阵原本只采样了三个点：editor（放行）、viewer（403）、
    无成员关系（403）。而 `KB_MEMBER_ROLES` 有**四个**合法角色 ——
    **owner（写白名单的另一半）与 reviewer 都没有用例**。
    盲区后果很实在：若实现把 `KB_WRITE_MEMBER_ROLES` 误写成 `{"editor"}`，
    测试会**全绿**，但「库主（owner）传不上自己的文件」在线上必然发生。
    已补 4 条：
      · `test_upload_allows_knowledge_base_owner`（补上白名单另一半）
      · `test_upload_rejects_reviewer_member`（reviewer 有「审核」语义，最易被误认为可写）
      · `test_upload_respects_knowledge_base_role_matrix[owner|editor|reviewer|viewer]`
        —— 由 `KB_MEMBER_ROLES` 与 `KB_WRITE_MEMBER_ROLES` **两张真值表驱动**而非抽样，
        以后往角色枚举里加值，要么被接纳、要么被拒，不会出现
        「既没被授权、也没有测试提醒」的静默缺口；
      · `test_write_member_roles_are_a_strict_subset_of_all_member_roles`
        —— 纯集合断言，同时守两个方向：拼错角色名（如 `"ower"`）会导致
        「加了成员也永远 403」且不报错；写白名单等于全集则说明分级失效。
    测试文件 **100 → 107**，全量 **548 → 555**（见第二节，已重跑）。

═══ 四、风险与回滚点 ═══

风险 1（继承自 B2，未消除）：本机无 Docker / 无 PostgreSQL，
  数据层只在 SQLite 上实测。缓解与复验安排同阶段 1，归入阶段 7 门禁。

风险 2（B3 引入，未消除）：**PDF 标题识别是启发式的**（字号倍数 + 长度 + 句末标点）。
  会误判，但只影响 heading_path 的丰富程度，**不会丢内容** ——
  最坏情况是一个段落被当成标题。若真实 PDF 的层级还原不准，可考虑 pymupdf_layout。

风险 3（B3 引入，已在实现期消除，记录以备考）：HTML 降级兜底最初有两个缺陷 ——
  (a) 送进 trafilatura 的是**未清洗**的 HTML，它会从已被判定为噪声的 nav/footer
      里把内容捞回来，等于同一策略在两处得出互相矛盾的结论；
  (b) 只要兜底结果非空就降级，于是 4 个字的合法短页面也会被判定为「降级」。
  修复：改送清洗后的 HTML，并要求兜底结果严格多于结构结果。

风险 4（B3 引入，未消除）：**扫描件 OCR 未在真实引擎上跑过**。
  本机默认不装 rapidocr-onnxruntime，全部触发逻辑用注入的假引擎覆盖，
  真实引擎的接入效果（识别质量、单页耗时、内存占用）需要单独复验，归入阶段 7。

风险 5（B4 新增，未消除）：**Redis 分支没有连过真实 Redis**。
  Redis Stream 实现用注入的假客户端断言 XADD 参数与 XLEN，
  「配了 URL 却没装客户端」用 `sys.modules["redis"] = None` 模拟。
  真实 Redis 上的行为（连接、重连、消费组创建）归入阶段 7 门禁；worker 属 3.3。

风险 6（B4 新增，需注意）：**同名重传会覆盖同一个对象 key**。
  同一租户内「同名 = 同一份文档」，重传即这份文档的新修订，因此 key 相同、对象被覆盖。
  代价：如果两次上传之间 job 还没被 worker 消费，先到的 job 会读到后一份字节。
  缓解：流水线必须在拿到 job 后尽快读取字节，并以 content_hash 唯一约束兜底
  （最坏结果是一个 duplicate 标记，不是数据损坏）。
  若产品上要求保留每个修订的原始字节，需要给每次上传独立的 blob key，
  那要动 ingestion_jobs 表结构（新增列必须走 Alembic 迁移），
  属于一次明确的范围变更，不在本批内。

风险 7（B4 新增，需注意）：**读接口目前只做租户过滤 + 操作权限，还没有资源级 ACL**。
  `document:read` 与 `document_acl` 表属于阶段 4.1 / 4.2，
  届时在仓储层的查询条件上收紧，端点签名不变。

风险 8（B4 新增，需注意）：**对象写入与元数据写入不是同一个事务，失败会留下孤儿字节**。
  对象存储与数据库之间没有分布式事务，两者只能靠顺序与回滚尽力对齐：
  当前顺序是「先查/建 document（事务内）→ 写对象 → 建 job + 写审计 → 提交」。
  对象 key 含 document_id，而新文档的 id 只有插入后才有，因此**事务确实跨在对象写入之外**
  （这是「先落库再写对象」的直接结果，也换来一个好处：对象写入失败时整条记录随事务回滚，
  不会留下「有文档没有字节」的空壳）。代价是反方向的不一致 —— 对象已写入而提交失败时，
  对象存储里会残留一份无人引用的字节。
  缓解：流水线以 job 为入口、以 content_hash 唯一约束兜底，孤儿字节不影响正确性，
  只占空间；彻底清理需要一个按对象存储与 documents 表对账的任务，归入阶段 7 门禁项。
  另需注意：本地磁盘写入极快，但换成 S3 后这段事务会覆盖一次网络写入的时长 ——
  50 MB 上限下的同步写入仍在可接受范围内，若将来放宽上限需要重新评估（改为
  「先写对象 → 再开事务」或异步直传）。
