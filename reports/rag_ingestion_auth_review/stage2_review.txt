      七个字段齐备（Block.to_dict() 一一对应，测试断言）。

[√] 解析器不得写数据库
      不靠纪律，靠两条可执行断言：

      不吞异常的证明是 `__cause__` 断言，而不是「看起来会抛」：
        · test_unexpected_exception_is_wrapped_without_being_swallowed
          注入 RuntimeError → 断言 error_code=parse_failed 且 __cause__ 是原 RuntimeError
        · test_parser_error_from_subclass_is_not_rewrapped
          子类抛 ParserError → 原样上抛，不被二次包装丢错误码
        · test_invalid_produced_document_is_rejected
          解析器写出「表格块没有 table_json」的产物 → 在源头失败，不流到下游

阶段 2 额外加固（计划未显式要求，但属于同类风险）：
  · **扩展名优先于 MIME**（parser_registry.detect_source_type），并有测试锁定。
    若反过来，攻击者可以用「报表.pdf + Content-Type: text/html」绕过基于扩展名的
    准入规则，让 HTML 解析器去处理本该被 PDF 规则约束的文件。
  · **注册表拒绝重复注册与未知来源类型**，避免「解析行为取决于注册顺序」。
  · **默认注册表懒加载**：OCR 阈值环境变量配错时在首次解析才暴露，
    而不是在任何人 import 该模块的瞬间炸出一个看不懂的栈。
  · **降级兜底必须是严格改进**：HTML 结构遍历结果不足时，只有 trafilatura 抽出的
    文本**严格多于**结构结果才降级。否则一篇只有一句话的合法短页面会被无谓地
    丢掉结构信息并平白多一条警告。两个失败用例都是在实现期被测试逼出来的，见下方风险 3。

═══ 四、风险与回滚点 ═══

风险 1（继承自 B2，未消除）：本机无 Docker / 无 PostgreSQL，
  数据层只在 SQLite 上实测。缓解与复验安排同阶段 1，归入阶段 7。

风险 2（新增）：**PDF 标题识别是启发式的**（字号倍数 + 长度 + 句末标点三个条件）。
  会误判，但只影响 heading_path 的丰富程度，**不会丢内容** ——
  最坏情况是一个段落被当成标题。若后续发现真实 PDF 的标题层级还原不准，
  可考虑引入 pymupdf_layout（PyMuPDF 运行时会打印推荐该包的提示）。

风险 3（新增，已在实现期消除，记录以备考）：HTML 降级兜底最初有两个缺陷 ——
  (a) 送进 trafilatura 的是**未清洗**的 HTML，它会从已被判定为噪声的 nav/footer
      里把内容捞回来，等于同一策略在两处得出互相矛盾的结论；
  (b) 只要兜底结果非空就降级，于是 4 个字的合法短页面也会被判定为「降级」。
  两者都不是靠 review 发现的，而是被 test_html_blockquote_text_is_not_duplicated
  与 test_html_without_extractable_text_reports_empty_document 直接逼出来的。
  修复：改送清洗后的 HTML，并要求兜底结果严格多于结构结果。

风险 4（新增）：**扫描件 OCR 未在真实引擎上跑过**。
  本机默认不装 rapidocr-onnxruntime，全部触发逻辑用注入的假引擎覆盖。
  真实引擎的接入效果（识别质量、单页耗时、内存占用）需要单独复验，
  归入阶段 7 发布门禁。

回滚点：本批改动集中在

  services/ingestion/parser_registry.py（新增，可删）

  tests/test_document_parsers.py、tests/fixtures/、scripts/make_parser_fixtures.py、
  .gitattributes（均为新增，可删）
  requirements.txt / requirements-dev.txt（可 git 恢复）
与阶段 1 的鉴权改动、迁移、仓储层**完全无耦合**，两个方向都能独立回滚。

═══ 五、遗留问题（不阻塞本文件结论） ═══

1. **2.3 未实现**，阶段 2 未结束，阶段级结论待回填。这是本文件唯一的功能性缺口。
2. HTML 的列表项每项单独成块，而 Markdown 的连续列表合成一个块。
   两者语义不同（<li> 是显式结构，Markdown 列表是纯文本推断），故未强行统一；
   切分器（3.2）需要同时处理这两种形态。
3. PDF 表格识别依赖 PyMuPDF find_tables() 的 lines 策略，只靠空格对齐的
   「表格」不会被识别（符合预期）；识别失败时降级为正文而不中断解析。
4. DOCX 单元格合并（w:gridSpan / w:vMerge）不做还原，合并区域的文字会在每个
   参与合并的格子里各出现一次。这是有意取舍：还原 vMerge 需要状态机，
   而错误还原会把内容错位到别的列，比重复出现更危险。
5. 本机 venv 在 B3 期间被破坏过一次并已按轻量口径重建（不含 torch / transformers /
   datasets / trl / peft / sentence-transformers）。这不影响任何测试与 lint 门槛
   （tests/ 下零处导入这些包），但需要真实模型推理时得按 requirements.txt 补装。
   细节记录在台账第 5 节坑 3。
