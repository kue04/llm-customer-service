      target_tokens=450 / min_tokens=120 / max_tokens=700 / overlap_tokens=80 /

      证据：tests/test_chunking.py::TestChunkConfigDefaults::test_defaults_match_plan_3_1
[√] 允许知识库配置覆盖
      `ChunkConfig.replace_overrides(mapping)` / `build_config(overrides)`：

      证据：TestChunkConfigOverrides::test_knowledge_base_override_layers_on_top_of_base
[√] 每个文档版本保存「实际生效配置 + tokenizer 标识」
      `ChunkConfig.storage_payload()` → {"config_version", 全部字段, "tokenizer_id"}；

      `document_versions.metadata_json["chunking"]`；
      每个 chunk 的 metadata_json 里还冗余记了 tokenizer_id / chunker_version /
      chunking_config_version（便于脱离版本记录解释单个 chunk）
      证据：test_storage_payload_carries_tokenizer_and_version、
            test_result_exposes_effective_config_for_version_storage
[√] 配置越界时启动失败并给出字段错误（**不静默夹取**）
      `ChunkConfig.__post_init__` 抛 `ChunkConfigError`，错误对象含逐字段
      (field, message, value)；模块级 `CHUNK_CONFIG` 在 **import 期**构造并校验，
      所以任何 import 本模块的进程都带着非法配置一起启动失败；
      证据：TestChunkConfigValidation 共 22 条参数化用例（越界 / 类型 / 布尔子类陷阱 /
            跨字段约束）；test_import_time_failure_on_bad_env 用**子进程**验证
            「进程起不来」，stderr 里能看到 max_tokens 字段与出错的值。

方向标注（3.1 有两处比计划更严，均为有意为之）：
  * [更严] 未知配置键报错而不是忽略。计划只说「允许知识库配置覆盖」，
    没说拼错的键怎么处理。若静默忽略，`{"max_token": 700}`（少一个 s）
    会让配置看起来生效、实际用默认值跑完全程 —— 这类错误只能靠「不认识就报错」兜住。
  * [更严] 布尔字段拒绝字符串 "false"。JSON 里写错类型时，
    Python 的 `"false"` 是**真值**，静默接受会得到与直觉相反的行为。

[计划外新增] 第 7 个配置项 `parent_max_tokens`（默认 2800 = 4 × max_tokens）
  理由：一个 section 可能是一整章。让它整体当 parent，会产出一条几十万字符的记录，
  它既不参与 embedding，也没有检索路径会用这么长的上下文，只是把库撑大。
  计划 3.1 只给了 6 个「初始默认值」，这属于实现补的一个边界参数，
  校验规则是 `parent_max_tokens >= max_tokens`。已在下方向表中登记。


三、3.2 实现结构化切分器 —— 逐条核对（9 条要求）
--------------------------------------------------------------------------------
第 1 条 先按标题层级和页码分组，再按段落切分
  [√] `_group_sections`：按 `(block.heading_path, block.page)` 切**连续**块。
      标题块的 heading_path「包含自己」（B3 契约），所以「标题 + 它的正文」天然同组，
      不重建层级。
  [√] 同名标题出现在两个不相邻位置时**不合并**（否则 parent 会跨越无关内容）
      证据：test_same_heading_in_two_places_is_not_merged、
            test_same_heading_on_different_pages_splits_sections、
            test_different_heading_paths_produce_separate_parents

第 2 条 超过上限的段落依次按句号、问号、分号、换行切分
  [√] `_split_overlong` 固定四级：句末标点 → 分号 → 换行 → 按 token 硬切
      证据：test_splits_on_sentence_endings / test_falls_back_to_semicolons /
            test_falls_back_to_newlines / test_hard_splits_when_there_is_no_punctuation_at_all /
            test_hard_split_never_loses_characters
  [补全] 计划只定义到「换行」，实现多了一级「按 token 硬切」：
      无标点长串（OCR 产物常态）若不硬切，会变成 3000 token 的 chunk，
      把 max_tokens 这条硬约束直接架空。硬切计入 stats.hard_split_units，
      不静默发生。
  [合并] 计划把「句号、问号」写成两级，实现合并为一级（同一类句末终止符 `。！？!?`）：
      拆分结果与逐级拆完全一致，因此合并只是实现层面的简写。

第 3 条 表格按行分块并重复表头；代码块不从内部截断
  [√] `_table_units`：表头 + 成组行；每组首行都是表头
      证据：test_header_is_repeated_in_every_chunk（4 块，每块首行都是表头）、
            test_every_row_appears_exactly_once（每行恰好出现一次）、
            test_table_content_is_rendered_from_table_json、test_header_only_table_keeps_header
  [√] 代码块整块保留，绝不内部截断
      证据：test_code_block_is_never_cut_internally（10 行代码 + max=5 → 仍是 1 块）、
            test_oversize_code_gets_its_own_chunk、test_code_indentation_is_preserved
  [取舍] 见下方「偏离」表第 1 条：代码块与 max_tokens 的冲突处理方式。

第 4 条 列表项尽量保持完整
  [√] `_list_units`：先按项边界切 item，再把 item 贪心装箱；
      只有**单个 item 自己超限**时才进入项内拆分，并计入 stats.list_items_split
      证据：test_markdown_list_items_stay_whole（每行都是完整项）、
            test_oversize_list_item_is_split_inside_and_counted、
            test_html_style_single_item_blocks（HTML 每项一块的形态）、
            test_continuation_lines_stay_with_their_item、test_list_without_markers_is_treated_as_one_item

第 5 条 相邻 child chunk 重叠 80 tokens，chunk 不超过 700 tokens
  [√] `_pack_children` + `_take_overlap`
      证据：test_every_child_respects_max_tokens、test_adjacent_children_overlap_by_target、
            test_overlap_appears_verbatim_in_the_next_chunk、
            test_overlap_never_pushes_chunk_over_max、
            test_overlap_stays_within_twice_the_target、test_overlap_can_be_disabled、
            test_default_config_overlap_is_applied（生产默认配置 + 默认 tokenizer）
  [度量口径] 重叠按**单元边界**取整，因此实际重叠 ≥ 目标值（不是恰好 80），
      且被限制在 2×目标以内（防止上一块尾部是一个巨大单元时把新块塞满重复内容）。
      为验证这件事，测试里实现了「接缝共享文本」度量（字符级最长公共后缀/前缀 →
      再按 tokenizer 计 token）。

第 6 条 每组 child chunk 指向一个 parent chunk
  [√] 每个 parent 组产出一行 parent + N 行 child；child.parent_chunk_id 指向该 parent
      证据：test_parent_chunk_enabled_by_default、test_every_child_points_to_an_existing_parent_of_its_own_section、
            test_child_body_is_a_contiguous_part_of_its_parent（child 正文是 parent 正文的连续片段）、
            test_parents_come_before_their_children（父先于子）、
            test_parent_max_tokens_splits_giant_sections、test_parent_can_be_disabled
  [更严] 重叠**只在同一个 parent 内部**发生，不跨 parent。跨 parent 重叠会把上一节正文
      带进下一节，检索时表现为「引用出处对不上」。

第 7 条 标题路径可作为上下文前缀，但不得重复原文主体
  [√] `_section_prefix` + `_prefix_would_duplicate`（三重判据：整段前缀出现在正文开头 /
      正文首行等于最后一级标题 / 正文首行等于完整前缀）+ 前缀计入 token 预算
      证据：test_prefix_is_the_flattened_heading_path、test_prefix_is_not_repeated_when_body_already_starts_with_heading、
            test_prefix_is_not_repeated_for_last_heading_component_only、
            test_prefix_can_be_disabled_but_heading_text_is_kept、
            test_prefix_is_dropped_when_it_would_break_the_limit、
            test_prefix_counts_towards_token_budget
  [补全] `preserve_heading_path=False` 时，标题文本会以正文首行的形式保留 ——
      否则关掉前缀就等于让标题从 chunk 里彻底消失，「按标题检索」整类失效。

第 8 条 去除空白、重复页眉页脚和完全重复段落

      空白：test_strips_trailing_spaces_and_invisibles / test_collapses_blank_lines_and_trims_edges /
            test_drops_empty_and_non_text_blocks_with_counters
      页眉页脚：test_drops_running_header_repeated_on_three_pages /
            test_does_not_drop_text_repeated_on_only_two_pages（**阈值边界**）/
            test_long_repeated_text_is_not_a_running_header / test_headings_are_never_treated_as_running_headers
      重复段落：test_drops_duplicate_paragraphs_keeping_first /
            test_exact_duplicates_are_only_removed_for_paragraphs（刻意收窄）/
            test_cleaning_is_idempotent
  [计划外新增] 「纯页码行」删除规则：仅当该块位于**该页首块或末块**且形态是纯页码
      （`12` / `- 12 -` / `12 / 30` / `第12页 共30页` / `Page 3 of 10`）才删。
      证据：TestPageNumberDetection 的 13 条真值表用例 + test_drops_page_number_only_at_page_edges

第 9 条 每块保存 token/字符数、页码、标题、来源、ACL 和租户信息

七、回头看 B4（第 4 步要求「顺带回头看」）
--------------------------------------------------------------------------------
1. [正面确认] B4 的 `insert_chunks` docstring 声称「父 chunk 必须排在子 chunk 之前」
   —— 本批用**真库**证明这条要求确实被数据库强制（复合自引用外键）。
   B4 当时的说法成立，无需修正。
2. [新发现，非缺陷但需登记] `repository.list_chunks` 的排序键是
   `(created_at ASC, chunk_id ASC)`。同一批 flush 写入的 chunk
   `created_at` 很可能同值，此时实际顺序由 **chunk_id（哈希）** 决定 ——
   也就是说**读回顺序 ≠ 写入顺序**。
   写入侧不受影响（父先于子由调用方保证），但 B6 若需要「按文档顺序」重建
   （manifest 的 chunk 顺序、按 ordinal 续切），必须读 `metadata_json["ordinal"]`。
   不修 B4 代码（不属于本批范围），登记到遗留问题。
3. [一致性确认] B4 [D-6]「上传不建版本、版本由流水线创建」与本批无冲突：
   本批完全不碰 `document_versions` 的创建，`Chunk` 只携带调用方给的版本信息。


八、遗留问题（本批不做，登记备查）
--------------------------------------------------------------------------------
1. chunker 目前**没有生产调用点**（B6 的 pipeline 才是第一个调用方）。
   按「每个新模块必须登记生产调用点」的纪律，已把它登记进台账第 4 节的
   「已建未启用」清单 —— 这是有意的分批结果，不是漏接线。

   真正从 `knowledge_bases.chunking_config_json` 读出来、并写进

3. 图片块不进 chunk（无图检索）。若以后要做「图文混合检索」，需要给 image 块

   本批未触碰任何评测脚本。
7. PostgreSQL 复验、真实 Redis 消费端、真实 OCR 引擎属 B6/B8 门禁范围。
