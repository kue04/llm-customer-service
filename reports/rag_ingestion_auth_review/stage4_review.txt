═══ 三、风险与回滚点 ═══

回滚点：
  · **本阶段全部改动尚未提交**（工作区状态），`git checkout --` / `git stash` 可整体回到
    B6 收尾状态（HEAD `a670373185cd074b4ceae0c4008e55135276f341`）。
  · 索引侧有**函数级**回滚：`index_builder.rollback_index()`（只改指针、不重建、不删文件，
    回滚前重新校验旧版本目录）。⚠️ 但它**没有测试、没有 API 出口**（见第四节第 3 条），
    因此"有回滚能力"目前是**未验证**的。

风险项：

  1. **全局索引是单点**。B7 把索引从"每租户分片"改成"全局一份 + 检索期过滤"，
     换来的是 B14 的修复；代价是**任一次重建都影响所有租户**。
     缓解：reproduce 权限收窄到 {supervisor, admin}；构建走临时目录 + 校验后原子切换，
     失败不动旧指针（这条在 B6 已落地，本阶段未放宽）。
  2. **`rebuild_index` 的 `all_tenants` 默认值是 `True`** —— 这是本阶段有意的选择，
     但意味着"将来若要做按租户分片索引"必须先改这里。缓解：生效 scope 落在
     manifest `extra["scope"]`，测试断言 `"all_tenants"`，退回去会立刻红。
  3. **`IndexManifest.verify()` 的租户不变量被放宽**（条目租户 ∈ 声明集合）。
     若 `extra["tenants"]` 被写错（比如漏了一个租户），校验会**发现不了**。
     缓解：`tenants` 由实际条目聚合生成（`sorted({entry.tenant_id ...})`），不是手写常量。
  4. **响应暴露索引元信息**（`index_version` / `built_at` / `chunk_count` / `tokenizer_id`）。
     评估：不含任何文档内容或 chunk 文本，且端点已要求 `retrieval:read` scope；
     `describe_chunk_index()` **只读 manifest、不加载 FAISS 索引**，无性能风险。
     判定：可接受，但登记在案。
  5. **`visible_chunk_count` 会暴露"我能看到多少 chunk"这个量**。
     评估：它是**本租户可见量**（已按 tenant/ACL 过滤后统计），不跨租户；
     且它是"零命中 vs 索引坏了"的唯一现场判据，收益大于风险。判定：保留。
  6. **并发重建的版本号竞态未测**（两个请求同时重建 → 可能都算到同一个 v 号）。
     本机 SQLite 上难以构造；见第四节第 8 条。
