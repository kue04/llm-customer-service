# 5.4 稳定性与成本：实施顺序和验收标准

状态：**实施建议，尚未执行**。先完成当前 5.3 的代码修复与人工复核材料整理；不把质量不足掩盖为吞吐提升。本计划沿用非 Docker 环境，不更换模型、不默认增加依赖。

## 已有基础与真正缺口

- 已有实际 PostgreSQL/Redis/API/worker/本地模型联通、重启和断链 readiness 验收，不无理由重做。
- Redis 客户端已有连接/读超时，线上生成调用有局部 timeout；这些不等于贯穿一次聊天请求的总预算。
- queue.read 当前使用 XREADGROUP 的新消息路径，ACK 失败会记录错误；仍需实际验证失联消费者 pending 消息的回收、有限重试与死信闭环。
- ops_metrics 已有 token、平均延迟和 P95 等统计，5.4 应复用；缺的是可持久追溯到每次调用/重试的成本与容量口径，不能重新搭一套相互矛盾的指标。
- PostgreSQL 业务写事务采用保守租户级锁；须实测锁等待与连接池占用，不能先为猜测瓶颈改锁粒度。
- 既有故障恢复验收不等于从数据库/对象备份恢复，备份策略文档也不等于恢复演练通过。

## 五步推进

### 第一步：固定负载与测量当前容量

冻结机器配置、CPU/内存、模型/线程数、API/worker 数、语料规模、索引版本和超时配置。固定三个真实负载：聊天、文档入库、聊天与入库混合；分别测冷启动和预热后。先串行，再逐级增加并发，达到预先定义的停止条件即停止，避免无界压垮复用环境。

记录每阶段耗时及总耗时、吞吐、P50/P95/P99、成功/失败/拒绝/超时数、数据库锁等待、连接池占用、Redis pending/积压年龄、进程内存。所有统计保留分母；不能只报告成功请求的延迟并隐藏超时。测试使用专属租户、Stream/消费组、对象与索引目录。

**完成判据**：一份能复跑的当前容量报告；明确“哪一级并发开始排队或失败、瓶颈在哪里”。先测再与业务确认并发/延迟目标，不凭本机 CPU 环境承诺线上 QPS。

### 第二步：总 deadline、资源预算与背压

在请求入口建立总预算，向检索、工具和生成传递剩余预算；保留现有局部超时并使其不能超过剩余预算。为模型并发、待处理请求和文档入库设置有界容量；容量满时返回稳定错误与可重试提示，而不是无限排队。区分用户取消、超时、依赖故障与容量拒绝。

取消必须验证后续模型/工具工作是否真正停止或被有界隔离，不能仅让 HTTP 返回而继续无限占用资源。请求结束须释放并发名额；涉及订单等写操作时遵守现有幂等与事务约束，不能盲目重试非幂等调用。

**完成判据**：超时与取消后资源可回收；超额请求可预期地拒绝；已接纳请求不被无界积压拖垮；其他租户仍能服务。所有预算可配置，并有单元及真实故障测试。

### 第三步：worker pending 回收、有限重试与死信

补充失联消费者未确认消息的接管与重放。先定义有效执行租约/心跳与接管条件，避免长任务仍在执行时被错误接管。消息投递至少一次的情况下，继续依赖任务/阶段幂等保证发布效果不会重复。

按错误类型处理：依赖抖动可退避且有限重试；永久格式错误等进入明确终态；超过尝试上限进入可查询的死信记录。尝试次数、下一次重试时间、最后错误码应可持久追溯。死信只保存必要引用和脱敏错误，不复制凭据或全文。重投入口必须验证权限与幂等。

**必须保留 5.2 语义**：requires_review 是等待人工处理的业务终态，正常 ACK；不自动重试、不自动放行，不当成需要无限救活的队列故障。

**完成判据**：执行中杀掉专属 worker、制造 ACK 失败和依赖抖动后，任务不丢、不重复发布、不过度重试；死信可定位、经授权可重投；积压数量和最老等待时间可观测。

### 第四步：统一可观测性与成本记录

复用现有 trace、token 与 ops_metrics，增加请求/任务/模型调用/重试之间的关联。每次模型调用记录 provider、模型、尝试次数、开始结束时间、结果、token 计数来源及价格版本。失败/取消的调用也必须有记录，避免只统计成功调用；落库与汇总避免重复计费。

本地模型记录 token、耗时与资源消耗；未提供计价依据时货币成本标记 unknown/null，不能填 0 假装免费。外部模型价格由已确认的配置维护，不硬编码未经核实的价格。日志、指标和账本均遵守租户访问边界与脱敏。

**完成判据**：单次请求可追到全部调用和重试；重启后记录仍可核对；汇总与明细一致；告警能区分依赖故障、积压和模型瓶颈。

### 第五步：复测容量与真实恢复演练

用第一步相同配置与负载比较前后结果，再在独立恢复环境演练数据库、对象文件及索引 manifest 的一致恢复。记录备份时间点、恢复时长、数据缺口、关键表数量、租户隔离、文档引用与恢复后的可检索性。现有活动索引和共享数据库不得作为破坏性演练对象。

**完成判据**：同负载下无新增正确性/隔离退化；延迟、拒绝率、吞吐和成本有完整结果。恢复后完成真实问答与引用核验，并记录实际 RPO/RTO；业务未确认目标前只报告观测值，不宣称满足 SLA。

## 交付方式与启动条件

每步单独交付代码、直接相关测试和真实证据，再进入依赖它的下一步。最终形成一份容量前后对比、一份故障与重试报告、一份调用/成本核对、一份恢复演练报告；复用现有验收脚本，不以单元测试数量代替真实运行证据。

5.3 的人工标注可以与 5.4 的第一步基线工作并行等待，但“5.4 完成”不能替代“检索质量达标”。如果没有生产目标，先以当前本机配置做测量，不因此停下所有可执行工作，也不擅自扩大成容器化部署。

最先应执行的是 **固定负载与当前容量基线**。不先承诺 QPS，也不先堆积限流、重试和队列机制后才测现状。
