## A. 环境与工具链

### A1. `git commit` 返回成功，但分支指针根本没前进

- **现象**：命令退出码为 0、输出也像成功了，但 `git log` 里找不到这条提交，
  `git status` 显示的状态与提交前一样。
- **根因**：git **不会自动创建嵌套 ref 目录**。当分支名含 `/`（如 `feature/rag`）而
  `refs/heads/feature/` 目录不存在时，写 ref 这一步会失败，但提交对象已经创建了 ——
  于是表现为「提交存在但没人指向它」。
- **解决**：任何 commit 之后**必须复核**：`git rev-parse HEAD` 看指针是否真的动了；
  异常时 `git rev-parse <commit>` 取回提交，并手工修复 ref。
- **面试怎么讲**：这是「退出码 0 ≠ 副作用已生效」的典型例子。
  我说得出为什么"验证副作用"比"看命令输出"重要 —— 在自动化流程里，
  一个静默失败的分支指针会让后续所有工作站在错误基线上。

> **2026-09-23 补记（规范落盘批次第 3 次复现）**：
> `git commit` 打印 `[optimize/interview-ready d2f43a0]`、文件数也对，
> 但 `git rev-parse HEAD` 返回 **`e5d5bc3`**（`packed-refs` 里的旧值）；
> 按本文姿势 `mkdir -p .git/refs/heads/optimize` + 写 40 位完整 SHA 后**立即恢复**。
> 三次复现（B1/B2、B3、本次）说明：**只要分支名含 `/` 就必然发生，不是偶发**。
> 因此「提交后必须 `git rev-parse HEAD` 复核」是硬动作，不是可选项。

> **2026-09-23 补记二（B8 收尾批次：第 4~7 次复现 + 一个此前没注意的面）**：
> 本阶段四次 commit（`f934a26` / `1155af2` / `135d280` / `172a100`）**每次都复现**，
> 每次都按本文姿势手工修 `refs/heads/optimize/interview-ready`。
>
> **新发现：`git push` 成功后，remote-tracking ref 也会是旧值。**
> 推送成功（远端已是 `172a100`，`ls-remote` 实证）之后，
> `git status` 却报 `ahead 17`、`git rev-list --count origin/…HEAD` 也报 17 ——
> 因为 `refs/remotes/origin/optimize/` 这个目录**跟 `refs/heads/optimize/` 一样会被清掉**，
> 于是 git 退回读 `packed-refs` 里的旧值。
> 处置同姿势：`mkdir -p .git/refs/remotes/origin/optimize` 后写入远端真实的 40 位 SHA
> （remote-tracking ref 只是本地缓存，写它不影响远端）。
>
> **教训扩展**：这条坑不只影响 commit，**也影响 push 之后的本地视图**。
> 凡是"本地 ref 到底指向哪"的判断，都要用 **`ls-remote`（远端）** 或
> **`rev-parse`（本地）** 去**实证** ——
> **不能信 `status` 的 ahead / behind 数字**，它们在这台机器上会骗人。
> 这与 A5 / A6 同源：**任何"汇总性指标"都要能追到它的取数方式**。

> **2026-09-23 补记三（第 8 次观察：现象未复现 + 一个残留隐患）**：
> B8 推送批次最后一次 commit（`1c47394`）后复核，**loose ref 与 HEAD 一致**，
> 且分支 reflog（`.git/logs/refs/heads/optimize/interview-ready`）里有 git 自己写的
> 两条 `commit:` 记录（`ed06dbb→f188aa6`、`f188aa6→1c47394`）——
> 这两次 git 都正常更新了分支指针。
>
> **所以上文「只要分支名含 `/` 就必然发生」这个结论要收窄。**
> 现有证据只支持：该现象与 **loose ref 路径是否可用**有关
> （`optimize/` 目录会被 git 的 ref 更新动作清掉，见上文实测结论）。
> 「必然」这个说法会引出两个坏后果：① 每次做一遍无谓的修 ref；
> ② **更危险** —— 既然「反正都要修」，就**跳过检查**，
> 而指针不一致恰恰是**静默**的（退出码 0、输出正常）。
>
> **硬动作是「检查」，不是「修」**：commit 后核对
> `git rev-parse HEAD` == `git rev-parse refs/heads/<branch>`；
> 推送后核对远端 `git ls-remote`；**三者不一致才修**。
>
> **残留隐患（客观事实）**：`.git/packed-refs` 里
> `refs/heads/optimize/interview-ready` 仍是旧值 `e5d5bc32`，
> 只是被 loose ref 覆盖。git 读 ref 时 loose 优先，所以现在无影响；
> 但**一旦 loose ref 文件被清掉（gc / 误删 / 路径不可写），就会静默退回 `e5d5bc3`**
> —— 这正是「指针看起来没动」现象的直接来源。
> 清理方式：`git pack-refs --all`（把 loose ref 合并进 packed-refs，旧值随之消失）。

### A2. 代理与直连都会间歇性抽风，`git push` 只能"探测 + 交替重试"

- **现象**：push 被拒。实测**重试 5 次才成功**（前 4 次直连与代理通道都被拒）。
- **根因**：本地网络环境不稳定，且代理与直连**不是互补关系** —— 两者都可能失败。
  最初记录（B1/B2 期间）以为"直连不行就用代理"，B3 期间的实测推翻了这个结论。
- **解决**：每次先探测可用通道，失败就换另一个交替重试；
  **以远端 SHA 为准**判断是否真的推送成功，不看命令输出。

> **2026-09-23 补记（B8 收尾当日两次推送，粒度更细）**：
> 同一天、同一台机器、相隔几分钟，两次结论就不同 ——
> · 第一次（`624d496..172a100`）：探测时**两条通道都通**，直连**第 1 轮**即成功；
> · 第二次（`172a100..ed06dbb`）：**直连连续两次失败**
>   （`fatal: unable to access …: Empty reply from server`），**代理一次成功**。
>
> **新粒度：失败不只在 `push` 上，只读请求同样会失败。**
> 第二次时连**直连的 `ls-remote` 都失败**了（脚本自动切代理才拿到 SHA）。
> 所以「探测」与「执行」必须走**同一条通道** ——
> 不能拿"刚才 `ls-remote` 直连通"当作"`push` 直连也会通"
> （本次就这么误判了一次：探测直连成功 → 直接 push → 失败）。
>
> 推论：**探测的有效期很短。** 正确姿势是「探测 → 立刻用同一条通道执行 → 失败立即换」，
> 而不是"早上探测过，下午就不用探了"。
- **面试怎么讲**：这体现了「结论要能被新证据推翻」。
  我把一条写进文档的旧结论（坑 2）明确标注为"实测修订"，
  而不是删掉重写 —— 保留推翻过程本身就是工程判断力的一部分。

### A3. 轻量 venv 缺源配置，`pip install` 必须显式指定镜像

- **现象**：装依赖直接失败。
- **根因**：本机 venv 在 B3 期间被破坏过一次，之后按"轻量口径"重建
  （不含 torch / transformers / datasets / trl / peft / sentence-transformers），
  源配置没有连带恢复。
- **解决**：`pip install --trusted-host mirrors.aliyun.com -i https://mirrors.aliyun.com/pypi/simple/`。
  并把「venv 是轻量版」写进交接文档，避免下一个窗口重复踩。
- **面试怎么讲**：环境即代码的一部分。我会把环境的**限制**（缺什么、为什么缺）
  写进交接文档，因为"某次能跑"和"别人能跑"是两件事。

### A4. Bash 与 PowerShell 两个通道能力不互补

- **现象**：同一条命令在一个通道能跑、在另一个通道报错；想用另一个"绕过"时发现它也不支持。
- **根因**：两个 shell 的可用命令集、路径语义、引号转义规则都不同，
  不存在"一个不行换另一个就行"的保证。
- **解决**：按命令能力**选通道**，不做互补假设；跨通道的产物（临时文件）用绝对路径传递。
- **面试怎么讲**：跨平台脚本要显式声明依赖哪个 shell，而不是"应该都能跑"。

### A5. 一轮里反复重跑全量测试，会把「绿」跑成「红」（2026-09-23）

- **现象**：为了取回转义被吞掉的 pytest 汇总行，在**同一轮**里连跑 5 次全量测试。
  第 4 次起出现 `1 failed, 789 passed` —— 失败的是一条**只做读写删**的对象存储用例
  （`LocalObjectStore.delete`）。看堆栈才发现异常是 `SystemExit` 而不是 `AssertionError`：

      object_store.py:234: path.unlink()
      → sitecustomize.py: _safe_path_unlink → _try_trash → _check_bulk_delete_guard
      → raise SystemExit(1)
      {"count":550,"threshold":50,"scope":"turn"}

- **根因**：**环境的批量删除保护是按「轮次」累计计数的**（本机阈值 50 个文件/轮）。
  每次全量 pytest 都会在临时目录创建/删除数百个文件，跑几次就必然越阈值；
  **一旦越阈值，本轮内后续所有删除都被拦下**，于是「唯一要删文件的用例」替所有用例背了锅。
  两个误导性特征让它特别像真 bug：① 失败在**测试末尾**（前面的断言都过了）；
  ② 前几次运行连汇总行都看不到（守卫在 sessionfinish 阶段 `SystemExit`，
  进程在打印汇总行之前退出，退出码 1）—— 很容易被判成"测试挂了"，其实**是绿跑完了**。
- **解决**：**一轮只跑一次全量测试**；需要多次取数时改成
  「一次运行 + 输出重定向到证据文件 + 从文件里读」，而不是反复重跑。
  判断"到底绿没绿"要看**进度输出里有没有 `F`／`E` 字符**，不要只看退出码和汇总行。
  另：`--basetemp=<项目内路径>` 可以让临时文件不落在用户 Temp 目录，
  但**不能**绕过按轮计数的保护 —— 那是环境级约束，不是路径问题。
- **面试怎么讲**：**测试结果的"红"也分真假，先看异常类型再谈原因** ——
  `SystemExit` / `PermissionError` / 断连 属于**环境**信号，`AssertionError` 才是**逻辑**信号。
  更深一层的通用教训：**当测试与被测系统共享同一个"会消耗的全局资源"时
  （删除配额、连接数、临时目录、端口），测试之间就不再独立** ——
  这正好是 D 节反复讲的"测试要可重复、无顺序依赖"的另一个化身。
  工程上还多一条：**不要为了"把日志看全"而反复重跑重任务**，
  一次落盘、多次读取，既省时间也避免自己把环境弄脏。

### A6. 环境删除守卫会把 pytest 的「绿」连同它的证据一起吃掉（2026-09-23）

- **现象**：B7 收尾跑全量，进度条全绿走到 `[100%]`、**一个 `F`/`E` 都没有**，
  然后**没有** `884 passed` 汇总行，退出码 1，末尾多出一行：

      [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":1542,"threshold":50,"scope":"turn",...}

  最危险的读法是「跑到最后挂了 → 一定有测试失败」；实际上**测试全部通过**。
- **根因**：pytest 的 `TempPathFactory.getbasetemp()` 在 session 收尾时会把
  `%TEMP%\pytest-of-kk\pytest-*` 的旧目录**批量搬进 `garbage-<uuid>/` 再整体删除**
  （本机累计 1542 个文件），命中环境的批量删除守卫（阈值 50），
  守卫抛 `SystemExit(1)`，进程在 `pytest_terminal_summary` 打印汇总行**之前**退出。
  也就是说：**守卫不针对你的测试，它针对 pytest 自己的临时目录清理**，
  但被杀的是「打印测试结果」这一步。
- **排查过程（两条死路，记下来省得再走）**：
  ① `--basetemp=<项目内路径>` 无效 —— pytest 对已存在的 basetemp 会**先删再重建**，照样触发守卫；
  ② `PYTEST_DEBUG_TEMPROOT=tmp/...` 直接**卡死**（3 分 48 秒没跑完，86% 处停住），手动终止。
- **解决（B7 起的固定口径）**：
  1. 全量测试改用 `--junitxml=<file>` 取数 —— XML 在**测试执行期**写入，
     不经 sessionfinish，不受守卫影响；`tests / failures / errors` 三个属性即权威计数；
  2. warning 条数用 `pytest --collect-only -q` 的 warnings summary 取
     （只收集不执行，不产生批量删除）；
  3. **判据 = 「输出里有没有 `F`／`E`」＋ JUnit XML**，不看退出码、不看汇总行；
  4. 一轮只跑一次全量（A5 的既有纪律）——守卫按**轮次**累计计数，重跑只会更糟。
- **与 A5 的关系**：同一个环境约束的两次现身，方向相反 ——
  A5 是环境噪声把「绿」**说成**「红」（多出一条 failed）；
  A6 是环境噪声把「绿」的**证据抹掉**（汇总行消失、退出码 1）。
  两次的应对是同一句话：**别拿退出码和汇总行当唯一真相源**。
- **面试怎么讲**：**"测试结果"和"测试结果的呈现"是两个东西，都可能被环境污染。**
  当 CI 或本地跑分出现"退出码非 0 但看不到失败详情"时，第一反应不该是改代码，
  而是找一个**不受呈现层影响**的权威数据源（这里是机器可读的 JUnit XML）。
  更深一层：**测试基础设施自己也依赖文件系统这类共享资源**，
  它和被测系统一样会遇到环境限制 —— 所以"为什么这条命令不可信"的答案，
  往往要到"它收尾时还做了什么"里找。

## B. 契约与职责边界

### B1. 解析器不能碰数据库：用 AST 守卫测试代替 code review

- **现象（设计约束）**：解析器是纯函数（`parse(source: bytes, filename: str)`），
  不接受 `tenant_id`、不写库 —— **签名被测试锁死**，因为多一个参数就会破坏可测试性与可复用性。
- **根因**：租户过滤、事务边界、落库都属于数据访问层，
  一旦解析器开始接收 `tenant_id`，它就从"纯函数"退化成"带环境的半成品"。
- **解决**：把约束写成**可执行断言**，而不是靠评审时人工看：
  - 源码扫描拒绝 `sqlalchemy` / `repository` / `db`；
  - AST 解析断言不出现 `parse_document(...)` 调用（见 D1）；
  - 断言解析器签名不含 `tenant_id` 参数。
- **面试怎么讲**：纪律会腐化，断言不会。把"我们约定不这么做"翻译成"CI 会拦住你"，
  是架构约束真正生效的唯一方式。

### B2.「算 hash」与「标 duplicate」被文档写在一段里，实际必须拆到两层

- **现象（认知陷阱）**：计划原文「每份原文件计算 SHA-256；重复文件标记 duplicate，
  不能创建第二份有效文档版本」把两件事写在同一段，读起来像"同一个任务里做完"。
- **根因**：**计算 hash** 只需文件字节（纯函数层就能做）；
  **判定 duplicate** 需要「同租户下是否已有同 hash 的版本」+ 当前 job 的 document_id + 事务边界，
  这些在纯函数里根本拿不到。
- **解决**：机制在解析层（`ParsedDocument.metadata["content_hash"]`，
  由 `REQUIRED_METADATA_KEYS` 保证必然存在），判定在流水线层
  （`find_version_by_content_hash` 命中则标 `duplicate`、不建新版本）；
  数据库层再用 `uq(tenant_id, content_hash)` 兜底 —— 即使流水线判漏，写入也会被拒。
- **面试怎么讲**：这是我主动识别并写进审查文档的"文档字面与架构现实不一致"。
  我没有照字面硬做，而是拆成两层并说明为什么，还补了数据库层的第二道防线。

### B3. 上传接口建版本会撞唯一约束

- **现象（推演出的必然故障）**：若上传时就创建 `document_version`：
  先传 `a.pdf`（hash `H1`）→ 文档 A、版本 1；再传**内容相同**但文件名不同的 `b.pdf`（hash 同为 `H1`）
  → `source_uri` 不同 → 新建文档 B → 创建版本时**必然撞** `uq(tenant_id, content_hash)`，
  抛 `IntegrityError`。
- **根因**：`document_versions` 上有 `uq(tenant_id, content_hash)`，
  而上传期还不知道 `parser_name` / `parser_version`（要解析后才知道）。
- **解决**：上传只建 `documents`（按需）+ `ingestion_jobs`，**不建版本**；
  版本由流水线在 `parsed` 阶段创建。`ingestion_jobs.document_version_id` 本身就是**可空列**，
  说明"建 job 时版本还不存在"是被 schema 预期的顺序。
- **面试怎么讲**：这是"从唯一约束反推职责边界"。
  我不需要在线上撞一次 `IntegrityError` 才知道，读 schema 就能推出来。

### B4. `source_uri` 与对象存储 key 必须分离

- **现象**：如果把「逻辑标识」和「物理路径」当成一个东西，"重传追加版本"就会坏掉 ——
  同一个文件重传时物理路径变了（含随机 document_id），就再也关联不回原来那条文档。
- **解决**：
  - `documents.source_uri = upload://<净化后的文件名>`：**稳定的逻辑标识**，
    同租户内同名 = 同一份文档（重传即追加版本）；
  - 对象 key = `rag/<tenant_id>/<document_id>/<净化文件名>`：**物理位置**（计划原文要求含租户路径与随机 ID）。
  - 并且 `source_uri` **由服务端派生、不接受客户端传入** —— 否则 KB-A 的成员
    可以传入 KB-B 文档的 URI 给别人的库追加版本，形成越权写入口。
- **面试怎么讲**：「逻辑标识 vs 物理位置」的分离在存储设计里是通用模式
  （数据库主键 vs 文件路径、UUID vs 自增 ID 同理）。这里的加分项是我同时想到了它的**安全含义**。

### B5. `source_uri` 唯一性粒度：用「可逆性」而不是「灵活性」做判据

- **背景**：初版把唯一约束写成 `uq(tenant_id, knowledge_base_id, source_uri)`（三列），
  看起来比两列更灵活（同一文件可分别归属多个知识库）。
- **现象（推演出的必然故障）**：`document_versions` 上有 `uq(tenant_id, content_hash)`，
  即租户内相同内容只允许一份版本。同一文件 F 上传到 KB1 后再上传到 KB2：
  三列约束**放行**新建文档 D2，但 D2 建版本时**必然撞** content_hash 唯一约束。
  结果只有两条坏路 —— 要么 `IntegrityError`，要么按「重复文件标 duplicate」
  生成一个**永远没有内容的僵尸文档**。
- **根因**：两条约束在**不同粒度**上表达同一个事实（"这份内容已经存在"），
  三列的写法让「文档层」可以绕过「版本层」的判定。
- **解决**：改为 `uq(tenant_id, source_uri)`（两列）。
- **决定性判据是「可逆性」而不是「灵活性」**：

  | 方案 | 以后要变更时的代价 |
  | --- | --- |
  | 两列（现选） | 要支持跨库共用，加 `knowledge_base_documents` 关联表 —— **纯增量，不动现有数据** |
  | 三列（原设计） | 要合并重复副本时，chunk / embedding / ACL / 审计已各自分叉，**无法判定该留哪份** |

  附带收益：两列给出**正确语义** —— `source_uri` 唯一标识「这份文件这个逻辑实体」，
  重传同一 URI 应**追加版本**而非新建文档，正好对上 `documents` / `document_versions` 的分层本意。
- **落地纪律**：修订 `0001` 而非追加 `0002`，依据是「`data/rag_metadata.db` 不存在、
  0001 从未落到任何正式库、尚未提交」，并显式写明
  **「若 0001 已被部署，则必须改为追加新迁移」**。
- **面试怎么讲**：两个方案在功能上都"能满足需求"，差别只在**以后要改的时候代价多大**。
  三列方案的"灵活性"是**假的** —— 真正的灵活性体现在**能不能平滑演进**。
  这条还附带一个可讲的细节：我明确标注了"修订 0001 的前提"，把对环境状态的依赖写出来了。

### B6. 解析失败：抛异常，而不是返回结构化错误对象

- **现象（有意偏离计划原文）**：计划 2.1 写的是「失败返回结构化错误，不能吞异常」。
  实现改成**抛 `ParserError`**（结构化、带稳定 `error_code`）。
- **根因**：做成**返回值**会留出「调用方忘记检查」的口子，
  而忘记检查的后果是**把空文档当成功结果送进索引** —— 这是**静默的数据损坏**，
  比一次显式失败严重得多。
- **解决**：
  - `ParserError` 携带 `error_code` / `message` / `parser_name` / `filename` / `detail`，
    可直接落 `ingestion_jobs.error_code` / `error_message`；
  - 未预期异常必须保留 `__cause__`（`raise ParserError(...) from exc`）——
    只包不链等于吞掉 traceback，有测试断言 `excinfo.value.__cause__` 是原始异常；
  - **产物自检前置**：模板返回前跑 `validation_errors()`
    （表格块必须有 `table_json`、图片块必须有 `image_ref`、`order` 必须从 0 连续），违反即抛 `parse_failed`。
- **面试怎么讲**：返回值与异常的区别，本质是**失败模式的可忽略程度**。
  返回值可以被忽略、异常默认中断。当「忽略失败的后果是数据损坏」时，
  必须选**不容易被忽略**的那个。关键在于这是个**权衡判断**而不是教条 ——
  所以我在决策记录里写明了"这是有意偏离计划原文"，并说明理由。

### B7. 解析产物自带身份，不依赖取出它的运行时环境

- **背景**：计划只列出 `ParsedDocument` 的四个字段（`title` / `blocks` / `metadata` / `warnings`），
  实现额外加了三个**自描述字段**：`parser_name` / `parser_version` / `source_type`。
- **根因**：`document_versions` 表需要落 `parser_name` / `parser_version`，
  而流水线在「解析成功」与「写库」之间可能**失败重试、可能换 worker 执行**。
  如果这两个值只挂在**解析器对象**上，重启后就必须靠 registry 再猜一次 ——
  而 **registry 是可被覆盖的**（测试里就换过）。
- **解决**：让**产物自带身份**，一条历史版本记录就能**脱离运行环境**被解释。
- **面试怎么讲**：原则是「**数据应当自描述，而不是依赖取出它的环境**」。
  反过来说：如果一个数据记录必须依赖"当时的代码版本/全局注册表"才能解释，
  那它就不可回溯 —— 而 RAG 系统**必须能回答"这份内容的解析结果是怎么来的"**。

### B8. 上传必须流式累计大小，不能全量读进内存

- **现象（容量风险）**：`await file.read()` 会把整个文件读进内存，
  50 MB 上限 × 并发请求会直接打爆内存。
- **解决**：分块读取、**超限立即中止**；上限做成模块级常量 + 环境变量可覆盖。
  测试覆盖三个边界值：「超一字节即 413」「**恰好等于上限放行**」「上限配置写错报 500」。
- **面试怎么讲**：边界测试最容易漏的是**「恰好等于」**那一档 ——
  超限与未超限两侧都会被测到，唯独等号处最容易被 `>` / `>=` 写反而不被发现。

### B9. OCR 引擎缺失时降级为**警告**，而不是让任务失败

- **现象**：扫描件需要 OCR，但本机默认不装真实引擎（`rapidocr-onnxruntime`）。
  如果这时抛错，用户会**反复重传一个必然失败的文件**。
- **解决**：四级行为分离，并用注入的假引擎全覆盖（测试不需要真装引擎）：

  | 场景 | 行为 |
  | --- | --- |
  | 文本层充足 | **不调用** OCR（对已能取到文字的页面做 OCR 只会引入识别错误） |
  | 文本层低于阈值且引擎可用 | 整页渲染 2 倍 PNG → OCR，`pdf_ocr_used=True`，无警告 |
  | 文本层低于阈值且**引擎不可用** | **不报错**，写 `no_text_layer` 警告（`detail.ocr_engine=None`） |
  | 引擎可用但识别为空 | 同样写 `no_text_layer` 警告 |

- **两个关键细节**：
  1. **文件已经存进对象存储了**，让任务失败只会让用户重传；
     正确做法是**入库成功 + 一条可查询的警告**。
  2. 触发条件是「**低于阈值**」（默认 32 字符）而非「**为空**」——
     只识别出页眉页脚的扫描件文本量很少但**非零**，只判空会**永远不触发**。
- **面试怎么讲**：① 失败要往「**可观测**」而不是「**中断流程**」的方向设计。
  ② 「阈值 vs 判空」是**真实数据形态驱动的细节** —— 扫描件的典型特征正是"有少量文字但不是正文"。

### B10. 超出计划原文的取舍必须标注方向（更严 / 更宽 / 更可测）

- **背景**：B4 完成后回头逐条比对「计划原文」与「实现」，
  发现**三处实现比文档更多/更宽/更严**，但此前只写在决策记录里，
  **没有点明「这是超出文档的加固」**。

  | # | 计划原文 | 实现取舍 | 方向 |
  | --- | --- | --- | --- |
  | 1 | 校验「成员身份」，无成员关系 403（**未区分角色**） | 写操作要求 owner/editor，reviewer/viewer 一律 403 | **更严** |
  | 2 | 「只在嗅探结果明确且与扩展名不一致时拒绝」，**未定义「明确」** | 物化为强特征（必拒）/ 弱特征（html 前缀命中不拒）/ 无魔数（放行）分级 | **更宽**且更可测 |
  | 3 | 用 `get_document_by_source_uri` 复用，**未规定 `source_uri` 来源** | 服务端从净化文件名派生，**忽略客户端传入** | **更严** |

- **为什么标注是必要的**：这些取舍若不写明，**下一位执行者会误以为它们是文档要求**，
  从而在「放宽写权限」「让前端传 `source_uri`」这类改动上以为**无需决策记录**。
- **面试怎么讲**：讲「**实现与规范的偏差管理**」。
  偏差本身不可怕（规范总有模糊处），可怕的是**偏差没有被记录、后来者把偏差当规范**。
  方向标签（更严/更宽/更可测）让对方一眼判断影响面。

### B11. 两条硬约束字面打架：用「不可变上下文对象」同时满足（2026-09-23）

- **现象**：计划里同时写着两条看起来互斥的要求 ——
  ①「切分器**不得接收 `tenant_id`**」（和解析器同一条纪律：不许把归属信息塞进函数参数）；
  ②「每个 chunk **必须带 `tenant_id` / `acl` / 页码 / `heading_path`**」。
  按 ① 的字面执行，② 就没法满足；按 ② 的字面执行，就得给切分器加一个
  `chunk_document(doc, tenant_id, acl, ...)` —— 那 ① 就形同虚设。
- **根因**：约束 ① 想禁止的其实是**「归属信息以裸标量散落在调用链上」**这种形状
  （每加一个字段就要改签名、漏传就退化成空租户），不是「知道归属信息」这件事本身。
  两条要求描述的是**不同的关注点**，被写在了同一段话说，于是显得矛盾。
- **解决**：引入**不可变上下文对象** `ChunkContext`
  （`frozen=True`，构造时校验非空 + 版本号 ≥ 1），把归属信息**整体**传进去，
  函数签名变成 `chunk_document(document, *, context: ChunkContext, config: ChunkConfig)`。
  于是 ① 满足（签名里没有任何裸 `tenant_id` / `acl` 形参），
  ② 也满足（`context.to_metadata()` 一次性带齐 tenant / acl / 来源 / 版本）。
  并补决策记录 `[D-9]`，写明**三个被否决的方案 + 否决理由**：
  裸参数（每加字段就改签名）、读全局/请求上下文（纯函数层不可测、并行不安全）、
  下游补字段（落库时才知道归属，等于把错误推迟到最不可见的地方）。
  **守卫用 AST 而不是字符串匹配**：逐个函数检查形参名，
  于是「换个名字绕过去」和「git 里有但没人调用」两类偷懒都被拦住。
- **面试怎么讲**：**需求里出现「两条要求打架」时，先别急着二选一，
  先问「这两条各自真正想禁止的是什么」。** 90% 的情况是它们在不同抽象层上说事，
  找一个能同时承载两侧关注点的**数据结构**，冲突就消失了 ——
  这比写一条"例外说明"然后留个 TODO 强得多（例外说明会被后来人当默认行为继承）。
  另外配一句加分项：**决策记录要写被否决的方案**，
  否则三个月后没人知道当时为什么不用更简单的那个，很容易被"简化"回去。

### B12. 硬上限与「不许截断」打架：选宽松但要留痕 + 统计可见（2026-09-23）

- **现象**：计划同时要求「代码块**不从内部截断**」和「chunk **不超过 700 tokens**」。
  一段 900 tokens 的代码块，两条只能满足一条。
- **根因**：两条约束的**优先级不同但计划里没排序** ——
  「不截断」是为了保住代码的可执行性（截断后语义直接坏掉），
  「不超上限」是控制 embedding 质量与成本的软目标。硬把代码切开会
  用「坏的输入」去换「好看的数字」。
- **解决**：**代码块整块保留**，允许它超过 `max_tokens`，但做三件事让它**可追溯**：
  ① 在 `ChunkingStats` 里记 `oversize_chunks`（有多少块超限）；
  ② 在 chunk 的 `metadata_json` 上打超额标记；
  ③ 在审查文件里**显式标注方向为「更宽」**（而不是假装没违反）。
  正文段落一侧**仍受硬上限约束**，不放宽。
- **面试怎么讲**：**当两条要求真的互斥时，回答不该是"我选了一条"，
  而该是"我按代价大小排了优先级 + 让违反变得可观测"。**
  "静默放宽"是最差的处理 —— 数字变好看了，但没人知道是什么换来的。
  可复用纪律：**任何「有意允许的例外」都必须能在统计里被数出来**，
  否则它在下一次排查时就是一个幽灵。
  （配套素材：`ChunkingStats` 的 17 个计数字段覆盖了每一处删除/妥协行为，
  回答"这份文档为什么少了一段"。）

### B13. 自引用复合外键下，`session.delete(row)` 循环 ≠ 一条批量 DELETE（2026-09-23）

- **现象**：B6 开工基线 `2 failed, 837 passed`，两条都挂在 `TestIdempotency`，
  且都是「任务**已经 succeeded** 之后再跑一次」。失败阶段固定在 `persisted`：

      sqlalchemy.exc.IntegrityError: FOREIGN KEY constraint failed
      [SQL: DELETE FROM document_chunks WHERE document_chunks.id = ?]
      [parameters: [('39f08807…',), ('440cf62c…',), … 共 6 行]]

  **首次执行全绿**，只有重跑才红 —— 所以正常链路用例一条都没发现它。
- **根因**：`document_chunks` 有一组**指向自己的复合外键**：

      ForeignKeyConstraint(["document_version_id", "parent_chunk_id"],
                           ["document_chunks.document_version_id", "document_chunks.chunk_id"])

  父 chunk 与子 chunk 同属一个版本，**删除时无论先删谁、只要对方还在就构成违规**。
  而 `delete_chunks` 当时写的是 `for row in rows: session.delete(row)` ——
  ORM 把它编译成 `DELETE ... WHERE id = ?` 的 **executemany，每行一条独立语句**。

  关键知识点：**SQLite 对即时（immediate）外键约束的检查发生在「每条语句结束时」**。
  于是"删掉父 chunk"这条语句结束时，子 chunk 仍然指着它 → 报错。
  「一条语句」与「N 条语句」在这里不是性能差异，而是**语义差异**。

  更值得记的是这个缺陷的形状：**函数自己的 docstring 写的正是正确做法**
  （「只要一次全量 delete 即可……逐条删反而会中途撞外键」），
  而代码用的恰是被它否定的做法 —— 注释与实现相反，code review 最容易漏的就是这种
  「读注释觉得没问题」的错。

- **解决**：把删除改成**一条**语句，让整个版本的行在同一个语句内一起消失，
  约束在语句结束时看到的已经是"全部删完"的一致状态：

      statement = (delete(models.DocumentChunk)
                   .where(DocumentChunk.tenant_id == tenant_id,
                          DocumentChunk.document_version_id == document_version_id)
                   .execution_options(synchronize_session="fetch"))
      result = session.execute(statement)

  于是**既不需要**「先删子再删父」的拓扑排序，**也不需要** `ON DELETE CASCADE`
  或 `PRAGMA defer_foreign_keys`。`synchronize_session="fetch"` 用来让 session 里
  已被删掉的 ORM 实例同步失效 —— 紧接着要写入的新行 `chunk_id` 与旧行相同（确定性哈希）、
  只有主键 `id` 不同，留着旧实例会让"到底删干净没有"变得不可信。
  验证：单文件 49 passed → 全量 **839 passed**。

- **面试怎么讲**：三句话。
  ① **"ORM 的 `session.delete()` 循环不等于批量 DELETE"** —— 它退化成 N 条独立语句，
  而这在有外键的方案里是**语义**差别：约束是每条语句结束时检查的（SQLite immediate FK），
  一条语句内整体消失才合法。
  ② **"这类缺陷只在重跑路径上暴露"** —— 首次执行时表里没有旧行，循环体根本没进去，
  代码看起来完好。所以**幂等性必须有专门的重跑用例**，不能指望正常链路顺带覆盖；
  这也解释了为什么它一直藏到基线才红。
  ③ **"注释与实现相反"是最隐蔽的一类错** —— 排查时先别信注释，去读真实 SQL
  （日志里那句 `DELETE ... WHERE id = ?` 就是全部答案）。
  通用纪律：**遇到「删除一批同表互相引用的行」，先问"这是几条语句"**。

### B14. 「按租户分片」还是「全局共用」没拍板，三个子系统各自选了一个（2026-09-23）

- **现象（红/绿双份证据：`B7_index_multitenant_RED.txt` / `_GREEN.txt`）**：
  1. A 租户上传并跑流水线 → 生效索引 `v1`，6 条（全 A 的 chunk）；
  2. B 租户上传并跑流水线 → **生效索引仍是 `v1`、仍是 6 条，但条目全部变成 B 的**；
  3. 此时 A 租户检索 → **0 条命中，且没有任何报错**。
  用户视角是「系统没找到资料」，而证据就在数据库里 —— **静默错误，比崩溃危险**。
- **根因（三处自相矛盾）**：

  | # | 位置 | 症状 |
  | --- | --- | --- |
  | ① | `index_builder.rebuild_index` | 只取**触发构建的那一个租户**的可索引 chunk |
  | ② | `repository.create_index_build` | 版本号按 `(tenant_id, index_name)` 计 → 两个租户**都拿到 v1**，`publish_build_directory` 切换时把另一个租户的 `v1/` 目录 `rmtree` 掉 |
  | ③ | `IndexManifest.verify()` | 要求 `entry.tenant_id == manifest.tenant_id` → 全局索引**永远无法通过校验** |

  三处单看都合理：① 是 B6 之前的检索口径、② 是"每个租户独立编号"、
  ③ 是"manifest 声明的租户要和条目一致"。**放在一起才炸** ——
  因为「索引是每租户一份还是全局一份」这个决定**从头到尾没有被显式拍板过**，
  于是每个子系统在写自己的时候各自选了一个。
  这不是编码错误，是**缺失决策（missing decision）**。
- **解决（4 处代码 + manifest 留痕）**：
  1. `repository.list_indexable_chunks(..., all_tenants=False)` —— `all_tenants=True` 去掉租户过滤；
  2. `repository.create_index_build(...)` —— 版本号查询去掉 `tenant_id` 条件
     （docstring 写明：版本号必须**全局**递增，否则两租户都拿 v1 会互删目录）；
  3. `repository.list_index_builds(..., all_tenants=False)` —— 跨租户降级 superseded 用；
  4. `index_builder.rebuild_index(..., all_tenants=True)` —— 取数用 `all_tenants`；
     manifest `extra` 增加 `"scope"` 与 `"tenants"` **留痕**；
  5. `IndexManifest.verify()` —— 放宽为「条目租户 ∈ **声明集合**」
     （`extra["tenants"]`，缺省退回旧语义 → **B6 老 manifest 仍能通过**，有意的向后兼容）。
  验证：A 入库 `v1`(6 条全 A) → B 入库后 **`v2` 含 12 条（B 6 + A 6）**，
  两租户各只命中自己的 6 条。
  回归守卫：`test_manifest_contains_both_tenants` +
  `test_own_tenant_can_still_retrieve_after_another_tenant_ingests`。
  **`search_chunk_index` 的契约一行未改** —— 修的是根因，不是在调用侧绕过。
- **面试怎么讲**：
  ① **为什么 B6 测试全绿却漏了它？** 因为三处各自都有测试、各自都过，
     唯独**「两个租户先后入库」这条跨子系统的组合场景没有用例** ——
     单模块测试验证不了子系统之间的**契约假设**。这正是 F1「接线」方法论的实证：
     B7 把检索 API 接上去的那一刻，这个缺陷才第一次有了暴露的机会。
  ② **为什么说它是"缺失决策"而不是"bug"？** 因为没有任何一行代码"写错了"——
     是三个模块对同一个未定义问题的答案不同。**架构约束如果只存在于人的脑子里，
     它就不是约束**；修完之后落成的可观测证据是 manifest `extra["scope"]` +
     `extra["tenants"]` + 响应字段 `tenant_count`（退化回分片时它会变成 1，测试立刻红）。
  ③ **「静默零命中」为什么比崩溃危险？** 崩溃会有人看日志；零命中只会有人抱怨
     "搜不到"，而且**没有任何报错可以让告警系统抓**。对策是给响应加
     `visible_chunk_count`，让"零命中"与"索引坏了"可区分 ——
     **把可观测性当作正确性的一部分来设计**。

### B15. 验收规范把「目标」和「现状」写在同一格 → 两边都不能用（2026-09-23）

- **现象**：拿到一份 515 行的企业级验收规范，指标定义和门槛都写得很细。
  想拿它当设计参考、又当验收基准，**两件都做不成**。逐条核对 13 项能力：

  | 规范里写的 | 项目实况 |
  | --- | --- |
  | §1「本次未收到源码，不能断言现有系统缺失某项实现」 | 源码早就在手，阶段 0~4 已落地并逐阶段审查 |
  | §6.2 方法矩阵含 XLSX / 扫描件 OCR / 图表视觉理解 | 只有 5 种格式，**OCR 仅接口** |
  | §7.3 要求三个状态字段 | 实现是**单一 `status` 枚举**，质量门禁整块没有 |
  | §10.5 `M10 Recall@5≥0.85` | 口径失真 + 无 gold 集，**这个数根本给不出** |

  结果分成两类：**3 处事实已过期**（当参考用会引到错结论）、
  **7 处「规范要求」与「项目实况」直接冲突**（当基准用会误报 NEEDS_WORK）。

- **根因**：表层是「规范自称非现有实现审计报告，却被当验收基准用」——**定位与用法不匹配**；
  深层是**表格结构**：门槛表只有「类别 / 起始目标 / 发布判定」三列，**没有一列写现状**。
  于是写的人按"应该做到什么"填，读的人按"我们做到了什么"读 ——
  **同一张表，两个人读出两种意思**。

- **解决**：三步，且**门槛数字一个都不改**（改门槛 = 把尺子锯短，规范当场作废）：
  ① **加「文档关系表」**：把本规范与 goal / 执行计划 / 路线图 / 台账的职责边界一次列清 ——
     列完它就自证「不是审计报告」；
  ② **把「目标」和「现状」拆成两列**：凡涉及现状的表格加「当前状态 + 证据」，
     取值只准 `已实现 / 部分实现 / 未实现`，另设受控标注 `已建未启用 / 未就绪 / 未演练`；
  ③ **执行层规则单开一节**（§17）：取数口径、结论状态机、证据落盘 ——
     它们不是「验收标准」而是「怎么执行验收」，混进正文会让标准与流程互相污染。
  收尾靠脚本做机械校验（`scripts/verify_acceptance_spec.py`，8 项），不靠通读。

- **面试怎么讲**：**让「目标」和「现状」不互相冒充，比把数字定高更难，也更值钱。**
  一条通用判据：**任何一列如果既可能被读成"要求"、又可能被读成"结果"，它就是设计缺陷。**
  这也解释了为什么「做不到就把标准改成做到的」是错的 —— 那是把尺子锯短，
  量出来的数好看，但没有任何决策价值。
  副产品更实在：改完之后这份规范自动变成差距分析文档的「按指标细化版」。

## C. 安全与鉴权

### C1. JWT 的 `sub` 不是 `users.id`：一个不报错的静默失效

- **现象**：测试里"拒绝非法扩展名"的用例期望 415，实际返回 **403** —— 300 行以外的错误码暴露了鉴权错了。
- **根因**：JWT 的 `sub` 是身份提供方的 `external_id`，
  而 `knowledge_base_members.user_id` 与 `documents.created_by` 都是指向 **`users.id`** 的外键。
  直接拿 `sub` 去比对成员关系，**永远匹配不上**。
- **解决**：新增 `_resolve_principal_user_id`，统一经 `get_user_by_external_id` 映射一次。
- **面试怎么讲**：这是最值得讲的一个坑，因为**它的失败方式是静默的** ——
  线上表现是"加了成员也永远没写权限"，不报错、不崩溃、日志也干净。
  是测试里一个**看起来不相关**的断言（415 用例）把它暴露出来的。
  结论：跨系统边界的 ID 映射必须有测试覆盖，因为错得最安静的地方往往最贵。

### C2. 通用脱敏规则会打碎结构化 ID

- **现象**：审计摘要写入后，`knowledge_base_id` / `job_id` 变成不可关联的乱码。
- **根因**：通用「手机号 / 订单号」脱敏规则会把 **32 位 hex 里的连续数字串**当成敏感数据打码。
- **解决**：脱敏范围收窄为**只对自由文本**（`filename` / `user_agent` / `error_message`）；
  结构化 ID 由服务端生成、不含个人信息，**必须保持原样**，否则审计失去可追溯性。
- **面试怎么讲**：这是由**断言不相等**逼出来的（而不是靠人工看日志）。
  脱敏的目标是"去掉个人信息"，不是"把所有像 ID 的东西都抹掉"——
  过度脱敏会静默破坏审计价值，而审计恰恰是出事时唯一能用的东西。

### C3. 跨租户与"不存在"必须不可区分

- **现象**：如果跨租户返回 403、资源不存在返回 404，攻击者就能用状态码差异
  **探测某个资源是否存在**（枚举租户/文档 ID）。
- **解决**：四类资源（知识库 / 文档 / 版本 / 任务）统一返回 **404**，
  且两种情况的响应体**逐字节相同**（各写一条断言）；`tenant_id` 全程只从令牌取，
  查询串里塞同名字段被忽略。
- **面试怎么讲**：多租户系统的存在性泄漏是很常见的疏漏，
  因为"403 更准确"在直觉上是对的。要讲清楚的是：**返回值的语义准确性和信息安全性会冲突，
  安全优先时选择更钝的响应**，并用断言把"逐字节相同"固定下来。

### C4. 内容嗅探的边界：宁可放过，也不错杀

- **现象**：要求"校验 MIME 与文件内容一致"，但 md / txt **没有魔数**，
  HTML 也只能靠 `<!DOCTYPE html` 前缀启发式判断。
- **根因**：硬校验会误杀正常文档 —— Markdown 里内嵌 HTML 是常见写法。
- **解决**：物化为**两级**：
  - 强特征（`%PDF-`、zip 内含 `word/`）：扩展名指向 pdf / docx 时**必须**匹配，否则 415；
  - 弱特征 / 无魔数（html / md / txt）：**一律放行**（"不确定即放行"）。
  另加一条独立验证：B3 的「扩展名优先于 MIME」继续成立
  （`report.pdf` + `Content-Type: text/html` + 真实 PDF 内容 → 正常受理）。
- **面试怎么讲**：准入策略要在「拦得住」和「不误杀」之间选边界。
  我的取舍是：**只在"确定不一致"时拒绝**，因为"正常文档传不上去"比"放过一个伪装文件"
  对用户的伤害更直接。同时用测试把两侧边界都钉住（正例 + 反例）。

### C5. 令牌自报的 `scopes` 必须忽略，否则任何持令牌者都能提权

- **现象（设计风险）**：计划只要求「校验 JWT」，**没有规定 token 里的角色与权限怎么用**。
  如果直接采信 token 里的 `scopes` / `permissions` claim，
  那么任何持有合法令牌的人（或任何签发配置宽松的 OIDC Provider）都能**自报权限提权**。
- **解决**：明确切分两件事 ——
  - token 里的 `roles` claim **被信任**（毕竟是我们自己签发的），
    但服务端只把它当作「**你是谁**」；
  - **权限（scopes）一律由服务端按 roles 推导**；
  - token 里若出现 `scopes` / `permissions` claim，**完全忽略**。
- **收益**：权限变更**不需要重新签发令牌**，也不必信任外部系统的权限声明。
- **固化**：负向测试 `test_token_supplied_scopes_are_ignored`（逻辑层）+
  `test_token_supplied_scopes_cannot_elevate_privileges`（HTTP 层）。
- **面试怎么讲**：一句话版本 —— **令牌证明「你是谁」，服务端决定「你能做什么」**。
  反向做法（信任令牌里的权限）在单体系统里"能用"，
  但一旦接入外部 IdP 就是提权洞，因为它把授权决策**外包给了令牌内容**。

### C6. `ROLE_SCOPES` 由授权表推导，不手工维护

- **现象（必然漂移）**：角色 → scope 的映射，如果既有一张「授权表」
  （`READ_OPERATION_ROLES` / `WRITE_OPERATION_ROLES` / `REVIEW_ACTION_ROLES`），
  又有一份手写的 `ROLE_SCOPES`，两份**必然漂移**。
- **解决**：`ROLE_SCOPES` 由三张授权表的 **inversion 自动生成**，
  并加断言 `test_role_scopes_is_exact_inversion_of_policy_tables` 锁住两者**严格同构**。
  新增接口只需加表项**一处**，权限视图自动同步。
- **面试怎么讲**：这是「**消除重复真源（single source of truth）**」的经典应用。
  关键在最后那半句：**推导还不够，必须加一条断言把推导结果和原表锁在一起** ——
  否则推导逻辑本身可能写错，而错误会以"权限莫名其妙不对"的形式出现，极难定位。

## D. 测试方法论

### D1. AST 守卫测试 > 源码字符串匹配

- **现象**：为了断言"代码里不调用 `parse_document(...)`"，
  最初用源码字符串匹配 `"parse_document("` —— 结果**误伤 docstring**
  （注释里提到这个函数名就报错）。
- **解决**：改用 `ast.parse` + `ast.walk`，分别检查 **import 节点**与 **Call 节点**。
- **面试怎么讲**：静态检查要在**语法树**层面做，而不是文本层面。
  文本匹配的假阳性会让人逐渐忽略这个测试，最后等于没有测试。

### D2. 权限矩阵要用真值表驱动，不能抽样

- **现象**：成员权限测试原本只采样三个点：`editor` 放行、`viewer` 403、无成员 403。
  但角色枚举有**四个**值 —— `owner`（写白名单的另一半）和 `reviewer` 完全没测。
- **后果**：如果实现把写白名单误写成 `{"editor"}`，**测试会全绿**，
  而线上必然出现"库主（owner）传不上自己的文件"。
- **解决**：参数化遍历 `KB_MEMBER_ROLES × KB_WRITE_MEMBER_ROLES` 两张真值表，
  另加纯集合断言守两个方向：白名单必须是合法角色的**真子集**
  （拼错角色名 → 静默变成"永远 403"；等于全集 → 分级失效）。
- **面试怎么讲**：抽样测试的盲区正好落在"新增枚举值"上，
  而枚举扩张是最高频的变更。**用集合/真值表驱动测试，让"新增一个值"自动获得覆盖**，
  这是我这批补的最有价值的一件事。

### D3. 用已废弃的状态码常量会引入新 warning

- **现象**：`HTTP_413_REQUEST_ENTITY_TOO_LARGE` 已被 starlette 标记废弃。
- **解决**：改用 `HTTP_413_CONTENT_TOO_LARGE`，保持 warning 数不增长
  （批次结束时 warning 稳定 5 条，且都不是本批引入的）。
- **面试怎么讲**：warning 基线是要守的。基线从 3 涨到 5 的**原因**必须能说清、
  且不能是自己引入的 —— 否则 warning 会逐渐失去信号价值。

### D4. 契约测试的「语义」和「描述」要分开对待

- **现象（冲突处理）**：契约测试 `test_reupload_same_source_uri_appends_version_not_new_document`
  的 docstring 把「命中就加版本」写成了**上传接口**的行为，
  与 B3「上传不建版本、由流水线建」的结论**直接冲突**。
- **根因**：契约的**语义**（同一 URI 只对应一份文档、版本号在文档内连续递增）**没有问题**，
  只是**描述**把责任分给了错误的一方。
- **解决**：**只改 docstring，断言与语义一字未动**，并明确「上传负责复用文档、流水线负责建版本」。
  这样它同时对上传接口（2.3）与流水线（3.3）成立。
- **为什么不能直接改测试**：契约测试是**上下游之间的接口契约**。
  改它的断言等于改契约，会影响已经在实现的调用方；而这里只是**措辞旧了**。
- **面试怎么讲**：区分「**测试的语义**」和「**测试的描述**」——
  断言 = 语义，docstring / 命名 = 描述。
  改描述是低风险的文档修复，改断言是契约变更。
  把两者混为一谈，就会在"只是措辞旧了"时误改契约，或在"契约真变了"时只改注释。

### D5. 二进制 fixture 要换成可复现的生成脚本

- **现象（测试资产问题）**：计划只要求「新增四个 fixture 文件」。
  但样本一旦提交为**二进制**，就没人知道里面是什么、也**没法重新生成** ——
  而 PDF 的字号、DOCX 的样式名**都是断言依据**。
- **解决**：改为「**内容写死在生成脚本里 + 脚本生成样本**」（`scripts/make_parser_fixtures.py`）。
  好处：样本可复现、断言依据**人可读**、脚本末尾校验体积不超过 1 MB（与 CI 门槛同源）。
  并加测试 `test_text_fixtures_match_the_generator_script` 断言文本样本与脚本常量一致，
  **防止有人手工改样本后被重新生成覆盖、让断言悄悄失效**。
- **面试怎么讲**：「**测试资产的可复现性**」。
  二进制 fixture 是"黑盒证据"，脚本生成的 fixture 是"可读证据"。
  当断言依赖文件**内部结构**（字号 / 样式名）时，这个区别是决定性的。

### D6. `.gitattributes` 锁行尾，避免断言以无关原因失败

- **现象（跨机器失效）**：本机 `core.autocrlf=true`，
  `tests/fixtures/` 里的文本样本在别人机器上会被检出成 **CRLF**，
  届时「与生成脚本**逐字节**一致」的断言会以一个
  **和它想守的东西（内容是否被改过）毫无关系的原因**失败。
- **解决**：新增 `.gitattributes`，把两个**文本**样本的 `eol` 锁成 **LF**
  （二进制样本 docx / pdf 不受影响）。
- **面试怎么讲**：一个断言如果在不同机器上有不同结果，
  那它守的**不是行为，而是环境**。这条最能体现"想过别人怎么跑这套测试"。

### D7. 测试数据被自己实现的清洗规则吃掉：比「断言失败」更危险的「前提不成立」（2026-09-23）

- **现象**：写一条「重叠内容应出现在下一块」的用例，
  造了两段各 20 词的段落（都调同一个 `words(20)` 辅助函数），
  结果 `overlap_skipped == 0`、断言失败。第一反应是**重叠逻辑写错了**。
- **根因**：两段文本**逐字符完全相同**，而本批刚实现的清洗规则里有一条
  「**完全重复的相邻段落只保留一份**」—— 测试数据在进入切分逻辑之前，
  就被**自己刚写的清洗层**删掉了一段。于是用例想测的「两段相邻内容之间的重叠」
  这个**前提本身就不成立了**；断言失败只是这个更深问题的**下游症状**。
- **解决**：把第二段改成不同文本（`words(20, start=100)`），
  并在用例里**显式断言前提**（如 `assert len(bodies(result)) >= 2`）。
  顺带获得一个额外收益：这条用例**反过来证明了清洗规则真的生效** ——
  一个"失败"同时验证了两块逻辑。
- **面试怎么讲**：**测试失败时，第一问不是"哪里写错了"，而是"这个用例的前提还成立吗"。**
  尤其当被测系统本身会**修改/丢弃输入**时（清洗、去重、规范化、限流、缓存），
  「造数据」和「被测逻辑」之间就多了一层会吃掉数据的处理 ——
  这类失败的症状（断言值不对）和病因（前提被改）**隔了两层**，最容易误改实现。
  可复用纪律：**关键用例必须把前提写成断言**，
  否则你无法区分"功能坏了"和"数据没到"。同源素材见 D4（语义与描述分开）。

### D8. 度量口径的字符集错配：给 CJK 文本按空白切词计 token，量出来的是错的（2026-09-23）

- **现象**：验证「默认配置下确实产生了 80 tokens 重叠」这条用例，
  实测重叠量算出 **27**，远小于 80，看起来像重叠功能没生效。
- **根因**：**度量工具和被测量对象说的不是同一种「词」。**
  测试里的 `junction_overlap` 辅助函数用 `text.split()` 按空白切词计数，
  而实测文本是**中文** —— 中文句子之间没有空格，整句被算成 **1 个 token**。
  于是「27」这个数字既不是重叠量、也不是 bug，**它什么都不是**。
  另一层坑：文本用「重复句子」生成时，找"公共接缝"会出现**歧义**
  （公共前缀/后缀可以匹配到多个位置），度量结果甚至不唯一。
- **解决**：把度量口径对齐到**被测系统真正使用的口径** ——
  改成**字符级**找最长公共接缝，再**交给 `HeuristicTokenCounter().count()` 计 token**；
  测试数据改成每句各不相同的 200 句，消除接缝歧义；
  并**给度量工具本身补两条自检用例**（先证明"尺子是准的"，再量东西）。
- **面试怎么讲**：**"数字不对"有两种可能：被测对象错了，或者尺子错了。**
  测量辅助函数是测试代码里**唯一不受断言保护的部分**，却决定了所有断言的基准 ——
  它出错时不会报错，只会给你一个"看起来合理的错数"（27 比 80 小，很像个真 bug）。
  可复用纪律：① 度量的口径**必须与被测系统同源**（同一套 tokenizer / 同一个规范化函数），
  不要另写一套"差不多的"；② **测试基础设施本身也要有测试**；
  ③ 造数据时避开"自重复"，否则任何"最长公共子串/接缝"类度量都会退化成多解。

### D9. 用 `importlib.reload` 验证「导入期失败」会污染同进程内其他测试（2026-09-23）

- **现象**：要验证「配置越界时模块在 import 期就崩（fail fast）」，
  自然写法是设好坏环境变量 → `importlib.reload(config.chunking_config)` → 断言抛错。
  单跑这条用例是过的。
- **根因**：`reload` 会让模块里的**类对象被重新创建** ——
  于是「其他测试手上的 `ChunkConfig`」和「模块内的 `ChunkConfig`」
  变成了**两个不同的类**，`isinstance` / `==` / pytest 收集全部悄悄改变行为。
  这是个**顺序依赖**的坑：它只在"这条用例先跑过"时才发作，
  表现出来是**别的用例时绿时红**，排查成本极高。
- **解决**：改成**子进程**验证 ——
  `subprocess.run([sys.executable, "-c", "import config.chunking_config"], env=坏环境)`，
  断言返回码非 0 且 stderr 含关键字段名。子进程天然隔离，
  而且**比 reload 更接近真实场景**（生产里"起不来"本来就是进程级的事）。
  附带修正：原先还断言了 `error_code` 字符串，实际异常 `__str__` 里并不含它 ——
  只断言 stderr 里**确实会出现**的东西（`ChunkConfigError` / `max_tokens` / 坏值）。
- **面试怎么讲**：**"在同一个进程里模拟进程级行为"是测试里的常见错位。**
  进程启动、全局单例、环境变量、模块级副作用 —— 这类行为在进程内模拟时，
  要么模拟不真（reload 出来的类不是同一个类），要么留下污染。
  遇到这类需求，**优先选真隔离**（子进程 / 独立解释器），成本是一个进程启动时间，
  换到的是"这个断言不会给别的用例埋雷"。
  也是 D 节一贯的主题：**测试要可重复、无顺序依赖**。

### D10. 测不到的分支等于没测：硬切逻辑需要「字符级 tokenizer」才触发得了（2026-09-23）

- **现象**：写了一条「超长段落按 token 硬切时**不能丢字符**」的用例
  （拼接所有 chunk 后应能还原原文），跑起来"过"了。
- **根因**：**它根本没走到硬切分支。** 用例用的是 `mock-word-v1`
  （按空白切词），而造的中文长串**没有空格** → 整串被算成 **1 个 token**，
  永远不可能"超长"，于是硬切逻辑一行都没执行。
  用例是"绿的"，但它验证的是一个**从未被触发的分支** ——
  比失败更有欺骗性，因为它**给出的是虚假的信心**。
- **解决**：改用 `mock-char-v1`（字符级计数）让中文长串真的超长、
  强制触发硬切，并**显式断言分支被走到**
  （`assert len(result.children) >= 5`）—— "走到分支"本身要成为断言的一部分。
- **面试怎么讲**：**"代码覆盖率"和"分支被执行"是两回事，
  而"分支被执行"和"断言真的检查了它"又是两回事。** 这条坑的价值在于它很难发现：
  测试全绿、覆盖率不低、逻辑也没错，只是**没有一次运行真正进入这条路径**。
  可复用纪律：**关键的分支/边界用例，除了断言结果，还要断言"前提成立"** ——
  因为 `assert` 在前提不成立时经常**恒真**（比如空列表上的 `all(...)`、
  从未发生的异常、没进过的循环）。同源素材见 D7、D11。

### D11. 测试红了先别改测试：列表缩进那个案子，错的是实现（2026-09-23）

- **现象**：`test_continuation_lines_stay_with_their_item` 失败 ——
  列表项的续行（原本有缩进）在切分后**丢掉了缩进**。
  直觉反应是"用例造的数据/期望写得太严"，想直接放过。
- **根因**：**是实现的问题，不是测试的问题。** 块级清洗里的 `normalize_text`
  按行 `strip()`，把续行缩进当成"多余空白"去掉了；
  但缩进在列表里**是语义**（嵌套层级），不是排版噪声。
  如果当时按直觉改测试，就会**把真 bug 固化成"期望行为"**。
- **解决**：改**实现** —— 新增
  `INDENT_PRESERVING_BLOCK_TYPES = (BLOCK_CODE, BLOCK_LIST)`，
  对代码块和列表**保留缩进**，其余文本块才做逐行去空白。
  顺带确立一条规则：**清洗规则必须是「按块类型分档」的**，
  不能用一套统一的空白处理打天下。
- **面试怎么讲**：**"测试失败"是一个中性的信号，它只说"两边不一致"，
  没说哪边错。** 改测试让灯变绿是最快的路径，也是**最贵的捷径** ——
  它把缺陷永久化成契约。判断方法：**问"这个断言想守的是什么语义"**，
  如果它守的是真实语义（缩进表达层级），那就是实现错；
  如果它守的是实现细节（某个中间变量），那才该改测试。
  同源素材见 D4（语义 vs 描述）、D7（前提 vs 断言）。

### D12. 拿到一个 failed，先看「异常类型 + 抛出点」再决定动不动代码（2026-09-23）

- **现象**：B6 一批里前后见到两次全量测试变红，**都是 failed，处置却完全相反**：

      B5 收尾：1 failed, 789 passed
        → SystemExit，抛出点 sitecustomize.py（运行环境注入的批量删除守卫）
        → 判定：**环境噪声**，不改任何代码（见 A5）

      B6 开工基线：2 failed, 837 passed
        → IntegrityError，抛出点 sqlalchemy 执行"项目自己写的" DELETE 语句
        → 判定：**真缺陷**，修 `delete_chunks`（见 B13）

- **根因**：项目里已经有一条"环境噪声"的先例（A5），这条先例本身很危险 ——
  **它会变成下一次"看到红就说噪声"的借口**。两次的 failed 数量在同一量级（1 条 vs 2 条），
  失败位置也都在"看起来无关的用例"上，靠"像不像上次"是分不出来的。
  真正能分开它们的是三个可核对的事实，而不是印象：

  | 判据 | 噪声（A5） | 真缺陷（B13） |
  | --- | --- | --- |
  | 异常类型 | `SystemExit`（进程被杀） | `IntegrityError`（业务约束） |
  | 抛出点 | 环境注入的 `sitecustomize.py` | 项目自己的 SQL / ORM |
  | 与本次改动的关联 | 与本批改动无关（纯文档改动） | 落在本批新交付的代码路径上 |
  | 是否可复现 | 换个"轮次"就消失 | **稳定复现**（单文件重跑必红） |

- **解决**：把上面那张表固化成动作 ——
  ① **先看异常类型**：`AssertionError` / 业务异常 = 逻辑信号；`SystemExit` /
  `PermissionError` / 断连 = 环境信号；
  ② **再看抛出点**：在项目代码里 = 真；在运行环境注入的模块里 = 多半是噪声；
  ③ **最后单独复跑那一条**（而不是重跑全量）：能稳定复现的就是真缺陷。
  B6 这条正是靠"单独跑 `TestIdempotency` 稳定红"确认的。
  顺带一条纪律：**"问题现场"的证据文件要留着** ——
  本项目同时保留了 `B6_baseline_test.txt`（红的那次）与 `B6_full_test-output.txt`（修好后），
  只留后者会让"这里红过、为什么红、怎么修的"整段历史消失。

- **面试怎么讲**：**"测试红了"和"测试错了"是两件事，判据要可核对，不能靠印象。**
  要讲清的是：**"环境噪声"这个结论本身是有成本的** —— 每用一次，
  下一次真缺陷被当成噪声放过的概率就上升一点。所以它必须有**客观判据**
  （异常类型 / 抛出点 / 可复现性），并且**写进团队的坑记录里**，
  让它成为"可查的规则"而不是"某个人的经验"。
  延伸素材：A5（噪声的画像）、D11（红的是实现不是测试）、D7（断言失败 vs 前提不成立）——
  四条合起来就是一套"测试信号分级"的方法论。

### D13. 列表项内缩进的代码围栏会被吞成行内代码（2026-09-23）

- **现象**：给 737 行的规范文档写交付前校验脚本，8 项检查里报「代码块数不对」：
  `fences=4 blocks=1`（4 个围栏应等于 2 个代码块，实际只渲染出 1 个）。
  定位到规范 §17.3：那段 bash 示例写在列表项里、缩进 2 空格，
  渲染成一个**行内 `<code>` 元素**（内容以 `bash` 开头），**代码块消失**，
  围栏标识符落进了正文。实测：缩进 **2 空格、4 空格都不行**，
  只有**取消缩进**才能渲染成代码块（代价是打断列表）。
  **同一批还在本文件里查出两处同类旧缺陷**（B11、F2 的旧版）—— 已顺手修掉。

- **根因**：列表项内的 fenced code 要按「列表内容缩进 + 4 空格」解析，
  而 Python-Markdown 在本项目的扩展组合（`extra` + `sane_lists` + `fenced_code`）下
  两种缩进都没被识别，退化成行内代码。
  真正危险的是它**同时骗过两道防线**：
  ① 源文件用编辑器看完全正常（围栏成对、缩进整齐）；
  ② 全文围栏总数是**偶数** —— 只数总数的校验会认为「围栏没问题」。
  **另注（不要混记）**：本文件里还有用**缩进式**代码块（不带围栏）的段落，
  表现也不一致 —— B13 那个渲染成了代码块，D12 那个退化成普通段落（换行保留但无 `<pre>`）。
  两者机制不同（indented code block vs fenced code）；本条只钉死**围栏**这一条，
  缩进式那条结论**不确定**，所以本文件的示例一律改用「围栏 + 取消缩进」。

- **解决**：① 列表项内不放围栏代码块：单行示例改用行内代码，多行示例取消缩进；
  ② 校验脚本增加「**按 h2 章节统计围栏，每段必须偶数**」这一项 ——
     代码块不跨章节，所以每段都该是偶数，**奇数的那一段就是问题所在**；
  ③ 经验回写 `markdown-longdoc-verify` skill（校验清单五项 → 六项）。

- **面试怎么讲**：**「源文件看起来对」和「渲染出来对」是两件事。**
  这类静默故障不报错、不留痕，只能靠程序校验发现。
  更值得讲的衍生结论：**校验项本身要按「故障模式」设计** ——
  只查「围栏总数是偶数」，这个 bug 会完整漏过；改成「按章节查」，它立刻暴露。
  同一个校验目标，**粒度不同，捕获能力差一个数量级**。

### D14. 交付前校验器会假报警：先校准口径，再判定被校验对象（2026-09-23）

- **现象**：同一轮校验里，**两条假报警和一条真报警长得一模一样**：

  - `[codeblocks] fences=4 blocks=1` → **真**：列表内缩进围栏被吞（见 D13）；
  - `[tables] md=21 html=24` → **假**：我的正则不认引用块内的表格（行首是 `>` 再接竖线）；
  - `<div class="codehilite"` 计数漏块 → **假**：无语言 / 未高亮的代码块不计入。

- **根因**：校验脚本是**新写的**（口径从未被验证），被校验的文档是**刚手工改过的**。
  **新写的校验器 + 新改的文档 = 谁也证明不了谁** —— 报警无法直接归因。

- **解决**：① 报警后**先单独验证校验器的口径**：拿「已知答案」探针测它 ——
  手写一个含引用块表格、含无语言围栏的小样例，看它认不认；
  ② 计数改口径：代码块用 `html.count("<pre")`，表格正则改 `^[> \t]*\|`，
     数列数前先排除转义竖线；
  ③ 脚本入库（`scripts/verify_acceptance_spec.py`）并过 `ruff` ——
     顺手清掉 `l` 这类变量名告警，因为**告警堆多了会掩盖真问题**。

- **面试怎么讲**：这条和 D12 是**同一套方法论的另一半**：
  D12 是「拿到 failed 先看异常类型 + 抛出点」，分的是「环境 vs 代码」；
  这条分的是「**校验器的错 vs 被校验对象的错**」。
  通用规则：**任何新写的检查工具，必须先用「已知答案」跑一遍**，
  否则它的输出只是噪声 —— 这也是「评测器自身也要评测」在工具层的同一个道理。

### D15. 证据文件名承诺了内容却没兑现：`*_collectonly_warnings.txt` 里没有 warning（2026-09-23）

- **现象**：核 warning 条数时，去翻 B7 留下的 `B7_collectonly_warnings.txt`，
  想看基线是几条 —— 打开发现文件里**只有测试清单**（末尾是 `880 tests collected`），
  **没有任何 warning 汇总**。而 B7 记的"warning 5 条"确实存在（它来自全量运行的 stdout）。
  实测确认：`pytest --collect-only -q` **不执行测试**，因此不产生 warning summary。

- **根因**：**证据文件名是一次"接口承诺"** —— 名字说里面有 warnings，读的人就不会去别处找。
  更要命的是这条口径被写进了项目笔记（"warning 条数用 `--collect-only` 取"），
  于是它**看起来有据可依**，实际上从没人验证过。
  **「有一个没验证过的口径」比「没有口径」更危险**：后者会去查，前者不会。

- **解决**：① 明确分工并写死：
  `--collect-only` → **取测试数**（880 / 889）与确认收集期无错误；
  **warning 条数 → 取全量运行的 stdout**（`889 passed, 5 warnings, ...`）；
  ② 本批证据文件改用名副其实的名字 **`B8_collectonly_tests.txt`**；
  ③ 同步修正 `MEMORY.md` 第 8 节的口径条目；
  ④ 连带现象：全量 stdout 的汇总行**可能被环境守卫吞掉**（见 A6）——
  那种情况下 **warning 就取不到**，结论里要写「N/A（汇总行被守卫吞）」，
  **不许估算、不许沿用上一次的数字**。

- **面试怎么讲**：**命名是接口的一部分。**
  一个文件 / 函数 / 字段的名字，就是它对使用者的承诺；承诺与内容不符时，
  错误不会立刻暴露，而是在**别人照着名字去用**的那一刻才爆发。
  更值得讲的是那条元教训：**写在文档里的"操作口径"必须有一条实测记录支撑** ——
  否则它会以"权威"的姿态传播，比口头经验更难纠正。
  可延伸：D3（用废弃常量引入新 warning）说明 warning 本身要管，
  这条说明**"数 warning 的方式"也得管**。

### D16. 接线守卫会静默变成空：目标改名后断言照样「全绿」（2026-09-23）

- **现象**：B8 给 B7 的检索接线补 AST 守卫（`tests/test_wiring_guards.py`）时意识到一件事：
  这类守卫的断言都长成 `assert "retrieve_chunk_items" in names`。
  如果**目标本身消失**（函数被改名、文件被挪走、`routers/*.py` 的 glob 返回空），
  "在某集合里找 X"这类断言会失败，但
  **"集合里不该有 X"（`assert not offending`）或 parametrize 到空列表**这两种写法，
  会**必然通过**。也就是说：**守卫可能因为"没东西可守"而变成装饰。**

- **根因**：守卫是对**约束**的断言，而约束的**主体**（文件、函数）在断言里是**隐式**的 ——
  写的人假定它在，读的人也假定它在。只有它消失的时候才暴露，
  而那时测试往往**不是红，而是绿**（空集合 / 空 parametrize 的**假绿**）。
  **假绿比假红危险得多**：假红会被追查到底，假绿会被当成"守卫正在工作"。

- **解决**：三条一起做 ——
  ① **取不到就报错**：`_function_def` 找不到函数时抛 AssertionError（消息写明"守卫已失效"），
     **不返回 None**；
  ② **健全性检查**：显式断言目标文件存在、`len(ROUTER_FILES) >= 10`
     —— 防 parametrize 拿到空列表而整组静默通过；
  ③ **反向验证**：用**临时文件构造违规样例**（`access=None` 的签名、`import jwt`、
     被改名的函数），确认守卫**真的会红**。这条最重要 ——
     它是唯一能证明"守卫不是装饰"的证据。

- **面试怎么讲**：**测试也需要被测试，守卫也需要被守卫。**
  常见的说法是"没有断言的测试没有价值"；这条要更狠一点：
  **「有断言、但断言对象可能不存在」的测试，比没有测试更糟** ——
  它占用了"这里有覆盖"的信用，却不提供任何保护。
  可延伸：D10（测不到的分支等于没测）、D14（校验器本身要先校准口径）——
  三条合起来是一套「**检查者的自检**」方法论。

### D17. 构造「坏输入」要先搞清它会被哪一层拦下（2026-09-23）

- **现象**：写四格式端到端时，要造一份"失败可见、可重试"的坏文件。
  第一版随手写了 `b"PK\x03\x04" + b"\x00" * 512`（zip 魔数 + 垃圾），
  以为"这样 python-docx 就会解析失败" —— 结果上传接口直接返回 **415**：
  「文件内容与扩展名 .docx 不一致（docx 需要对应的文件头特征）」。
  测试在**根本没走到解析阶段**的地方就红了。

- **根因**：**「坏」是可分层级的，而每一层由不同的代码负责。** 这里至少三层：
  ① **准入层**（magic bytes / `content_sniff`）；② **解析层**（python-docx）；
  ③ **流水线层**（错误码与状态落库）。
  `PK\x03\x04` 只说明"像 zip"，而准入还要求能**打开**这个 zip 并看到 `word/` 条目 ——
  **我以为在构造"解析失败"，实际构造的是"准入拒绝"。**

- **解决**：按**目标层**构造输入 —— 要触发**解析失败**，就得先**满足准入**：
  用 `zipfile` 造一个**合法** zip，放入 `[Content_Types].xml` 与
  `word/document.xml`（后者内容为非法 XML）。这样准入看得过去（有 `word/` 条目），
  而 python-docx 一解析就炸 —— 正是我们要的那一层失败。
  **副产品**：那次 415 不算白跑，它是"准入校验确实在工作"的一条正面证据。

- **面试怎么讲**：**测试输入要针对"你要验证的那一层"来构造。**
  随手拿个"看起来坏"的东西当坏输入，测出来的往往是**上一层**的行为 ——
  你以为在测解析容错，实际在测准入策略，而且**红的时候会误导你改错地方**。
  通用做法：先画清楚"这段输入会依次经过哪几层、每层认什么"，再决定在哪一层下手。
  可延伸：B9（OCR 缺失降级为警告，而 embedding 缺失必须失败）正是同一件事的另一面 ——
  **先分清"这是哪一层的失败"，再决定它该被降级还是该被抛出。**

## E. 工程协作

### E1. 对同一文件的多个编辑并行执行会静默丢改动

- **现象**：把两个编辑操作放在同一条消息里并行发出，
  两个都返回"成功"，但**后写的覆盖了先写的** —— 一处改动凭空消失。
  （本次实际发生 5 处，靠事后 `grep` 关键标记才发现。）
- **根因**：读-改-写竞态。两个编辑各自读到同一份旧内容，
  各自修改后写回，最后一次写入丢掉了另一次的修改。
- **解决**：**同一文件的多个编辑必须串行**；不同文件才可并行。
  改完用 `grep` 检查关键标记（如新写入的小节号、数字）确认真的落盘。
- **面试怎么讲**：这是并发写同一个资源时的经典丢失更新问题，
  只不过发生在"我的工具调用"这一层。教训是通用的：
  **并行化的前提是资源不冲突**；以及**改完要验证，不能相信返回状态**（与 A1 同源）。

### E2. 同一工作区存在并行会话 → `git add docs/` 会把别人的中间产物一锅端（2026-09-23）

- **现象**：本批开工时工作区是**干净的**（`git status --porcelain` 0 行）；
  落盘过程中再查，冒出 6 个不属于本次任务的未提交文件 ——
  `docs/FRONTEND_HANDOFF_AND_ALIGNMENT.md`、`docs/FRONTEND_AI_HANDOFF_PROMPT.md`、
  `docs/frontend/`、`scripts/{export_frontend_contract,mint_dev_token,seed_dev_tenant}.py`，
  文件时间戳就在几分钟内；同一份 append-only 的记忆文件里也被追加了两条。
  即：**另一个会话正在同一个仓库里做前端交接的活**。

- **根因**：**文件系统是共享的，但「工作区干净」这个判断只有瞬时意义。**
  按习惯写 `git add docs/ scripts/`，就会把对方**没写完的中间产物**一起提交 ——
  对方可能正在改其中某个文件，提交出去的是半成品，而它自己还不知情。

- **解决**：① **`git add` 一律用精确路径**，提交前 `git status --short` 复核暂存区，
  再确认 `git diff --cached --stat` 的文件数就是预期数；
  ② 改 append-only 文件（台账 / 踩坑 / 记忆）时用**末尾锚点追加**，不覆盖整段 ——
  对方的追加可能就发生在你读与写之间；
  ③ 工作区出现来路不明的新文件时，**先查时间戳与内容**再决定动不动它。

- **面试怎么讲**：这是 E1（同一文件的多次编辑并行丢改动）的**上一层**：
  E1 是「我的两次调用」抢一个文件，这条是「**两个会话 / 两个人**」抢一个工作区。
  教训一致且通用：**共享可变状态下，「看起来没问题」不等于「没有并发」**；
  所以**提交要窄（精确路径）、验证要宽（复核暂存区）**。

### E3. 两套编号体系并存且撞车，引用必须带前缀（2026-09-23）

- **现象**：验收规范用 `I01~I04 / Q01~Q06 / O01` 标阶段、`§7.x` 标小节；
  项目用 `B1~B8` / `阶段 0~7`（`阶段 7.1~7.4` 是发布门禁判据）。
  两套编号在仓库里**零交叉引用**（`grep "I01\|Q01"` 全无），
  而且**规范的 §7.x 与执行计划的「阶段 7.x」编号完全相同、内容完全不同**：

  | 位置 | 规范 §7.x | 执行计划 阶段 7.x |
  | --- | --- | --- |
  | 7.3 | 状态与原子发布 | 安全审查 |
  | 7.4 | 删除、撤权和缓存 | 阶段完成条件（含索引原子切换 / 回滚判据） |

- **根因**：两份文档独立演进，都没觉得自己需要给对方让路。
  后果不是「看不懂」，而是**看懂的人对错了**：写「§7.4 判据未通过」时，
  读者可能去翻规范的 §7.4（删除与撤权），而作者指的是执行计划的阶段 7.4。

- **解决**：① 在规范里加**编号映射表**（规范 ID ↔ 项目批次 / 阶段），
  并写明「引用时必须同时写出两边」；② 把「§7.x 与阶段 7.x 撞车」
  写成**显式陷阱提示**，引用一律带前缀（如「执行计划 阶段 7.4」）；
  ③ 本报告与审查文件内所有引用按此执行。

- **面试怎么讲**：**编号是接口。** 两套编号并存不是问题，**没有对照表才是问题** ——
  这和「两个子系统各自测试全绿、接起来就坏」（B14 / F1）是同一类：
  **各自内部自洽，缺的是那一层显式的映射**。
  可延伸的点：**凡是需要「人肉翻译」的地方，就应该固化成一张表或一个常量**，
  否则错误会在第 N 次引用时才暴露，且极难追溯。

### E4. 交付的命令按 bash 写，但用户在 PowerShell 里执行（2026-09-23）

- **现象**：给出的"可粘贴命令"里含 `timeout 90 git ... push`，
  用户在 PowerShell 里粘贴执行，报：

```
错误: 无效语法。默认选项不允许超过 '1' 次。
键入 "TIMEOUT /?" 以了解用法。
```

- PowerShell 解析到的不是 GNU `timeout`（限时执行），
  而是 **Windows 自带的 `timeout.exe`**（"等待 N 秒"的睡眠命令）—— 语义完全不同。

- **根因**：交付命令时**默认了 bash 方言**，没有确认用户的终端。
  同一段流程里另外两个 bash-only 写法：

  | bash 写法 | 在 PowerShell | 后果 |
  | --- | --- | --- |
  | `timeout 90 git ...` | Windows `timeout.exe` | **语法错**（参数形式不兼容） |
  | `env -u http_proxy cmd` | 无 `env` 命令 | 报错 |
  | `A \|\| B` | 5.1 **不支持**（7+ 才有） | 语法错 |

  最隐蔽的是**同名不同义**：`timeout` 两边都有、`curl` 在 PS 里是
  `Invoke-WebRequest` 的别名、`ls`/`cat` 是别名。
  这类**不会报「找不到命令」**，而是行为诡异或语法错 ——
  比"命令不存在"难查得多。

- **解决**：① 交付命令前**先确认目标 shell**（本机用户默认 **PowerShell**）；
  ② bash-only 的成分在 PowerShell 版里直接去掉或改写 ——

  | 意图 | bash | PowerShell |
  | --- | --- | --- |
  | 限时 | `timeout 90 git push` | 直接 `git push`（git 自身可 Ctrl+C） |
  | 绕开代理 | `env -u http_proxy git ...` | `$env:HTTP_PROXY=''` 后另起一行 |
  | 两者之一 | `A \|\| B` | 分两行，失败再跑第二条 |

  ③ 交付时**标注在哪个终端里跑**，并**只给本次真正要跑的那几条**
  （用户只问推送，就别把提交、保险、校验全塞进一个块里）。

- **面试怎么讲**：这是**「接口假定」**的典型案例 ——
  我交付的是"命令"，却没定义它的**执行环境**，等于给出一个未声明的契约。
  同一个项目里这类错误反复出现（B14 / F1「两段各自全绿、接起来就坏」、
  E3「两套编号各自自洽、引用时对错」）：
  **交付物的边界条件不写清，接收方只能按自己的默认去理解。**
  延伸：**同名不同实比「命令找不到」危险得多** —— 后者立刻暴露，
  前者静静地把事情做错。

## F. 尚未修复的已知缺口（2026-09-23 全仓复核发现）

> 与 A~E 的区别：**A~E 是已解决的坑；F 是尚未修复的问题**，全部由一次系统性复核发现。
> 详细分析与路线图见 `docs/RAG_GAP_ANALYSIS_AND_ROADMAP.md`。
> **保留这一节的意义**：这几个问题的发现过程本身，就是本项目最值得讲的工程反思 ——
> 它们都属于「**测试全绿、但功能/安全并没有真正生效**」这一类静默失效。

### F1. 双轨制：新建的 ingestion 子系统与线上检索链路完全没有接上

- **现象（实测）**：
  - 线上检索读的是 `data/takeout_customer_service_seed.jsonl`（**781 条手工 FAQ**），
    经 `utils/retriever.iter_knowledge_items()` 加载；
  - `utils/vector_retriever.py`（901 行）的 `retrieve_*` 函数签名里
    **连 `tenant` / `acl` 都没有**（`grep -n "tenant\|acl"` **零命中**）；
  - `services/ingestion/repository.py` **只被 `routers/documents.py`（上传）引用**，
    没有任何查询路径消费它；
  - `data/rag_metadata.db` **不存在** → 迁移从未落到开发库。
- **「已建未启用」资产清单**——以下函数都已实现、都被测试覆盖，
  但**生产代码路径上没有任何调用点**：

  | 资产 | 定义位置 | 生产调用点 | 测试调用点 |
  | --- | --- | --- | --- |
  | `create_document_version()` | `repository.py:279` | 无 | 有 |
  | `find_version_by_content_hash()` | `repository.py:314` | 无 | 有 |
  | `grant_document_acl()` | `repository.py:370` | 无 | 有 |
  | `insert_chunks()` | `repository.py:506` | 无 | **无** |
  | `index_builds.manifest_uri` | `models.py:430` | 无读写 | 有 |
  | `queue.publish()` | `queue.py` | **有** | 有 |
  | `queue` 消费端（`xreadgroup`） | — | **未实现** | — |

- **后果**：用户上传的文档进了对象存储和数据库，**永远进不了 FAISS，检索不到**。
  已建的租户 / ACL / 版本 / chunk 数据全部是「已建模、未启用」状态。
- **归属**：B5（chunker）+ B6（pipeline / worker / manifest）就是为它准备的。
- **面试怎么讲**：见下方「Q1」。这是回答「你遇到的最大困难」的最佳素材。

### F2. 检索评测口径失真：intent 命中率冒充 retrieval recall

- **现象（实测）**：`scripts/evaluate_retrieval_metrics.py:85` 的判定函数是：

```python
def is_relevant(candidate, expected_intents):
    intent = candidate.get("source", {}).get("intent", "")
    return intent in expected_intents
```

- 也就是说，「相关」的判定 = **召回条目的 `intent` 字段是否等于标注的 `expected_intent`**。
- **后果**：
  1. 报出的 **recall@1 = 0.9667** 是「**意图分类命中率**」，
     不是「检索到正确文档 / Chunk 的比例」。语料 781 条、意图只有**个位数个枚举值**，
     **只要召回任意一条同意图 FAQ 就算命中** —— 门槛比真正的 retrieval 低一个量级。
  2. 用例集 `data/chat_grounding_cases.jsonl` 与语料由同一批人按**同一套意图体系**手工构造，
     存在**构造性重叠（近似 train/test leakage）**。
  3. 因此「Recall@5 = 98.89%」**不能用来证明检索质量**，而 `README.md` 已引用它。
- **修正方向**：金标从「意图」升级为「**文档 ID + Chunk ID**」；
  引入**真实长文档**评测集；intent 命中率保留为辅助指标（`Intent Hit Rate`）
  但与 recall **分开命名、分开统计**；补充负样本集以计算**拒答准确率**。
- **面试怎么讲**：见下方「Q3」。**主动指出自己评测口径的缺陷，比报一个漂亮数字可信得多。**

### F3. 隔离测试守的是数据层，检索层裸奔

- **现象（实测）**：`tests/test_tenant_isolation.py` 有 14 条用例、**全部通过**，
  但逐条看都是在测**数据层 CRUD**（`test_cannot_read_other_tenants_document`、
  `test_document_list_only_returns_own_tenant`、`test_body_tenant_id_does_not_widen_scope` …）。
- **后果**：**测试全绿，但检索层没有任何 tenant / ACL 过滤**。
  它守的是 B4 上传 / 查询接口，而真正会把 A 租户文档喂给 B 租户的那条路径
  （`retrieve_rag_items`）**没有被覆盖**。
- **修正方向**：新增 `tests/test_retrieval_isolation.py` ——
  负向验证「被过滤文档的标题、分数、数量、引用和 trace 均不泄漏」。
- **面试怎么讲**：**「绿灯」不等于「安全」**。
  测试覆盖的是**你写的地方**，不是你**漏的地方**。
  这条对 F1/F3 是同一个教训的两个面，也是我把"接线"提升为最高优先级的直接原因。
- **修复于 B7（2026-09-23）**：新增 `tests/test_retrieval_isolation.py`（**23** 条，6 个测试类，
  覆盖规程最低要求 5 条 + **正向对照** 3 条 + 预过滤判决 2 条），
  并在 `tests/test_tenant_isolation.py` 增加 `TestAclOnRealRoutes`（**7** 条，
  走真实 `documents` / `knowledge` / `retrieval` 三路由）；
  `tests/test_retrieval_api.py` 新增 `TestChunkRetrievalApi`（**9** 条，API 出口层）。
  隔离测试**数据层与检索层各写一套**，且新增了「B 入库后 A 仍能检索到自己的 chunk」的
  **正向对照** —— 只写负向断言会退化成"空结果也算通过"。原记录保留，不改写。

### F4. README 与实测脱节

- **现象（实测）**：
  - README 第 6 行 badge 写的是 `tests-332 passed`，**实际是 555**；
  - 第 1 节快速验证也写「实测：332 passed」；

### F 节的方法论小结（最值得讲的一条）

F1~F3 是**同一类失效**：**代码全部写对了，测试全部通过了，但功能/安全并没有真正生效。**
它们的共同原因是「**验证了组件，没有验证组件之间的连接**」。

由此得出的可复用纪律（建议纳入后续每批的门禁）：

1. **每个新模块必须登记「生产调用点」**——
   定义在、测试在，但没人调用 = 未完成；
2. **权限隔离测试必须分层**：数据层与检索层各写一套，不允许用前者代替后者；
3. **指标命名必须精确**——`intent_hit_rate` 不能叫 `recall`，
   否则数字会被自己（和读者）误解为它不代表的含义。

### 六个「长答」骨架（推荐背这几条）

**Q1「你这个项目遇到的最大困难是什么？」**
> 不要答具体 bug，答**方法论层面的困难**：最大的困难是**判断"什么时候该停下来把地基补好"**。
> 项目一开始是「一份手工 FAQ + FAISS 向量检索」，能跑、评测数字也好看。
> 按企业级目标改造做到第 4 批时我发现：**新建的解析器 / 数据模型 / 租户 ACL / 上传接口，
> 和线上真正在跑的检索链路是完全断开的** —— 线上检索读的还是手工 FAQ，
> 检索函数签名里连 `tenant_id` 都没有。更麻烦的是，隔离测试 14 条全绿，
> 但测的是数据层 CRUD，**检索层没有任何权限过滤**。
> 于是我决定把「让两条链路接上」提升为最高优先级，而不是继续加新功能 ——
> 因为这个缺口卡住了所有下游能力。
> 这件事让我意识到：**"绿灯"不等于"安全"，测试覆盖的是你写的地方，不是你漏的地方。**

**Q2「你怎么保证代码质量和纪律？」**
六条，每条配一个已有证据：① 能用测试固化的纪律就不写在文档里（`B1` / `D1`）；
② 枚举类权限用真值表驱动不抽样（`D2`）；③ 权限测试**正负成对**
（踩过"只有负向用例导致 C1 完整穿过测试"）；④ **基线零失败**纪律
（每批记录起点测试数，任何失败不得归因历史遗留）；
⑤ **warning 数量作为门禁指标**（稳定 5 条，新增立刻发现，`D3`）；
⑥ 每个取舍写决策记录，含**被否决的方案 + 可逆性对比**（`B5`）。

**Q3「你这个 RAG 系统的检索是怎么做的？」**（诚实答法）
> 现在的实现是 **FAISS 向量召回 + CrossEncoder 精排 + 规则式加权**
> （`calculate_keyword_bonus` 关键词加权、`calculate_direction_penalty` 方向惩罚）。
> 它是"混合"的**简化形态**，**没有真正的 BM25 稀疏检索**，也没有 RRF 融合。
> 我知道正确做法是 dense + sparse 双路召回 + RRF，但我把它排在**权限过滤之后** ——
> 因为先有权限再谈召回质量：如果检索结果会跨租户泄漏，召回率再高也没有意义。
> 另外我复核时发现**现在的评测口径有问题**：报出的 recall@1 是按"意图是否命中"算的，
> 不是按"文档/Chunk 是否命中"算的，语料和用例还是同一套意图体系手工构造的。
> 所以这个数字**不能当作检索能力的证据**，我把它列为 P0 修正项。

**Q4「多轮对话怎么做的？」**
> 有**结构化会话状态**（不只是历史拼接）：`conversation_store` 存 `facts`（已确认事实）、
> `summary`（会话摘要）、`user_memory`（长期记忆），并有 `redis_context_cache` 缓存意图与风险态。
> 但**没有 query rewrite，也没有多跳分解** —— 现在是 `build_query_with_intent_hint`
> 在 query 后追加意图提示，属于**规则拼接而非改写**。
> 计划里的 query rewrite 我**有意排在后面**：没有 chunk 级检索和证据定位，
> 改写了也定位不到证据，改了等于没改。

**Q5「生产级要考虑什么？」**
> 按失败处理分层答，**明确区分已做到与未做到**：
> **已做到** —— 上传期拒绝（415/413/401/403 各有明确错误码）、解析失败抛结构化错误（`B6`）、
> OCR 引擎缺失降级为**可查询的警告**（`B9`）、审计脱敏按语义分档（`C2`）、
> fail-closed 鉴权（缺密钥返回 500 而非静默放行）。
> **未做到**（诚实说）—— 索引原子切换与回滚、超时/取消/重试、

> 其中最想讲的一条取舍：**高风险流式回复不能先把未经验证的 token 发出去再事后检查，
> 因为已发送的 token 无法撤回** ——
> 正确策略是先流式发**状态事件**，正文按句/按声明**缓冲**，核验通过后再放。

**Q6「如果重来一次，你会怎么改？」**

### B16. 前端以为 `routing` 是链路开关，其实它只是个展示字段（2026-09-23）

**现象**

前端交接提示词（`docs/BACKEND_TRACE_FIX_PROMPT_2026-09-23.md` §B7）要求「低置信度给出
独立的 routing 值 `clarify`，**让链路可以做澄清而不是硬猜**」。按这个描述听起来是要改
链路行为，于是先去查 `routing` 在后端被谁消费 —— 结果**一个分支都没有**：

```
services/chat_service.py:638   build_decision_trace 里透传给前端
services/chat_service.py:925   risk_precheck 的 output_summary
```

也就是说 `routing` 从头到尾只是「把 intent_service 的判定结果搬运到响应里」，
链路该怎么走（`retrieve_rag_items` → `build_prompt_context_items` → 安全校验 → 生成）
**没有任何一处读它**。加了 `clarify` 之后，界面上会多一个可辨识的信号，
但真实链路还是照常检索、照常生成。

**根因**

跨端交接时，「字段的**语义**」和「字段的**消费方**」被当成一回事了。
前端看到 `routing` 这个名字自然理解成「路由 = 决定走哪条路」，而后端这边它是
**判定结果的输出**，不是**分支的输入** —— 两者的因果关系是反的。
这类落差单看任何一端的代码都发现不了，只有「照着提示词去改、发现无处可接」时才暴露。

**解决**

1. 改之前先 grep 全仓确认消费点（本次是 0 个分支）；
2. 按「只补信号、不改链路」实现 B7 —— 落在提示词的范围内
   （提示词 §6.5 写死了本次范围只有 `full_trace` metadata 和意图识别逻辑）；
3. **在交付说明里显式声明这条落差**：B7 目前只能做到「暴露低置信度信号」，
   做不到「真的改走澄清」；要让链路真的澄清，需要新增分支代码 + 前后端契约再对齐一轮。

**面试怎么讲**

「跨端联调时我先查了字段的消费点而不是直接改。前端说『让链路可以澄清』，
我一 grep 发现 `routing` 在后端零分支消费 —— 它是判定结果的**输出**，不是分支的**输入**。
所以我把这次改动定位成『补信号』而不是『改链路』，并把这个落差写进交付说明。
这类『名字暗示了它做不到的事』的接口，是前后端最容易互相误解的地方：
修的办法不是猜，是先查消费点。」

### C7. 验收脚本里硬编码 admin 令牌 = 把密钥永久写进 git 历史（2026-09-23）

**现象**

前端给的验收脚本模板（`BACKEND_TRACE_FIX_PROMPT_2026-09-23.md` §5.2）里有一行：

```python
TOKEN = "<粘贴 mint_dev_token 的输出>"
```

照着做就是：签一个 admin 令牌 → 粘进 `scripts/verify_trace_fix.py` → 提交。
而 `git add` 之后这把令牌就**永久留在仓库历史里**（本项目 §5 明确由用户提交，
且历史会被推送到远端），JWT 撤销不了，只能改密钥。

**根因**

「临时验证脚本」和「要提交的文件」被当成两类东西了。联调期为了省事把令牌写进脚本，
是最常见的把临时凭据固化成永久资产的路径 —— 尤其本项目阶段 1 起**所有受保护接口只认
Bearer JWT**，一个 admin 令牌 = 全接口通行。

**解决**

`scripts/verify_trace_fix.py` 里令牌走环境变量，缺了直接 `exit 2` 报错：

```python
BASE  = os.environ.get("TRACE_FIX_BASE", "http://127.0.0.1:8001")
TOKEN = os.environ.get("TRACE_FIX_TOKEN", "")
...
if not TOKEN:
    print("缺少 TRACE_FIX_TOKEN：先跑 scripts/mint_dev_token.py 签令牌并 export", file=sys.stderr)
    return 2
```

**不给默认值、不退化成「跳过鉴权」** —— 后者会让脚本在没人注意时静默变成
「不鉴权也能跑」，门禁就废了。BASE 可以有默认值（不是秘密），TOKEN 不可以。

**面试怎么讲**

「联调脚本要落盘提交时，凭据一律走环境变量，而且缺失就报错、不给默认值。
我特意没有做成『取不到就跳过鉴权』——那种写法最危险：脚本看着全绿，
其实是在无鉴权状态下跑的，门禁等于没有。这条和『不许用默认值掩盖字段缺失』是同一个原则：
**缺了就报，别假装它有**。」

### E5. 跨端提示词的「期望代码」不能照抄：两处隐含前提它没写（2026-09-23）

**现象**

按提示词 §B5 的期望代码实现上下文继承，代码能跑、用例能过，但有两个隐含缺口：

1. **上一轮走兜底时会继承「通用客服咨询」** ——
   `facts.last_primary_intent` 由 `_facts_from_turn` 无条件写入，取值可能是兜底意图名。
   照抄实现 ⇒ 「上一句没识别出来」被继承成「这一句也是通用客服咨询」，
   还带 `inherited_from_context=True`，**把「没识别出来」伪装成「继承成功」**；
2. **脏 facts 里的未知意图名会直接进结果** —— 历史数据 / 规则表改动后，
   `last_primary_intent` 可能是个已经不存在的意图名，照抄实现会原样透传。

**根因**

提示词给的是**主干逻辑**，隐含前提是「`last_primary_intent` 一定是真实规则意图」。
写提示词的人心里有这个前提，但没写下来；照抄的人不知道，缺口就进代码了。
这和「照抄 Stack Overflow 的答案」是同一类问题 —— 抄的是代码片段，没抄到前提。

**解决**

把前提变成**显式守卫**（`_inherited_intent`）：

```python
last_intent = str(facts.get("last_primary_intent") or "")
if last_intent not in KNOWN_INTENT_NAMES:   # 兜底意图 / 脏数据都不在规则表里
    return ""
if not _looks_like_coreference(query):      # 本句得有指代词
    return ""
return last_intent
```

`KNOWN_INTENT_NAMES` 由 `INTENT_RULES` 推导（**不是手写清单** —— 手写会漏，
规则表加了新意图时不会自动跟上）。两条守卫都配了测试：
`test_inheritance_rejected_when_last_intent_was_fallback` /
`test_inheritance_rejects_unknown_intent_name_from_stale_facts`。

**面试怎么讲**

「外部给的实现方案我只当主干用，前提一律自己补守卫。这次的隐含前提是
『上文主意图一定是真实规则意图』—— 但上一轮走兜底时它恰恰就是兜底意图名，
照抄会把『没识别出来』伪装成『继承成功』。我改成从规则表推导白名单来卡，
顺带也挡住了历史数据里的脏值。**从规则表推导、不手写清单**，
是因为手写清单会漏，规则表改了也不会自动跟上。」

### D18. 同一轮测试的「测试数」有两个口径，本机相差 4（2026-09-23）

**现象**

同一轮全量跑完，两个来源给出的测试数**不一致**：

```
stdout 汇总行：923 passed, 5 warnings, 4 subtests passed in 42.76s
JUnit XML    ：tests=927 failures=0 errors=0 skipped=0
```

差 4，而且两个数都是「对」的。改完之后我以为是基线记错了（基线 918，
新增 9 条，918+9=927 才对得上 XML），差点去翻历史提交查「是不是少了 4 条测试」。

**根因**

`N passed` **不含 subtests**，`4 subtests passed` 是单列的一项；
而 JUnit XML 的 `tests=` 把 subtest 也算成独立的 testcase。
所以「两套口径差多少」= **该项目里 subtest 的数量**，是个定值，不是随机误差。

**解决**

1. 门禁一律以 **JUnit XML 的 `tests` / `failures` / `errors` / `skipped`** 为准（踩坑 A6 已定）；
2. 但**对数字有疑问时，不要靠算**，直接把新旧两个 XML 的 testcase 名字做集合 diff ——
   本次就是这么确认的：`added=9 removed=0`，多出来的 9 条正是新增用例名，
   **零删除、零失败**，改动才是可交付的；单看 "923 vs 918 差 5" 永远对不上账。

**面试怎么讲**

「改完测试我先对数字，发现 stdout 说 923、XML 说 927，差 4。
我没去猜，直接把新旧两个 JUnit XML 的用例名做成集合 diff ——
结果是 added=9、removed=0，正好等于我新增的 9 条，零删除零失败。
差的那 4 个是 subtest：`N passed` 不统计 subtest，XML 统计。
**结论是门禁只认 XML 的数字，而且对不上账时要做集合 diff，不要做减法。**」

### A7. pip 升级/覆盖安装会被环境的删除守卫直接杀掉，包停在半装状态（2026-09-23）

- **现象**：`pip install transformers==5.6.1 sentence-transformers==5.4.1` 跑到
  `Installing collected packages` 阶段抛 `SystemExit(1)`，栈底是：

      File "...\shim\sitecustomize.py", line 851, in _check_bulk_delete_guard
      File "...\shim\sitecustomize.py", line 826, in _exit_bulk_guard_control
      raise SystemExit(1)

  最坑的是它**不是失败，是中断**：`torch` 已经装上了，`transformers` / `sentence-transformers`
  没装上，`huggingface_hub` 被降到半新半旧 —— 于是 `import sentence_transformers` 报的错
  看起来完全不像"没装完"。
- **根因**：pip 覆盖安装已存在的包时会先 `os.unlink` 旧文件；本机的安全守卫把
  **单个进程内成批删除文件**判定为危险操作并直接 `SystemExit`。
  也就是说：`pip install X` 这种"看起来只读变更一个包"的操作，内部是**几千次删除**。
- **解决（本机装包的标准姿势）**：
  1. 用 `--target <独立目录>` 装到**空目录**，一次删除都不会发生；
  2. 配 `--no-deps` 避免把 torch 这种 2GB 的大包再下一份到该目录；
  3. 在 `site-packages` 里写一个 `.pth` 文件把该目录插到 `sys.path[0]`
     （`.pth` 里以 `import ` 开头的行会被执行，可以 `sys.path.insert(0, ...)`）——
     **只新增一个文件**，同样不触发删除；
  4. 缺失的依赖（如 `pyyaml`）逐个补装到同一个 target 目录。
- **面试怎么讲**：**"失败"和"被中断"是两种完全不同的故障形态，排查动作也不同。**
  失败会告诉你哪里不对；中断只会留下一个"看起来装了一半"的环境，
  后面所有报错都指向错误的方向（本例指向了版本冲突，真凶是安装被杀）。
  判断方法很简单：**对着依赖清单逐个 import，看谁在、谁不在** ——
  本例就是这一步发现了 torch 在、transformers 不在，才反过来定位到守卫。
  更深一层：**沙箱/安全策略会改变工具的内部行为**，
  不能假设 `pip install` 在任何环境里都是"下载+写文件"。

### A8. 降级装包会留下新旧混血的文件：`huggingface_hub` 1.32.0 → 0.36.2（2026-09-23）

- **现象**：`pip install transformers==4.46.3 sentence-transformers==3.3.1` 报装成功，
  但 `import` 时报：

      ImportError: cannot import name 'as_extended_path' from 'huggingface_hub.utils._paths'

  查 `huggingface_hub/__init__.py` 的 `__version__` 却是 `1.32.0`，
  而 pip 明明说 `Successfully installed huggingface-hub-0.36.2`。版本号自相矛盾。
- **根因**：venv 里原本是 `huggingface_hub` **1.32.0**；装 4.46.3 触发**降级**到 0.36.2。
  pip 用 0.36.2 的文件覆盖了大部分同名文件，**但 1.32.0 独有的 `_local_folder.py`
  因为删除被守卫拦截而留在原地**（见 A7）。于是 1.x 的 `_local_folder.py`
  去 import 0.x 的 `_paths.py` 里并不存在的 `as_extended_path` —— 两个版本的文件混在一个包里。
- **解决**：
  1. **以 `requirements.txt` 锁定的版本为准**，不要凭"这个版本我熟"自己挑版本
     （本例正确版本是 `transformers==5.6.1` / `sentence-transformers==5.4.1`，
     它们本来就配 hub 1.32.0，压根不需要降级）；
  2. 真的要换大版本时，先确认旧包的**独占文件**能被清掉，否则宁可换目录（A7 的做法）。
- **面试怎么讲**：**Python 包不是原子的，一个包是几千个文件，降级等于"覆盖+删除"两步，
  只完成第一步就是混血。** 这类故障的特征是"报错的符号在源码里搜不到" ——
  遇到这种事第一反应应该是**查包内文件的版本一致性**（`__init__.py` 的 `__version__`
  vs `pip` 说的版本），而不是去研究那个符号本身。
  管理上的结论：**依赖版本应该从锁文件读，不应该从记忆里读。**

### A9. 依赖上界是闭区间，而那个版本在 PyPI 上不存在（2026-09-23）

- **现象**：装完 transformers 5.6.1 后 import 报：

      ImportError: tokenizers>=0.22.0,<=0.23.0 is required ... but found tokenizers==0.23.2

  照着提示装 `tokenizers==0.23.0`，pip 回 `No matching distribution found`；

- **根因**：transformers 把自己的依赖上界写成闭区间 `<=0.23.0`，而 0.23.0 的稳定版

- **面试怎么讲**：**"装最新版"不是依赖管理策略。** 正确做法是"装满足约束区间里最合适的版本"，

  把这条和 A8 放一起讲更有力：**依赖问题的两个常见来源是"版本选错"和"版本选得太新"**，

### A10. 模型加载默认走网络，代理一崩服务就起不来（2026-09-23）

- **现象**：`build_embedding('...')` 抛 `httpx.ProxyError: 502 Bad Gateway` ——

### A11. 源站间歇性断连：单次请求从不失败，批量请求必现（2026-09-23）

- **现象**：抓 `policy.mofcom.gov.cn` 的法规正文，单条 `urllib` 请求稳定 200；
  一旦在脚本里连着抓 17 条，**全部**报：

      URLError: <urlopen error [SSL: UNEXPECTED_EOF_WHILE_READING]
      EOF occurred in violation of protocol (_ssl.c:1010)>

  第一次遇到时误判成"站点封了我们"，实际上换个时间单条再试又是好的。
- **根因**：对端在连续请求下会中途掐断 TLS 连接；**单次请求永远复现不了**，
  所以"我手工试过是好的"这种验证方式在这里是**无效证据**。
- **解决（两件事都要做）**：
  1. `fetch_text` 加**退避重试**（3 次，间隔 1.5s × n）—— 实测从 0/17 提到大多数成功；
  2. 更重要的是**正文落盘缓存**（`tmp/law_cache/<id>.txt`）：
     把"抓取"和"解析/生成"解耦，重跑生成器不再联网，
     既不反复骚扰源站，也让失败可以**增量补齐**而不是整批重来。
- **面试怎么讲**：**爬虫类的代码必须做成"可重入"的。** 判断标准是：
  跑到第 15 条挂了，重跑能不能只补第 15 条？如果答案是"会从头再来一遍"，
  那这个设计在真实语料规模（几百上千份）下不可用。
  拆成 fetch（带缓存）与 build（纯本地）两步，就是这个标准的落地方式。

### B17. 父子块双进索引：同一段内容会被命中 2~3 次（2026-09-23）

- **现象**：灌完 209 份文档后检索「消费者七天无理由退货的规定」，
  Top3 的分数**完全一样**（0.8061）、文本开头也完全一样，
  只是 chunk_id 不同：`p_9727a76c...`、`c_28bb6b3c...`、`p_d4f85aea...`。
  不知道设计的人会以为"切分器切重复了，有 bug"。
- **根因**：这是**刻意的设计**（`services/ingestion/chunkers/models.py:33`）：
  chunk 分 `parent`（承载一组的完整上下文）与 `child`（真正被检索 / embedding 的单位），
  small-to-big 检索先用 child 精确匹配、再用 parent 回捞上下文。
  当前索引**把 parent 和 child 都写进去了**，所以同一个语义单元会有多条命中。
- **解决 / 现状**：
  - 现状**不是 bug**，但**检索层需要按 parent 去重或回捞**，否则 Top-K 会被
    同一段内容的多个副本占满，实际读到的上下文反而变少；
  - 这也直接影响评测口径：recall@K 里如果 K 个位置被 2~3 个副本占掉，
    指标会被人为压低 —— 所以**金标必须落到 doc_id + chunk_id，且去重口径要先定死**。
- **面试怎么讲**：**"看起来重复"要先问是不是设计，再问是不是 bug。**
  判据是看数据模型里有没有显式区分这两个东西（本例 `chunk_type` 字段 + `parent_chunk_id`）。
  更值得讲的是后半段：**分层检索（small-to-big）会改变评估口径** ——
  索引里存什么、检索返回什么、评估怎么算，这三件事必须对齐，
  否则会出现"系统其实更好了，指标却变低了"的假象。

### B18. 空引用块让整份文档解析失败：契约该在源头满足，不是让文档陪葬（2026-09-24）

- **现象**：抓 MDN 中文文档做成语料样本后，两份文件解析**直接抛错**：

      ParserError: [parse_failed] 解析产物不满足契约：第 13 个 block（quote）没有文本

  定位到源文件里有一行**光秃秃的 `>`**（原文是 note/提示块，经 trafilatura 抽取后只剩标记）。
  也就是说：**一份 1.1 万字的文档，因为一个空块整份被拒。**
- **根因**：`markdown.py` 的引用块分支无条件产出 block：

      text, index = self._consume_blockquote(lines, index)
      blocks.append(Block(type=BLOCK_QUOTE, text=text, ...))   # text 可能是 ""

  而 `ParsedDocument` 的契约校验（`base.py:320`）要求 heading/paragraph/list/code/quote
  **必须有文本**。契约本身没错 —— 问题是**空块应该在源头被丢掉，而不是产出后被判死**。
  同一个 `_scan` 里，paragraph 分支是有 `if text:` 判空的（第 264 行），
  **quote 分支漏了**，两处风格不一致就是缺陷的来源。
- **解决（源头修，不在校验层放水）**：

      text, index = self._consume_blockquote(lines, index)
      if text:
          blocks.append(Block(type=BLOCK_QUOTE, text=text, ...))
          stats["quote"] += 1
      else:
          stats["dropped_empty"] = stats.get("dropped_empty", 0) + 1

  **为什么不在 `base.py` 的校验里统一过滤空块**：那样契约就名存实亡了 ——
  "block 必须有文本"这条约束的价值就在于**逼解析器在源头把半成品处理掉**。
  在校验层放水，等于把"解析器偷懒"变成"框架兜底"，下次还会有人产出别的空块。
- **面试怎么讲**：**契约校验发现问题时，先问"该谁负责满足它"，再决定改哪一层。**
  这里的判断是「空引用块是解析器的输入噪声，不是文档缺陷」——
  所以责任在解析器，修复点在源头。反过来，如果空块意味着"原文结构没解析对"，
  那才是文档级问题、该报错。
  更深一层：**同一个函数里两种块的处理风格不一致，就是缺陷的温床** ——
  paragraph 判空了、quote 没有，review 时很难看出来，只有真实语料能把它撞出来。

### D19. 单测绿不等于「真实语料验证过」：用覆盖率审计把这句话变成可执行的检查（2026-09-24）

- **现象**：209 份真实语料入库后，解析器的**五个分支从来没被走到过**：

      table  2.9%（6/209）· code 0% · image 0%
      无文本层/OCR 0% · 非 UTF-8 编码回退 0%
      标题层级最深只到 h2（h3/h4 从未出现）

  但全量测试 **927 条全绿**，解析器的每个分支都有自己的单测。
  换句话说：**"单测覆盖了"和"在真实文档上验证过"是两件事**，
  而当时我们差点把前者当成后者写进交付结论。
- **根因**：单测用的是**手工构造的最小样例**（fixtures），
  它们只证明"代码路径能跑通"，不证明"真实文档的形态会走到这条路径"。
  真实文档的脏、杂、长，是 fixtures 天然覆盖不到的。
- **解决（做成了可复跑的检查）**：写 `tmp/audit_corpus_coverage.py`，
  遍历语料 manifest → 用生产解析器解析 → 统计
  「**有多少个文件至少含一个该类 block**」而不是「block 总数」。
  用"文件数"而不是"块数"，是因为前者才反映**覆盖面**（一份文档里有 100 个表格
  也是只覆盖 1 份文档）。有了这个数，缺口就变成了可跟踪的指标。
- **面试怎么讲**：**覆盖率有两种，别混：**"代码覆盖率"看行有没有被执行，
  "输入覆盖率"看真实世界的形态有没有被见到。RAG 这类靠解析器吃饭的系统，
  后者才是质量瓶颈。做法是把后者**做成可复跑的脚本 + 数字**，
  而不是靠"我觉得应该覆盖到了" —— 这个脚本第一次跑就撞出了 B18 那个真 bug，
  这就是投入的回报。

### D20. 用自然语言措辞当测试锚点：一条「守卫」改了三次才抓到漂移（2026-09-24）

- **现象**：给 README 加一致性守卫，判断逻辑写成
  `if "仍走演示路径" in README: 认为 README 声明了演示路径`。
  做变异测试时删掉 README 的整个 F1 提示块，守卫**仍然报 PASS**。查了才发现
  「演示路径」这个词在 README 里出现 **6 处**（§0 正文、§3.1 标题、表格、§8 局限……），
  删掉那一处还有五处替补。改到第三版才抓到。
- **根因**：**探针太宽。**"文档里有没有这句话"和"文档有没有做出这个声明"是两件事 ——
  前者能被文档中任何一处同义/同词句满足，包括**根本不在讨论这件事的句子**。
  这正是 D1（grep 不算数）的翻版，只是这次 grep 的对象从**代码**换成了**文档**：
  以为在做"文档与代码一致性校验"，实际做的是"文档里有没有出现某个词"。
- **解决**：换成**机器可读锚点** —— README 里写一行 HTML 注释
  `<!-- f1-track: chat-service-retrieval=seed-faq -->`，测试只读这一行取值，
  再和 `chat_service.py` 里符号的真实存在情况比对。HTML 注释不渲染，
  不干扰读者，且改切轨时只需改一个词。同时要求锚点**必须存在**（读到空也算失败），
  避免出现"锚点丢了但守卫觉得一切正常"的假绿。
- **面试怎么讲**：**写文档守卫时，先问一句"这个探针会不会被其他句子满足"。**
  判据很实用：**变异测试要能一次抓住。** 如果第一次变异没抓到，
  那不是变异的姿势不对，是探针选错了（我这次第一反应是"改变异 script"，
  其实该改的是探针）。更一般的结论：
  **凡是"读文档找关键词"的校验，都应该换成"读一个明确定义的机器可读标记"** ——
  成本是多写一行注释，收益是校验真的成立。

### E7. 派生样本体积失控：一个「形态样本」做到 50MB（2026-09-24）

- **现象**：为了触发 OCR 分支，把一份法规 PDF 渲染成图片型 PDF。
  `page.get_pixmap(dpi=150)` 后直接 `insert_image(rect, pixmap=pix)`，
  产出 **52,235,882 字节 —— 52MB**，比全部其他 22 个样本加起来大 100 倍。
- **根因**：`insert_image` 传 `pixmap=` 时按**未压缩位图**存，
  一页 A4 @150dpi ≈ 17MB，三页就 50MB。而这份文件的目的**只是触发一次
  `no_text_layer` 判定** —— 一页就够，整本 8 页纯属惯性。
- **解决**：三件事一起做 ——
  1. **只取前 3 页**：形态样本够用就行，不需要整本；
  2. **走 JPEG**：`pix.tobytes("jpeg", jpg_quality=72)` 再 `insert_image(stream=...)`；
  3. `save(deflate=True, garbage=4)`。
  结果 **52MB → 608KB**（缩小 85 倍）。
- **面试怎么讲**：**"样本/测试数据"也要过体积这一关。**
  判据很简单：**这份文件的体积和它的目的是否成比例？**
  "触发一次 OCR 判定"这个目的，对应的合理体积是几百 KB，不是 50MB。
  更一般的教训是：在做"造数据"这类辅助工作时，人会不自觉地沿用
  "越完整越好"的惯性（整本 PDF、全量数据），但辅助产物的评价标准是
  **够用且轻量**，不是完整。

### C8. 前端凭据被编译进静态产物：`.env` 护住了仓库，护不住「部署产物」（2026-09-24）

- **现象**：在前端仓库已构建的 `dist/assets/index-CUMKmt9Z.js`（2026-09-24 16:13 产物）里
  直接 grep 到两样东西：

  ```js
  const B0="http://127.0.0.1:8001".replace(/\/$/,""),$s="eyJhbGciOiJIUzI1NiIs...".trim()
  ```

  `$s` 解码出来是
  `{"sub":"dev_user","tenant_id":"tenant-dev","roles":["admin"],"iat":1790236748,"exp":1790265548}`
  —— **admin 角色、寿命 8 小时**。两个后果：

  1. **地址是编译期字面量**：`127.0.0.1` 永远指"打开页面的那台机器"。部署上线后，
     每个访客的浏览器都在请求**他自己电脑**的 8001 端口，服务器上的后端从头到尾没人访问到；
     若页面是 HTTPS，请求 `http://` 还会被浏览器按混合内容直接拦掉。
  2. **凭据随产物公开发布**：`dist/*.js` 是静态文件，一上线就是人人可 `curl` 的东西，
     grep 一下就拿到一个 admin 令牌 —— 能上传/删除文档、重建索引、跨租户读数据。

  反直觉的地方在于：`client.ts:19` 原注释写的是「只从环境变量读，**绝不硬编码进仓库**」，
  而**仓库确实干净** —— `.gitignore` 里有 `.env.*` 和 `dist/`，两样都没入库。

- **根因**：**Vite 把所有 `VITE_` 前缀变量在构建期内联成字符串字面量。**
  它不是"运行时读环境变量"，是"编译期文本替换"。
  于是 `.gitignore` 只挡住了「仓库」这一个暴露面，而 `.env.local` 的值在 `vite build` 时
  被搬进 `dist`，`dist` 才是真正面对公网的那一份。
  **防线的位置错了：防的是 git，实际要防的是产物。**

  更一般的判断是 —— **「放进 .env 就安全」这条经验只对服务端成立**。
  服务端的 `.env` 运行时读取、不出机器；前端的"环境变量"是**编译期常量**。
  名字一样，威胁模型相反。这正是本条容易漏的原因：开发者沿用了服务端的直觉。

  叠加第二个错误：即便忽略暴露面，这个机制本身也不能上线 ——
  令牌 8 小时到期后**全体用户 401**，而"修复"方式是重新构建、重新部署前端。

- **解决**（本次做了第 1 步，第 2 步未做）：

  1. **地址改同源**：`client.ts` 的默认值从 `http://127.0.0.1:8000` 改成 `""`
     （空 ⇒ 拼出相对路径 `/chat/prompt`，由反向代理把 `/` 转发到后端）；
     本地开发仍由 `.env.local` 显式指定；**新增 `.env.production` 把两项都置空**
     —— 关键在 Vite 的模式优先级（`.env.[mode]` > `.env.local`），
     否则生产构建会静默回落到 `.env.local` 里的本机地址；
     `.gitignore` 加 `!.env.production` 例外：它不含秘密，而且**必须进仓库**，
     不然 CI / 服务器上构建同样会回落。
  2. **凭据改运行时**（未做）：前端不允许持有长期凭据 → 运行时登录换取令牌，
     `VITE_DEV_TOKEN` 这个机制整体删除。

  **判据（可复跑）**：

  ```bash

  grep -c "127\.0\.0\.1\|eyJhbGciOiJIUzI1NiIs" dist/assets/*.js   # 期望 0
  ```

  实测（2026-09-24）：

  | 构建模式 | 产物中的 API base | 产物中的凭据 |
  | --- | --- | --- |
  | `npm run build`（production） | `""` → 同源 | `""` 无 ✅ |

  唯一残留：`status.ts:230` 的**开发排查文案**「前端必须用 http://localhost:5173 访问」
  被带进产物（1 次 `localhost`）。它是提示文本、不是请求目标，无害，
  但生产环境显示这句话是错的 —— 待清理。

  **代价要主动说清**：生产构建出来的前端现在**没有令牌，所有受保护接口都会 401**。
  这是**故意的** —— 缺凭据就该报错，不能拿一个开发令牌顶上
  （同 C7 的原则：不给默认值、不退化成「跳过鉴权」）。

- **面试怎么讲**：「我把凭据放进 `.env`、`.gitignore` 也配了，以为就安全了。
  后来在**构建产物**里 grep 到自己的 admin 令牌，才意识到 Vite 的 `VITE_` 前缀
  意味着这个值会被编译进 bundle。我的暴露面不是『代码仓库』，是『每一个下载 JS 的访客』
  —— 仓库有 `.gitignore` 护着，产物什么都没有。」
  「更一般的判断是：**『放进 .env 就安全』只对服务端成立。**
  服务端的 `.env` 是运行时读取、不出机器；前端的『环境变量』是编译期常量，
  语义完全不同 —— 名字一样，威胁模型相反。我沿用服务端的直觉，所以漏了。」
  「修复分两层：地址改同源相对路径（配置问题），凭据改成运行时登录换取（设计问题）。
  另外我**保留了**『生产构建无令牌 ⇒ 401』这个看起来坏掉的结果，

### E9. 「半提交」：只挑自己改的文件，把仓库提交成编译不过的状态（2026-09-25）

**现象**

前端仓库 `D:\llm\front` 推进「部署准备」时，我给的是一批**只含 4 个文件**的精确提交指令
（理由是工作区躺着一堆并行会话的改动，不想混进来）。执行、推送都成功。
下一批准备挂 CI，我先做了一次「提交后状态能否构建」的模拟
（`git archive HEAD` 导出纯净 HEAD 到临时目录跑 build），结果是
**`tsc -b` 报 33 个 TS2353 错误**：

```
src/api/knowledge.ts(44,5): error TS2353: Object literal may only specify known
properties, and 'headers' does not exist in type 'ApiRequestOptions<unknown>'.
```

**HEAD 编译不过，而工作区编得过** —— 所以问题纯粹由「挑了部分文件提交」造成。

**根因**

把「提交」当成了「挑出属于我的那几个文件」，而正确判据是
**「这批改动落地后，仓库整体是否仍可构建」**。

具体到这次：`src/api/client.ts` 的 `ApiRequestOptions<TBody>` 契约在重构中被**收窄**
（不再接受 `options.headers`），调用方 `src/api/*.ts` 相应删掉了 `headers:` 传参。
「定义方改契约」与「调用方跟着改」是**一个原子改动**，但我只提交了定义方，
11 个调用方文件留在工作区。于是造出一个**两边各自自洽、拼起来不自洽**的状态：

| | `ApiRequestOptions` 含 `headers`？ | 调用方传 `headers:`？ | 能否编译 |
| --- | --- | --- | --- |
| 工作区（未提交） | 否（新版） | 否（新版） | ✅ |
| HEAD（已提交） | 否（新版，已提交） | **是（旧版，未提交）** | ❌ 33 errors |

关键点：**`npm run build` 在工作区永远是绿的** —— 它只看工作区文件。
「提交后的状态」是另一个状态，本地没有任何人跑过它。这类问题在单人本地开发里能潜伏很久，
只在别人 `git clone` 或 CI 首次运行时才第一次亮相。

另有一个诱因：TS2353 的中文语义是「对象字面量只能指定已知属性」，**长得像「多写了个字段」的小问题**，
很容易当成噪声跳过；实际它在说「你提交的定义方和调用方版本不一致」。

**解决**

判据固化成一条命令：**提交前，把 HEAD 导出到临时目录构建一次**。

```bash
cd D:/llm/front
mkdir -p .ci-sim-head && git archive HEAD | tar -x -C .ci-sim-head
cd .ci-sim-head && npm run build            # 必须绿，才叫「已提交状态可构建」
npm run build 2>&1 | grep -c "error TS"     # 判据取这里，别取管道退出码
```

三个操作要点，都是踩过的：

- **放在项目子目录**里导出，Node 的模块解析会自动向上找到真实 `node_modules` ——
  不用建 junction、不用重装，也就没有「清理时跟删真实依赖」的风险；
- 验证完**立刻删掉**，别留工作区（它会出现在 `git status` 里，有被误提交的风险）；
- **别信管道尾部的退出码**：`build` 脚本是 `tsc -b && vite build`，接了 `| tail` 之后
  `$?` 是 `tail` 的退出码。我这次就被骗了一下 —— 显示 `SIM_BUILD_EXIT=0`，实际 tsc 已失败。

修复动作：把「定义方 + 调用方」并入同一次提交。若确实要分批，正确拆法是**兼容序列**：
① 先给定义方加新字段（旧调用方不受影响）→ ② 提交调用方 → ③ 再删旧字段。
**每一步单独提交都必须是绿的。**

**面试怎么讲**

「版本控制里最小的可交付单位不是『文件』，是**能让 CI 变绿的最小文件集合**。」
我原先按『哪些文件是我改的』来挑提交内容，正确标准是『这批改动去掉之后，仓库还能不能编译』
—— 编译看的是**整个可达集合的一致性**，不是单个文件对不对。
「这类问题叫『半提交』：定义方和调用方各自都对，拼起来是错的。它在本地永远不暴露，
因为工作区的 `npm run build` 只看工作区。我是在挂 CI 之前先手动模拟了一次『干净检出』才发现的
—— 也正因如此，我坚持**先把 CI 挂上再继续开发**：没有 CI 的话这个问题要到别人 clone 时才炸，
而那时已经没人记得是哪次提交引入的。」
「还有个细节能讲：`npm run build | tail` 让我一度以为构建成功了，因为管道的退出码是 `tail` 的。
判据必须取自真正被检查的东西（这里是 tsc 的错误计数），不能取自被管道截断的退出码 ——
这跟『别拿空结果当通过』是同一类错误。」

### D21. 守卫的判据会随架构一起失效：从「单路」改成「可切换双路」之后（2026-09-25）

- **现象**：`TestReadmeTrackConsistency` 原来靠「`chat_service.py` 的 AST 里
  有没有调用 `retrieve_rag_items`」判断聊天走哪条轨道。F1 切轨改成开关制之后，
  这条判据**永远返回 `seed-faq`** —— 因为 `seed` 分支仍然调用那个函数，它还躺在文件里。
  守卫自身一行没改，区分度却已经归零。
- **根因**：判据盯着的是**实现细节**（某个符号在不在调用图里），
  而架构从「单路」变成「可切换双路」后，被盯的符号在**两条路上都存在**。
  这不是守卫写错了，是它**测的东西变了而它自己不知道**。
  危险程度高于 D20：D20 的探针是「太宽」（能被别的句子满足），
  D21 的探针是**在任何路径下都给同一个答案** —— 后者更像「稳定通过」。
- **解决**：判据从「符号在不在」换成「**默认值是什么**」——
  读 `services/chat_service.py` 里 `DEFAULT_CHAT_RETRIEVAL_PATH` 的字符串字面量，
  `"chunk"` → `chunk-index`、`"seed"` → `seed-faq`，**读不到即判失败**。
  再加一条自测 `test_guard_can_actually_read_the_default_path`：直接喂源码样本，
  验证两种取值都读得出、改名或改成非字面量时返回空串（而不是悄悄沿用旧值）。
- **面试怎么讲**：「**改架构时要顺手问一句：哪些守卫的判据依赖了旧架构。**」
  切轨这类改动最阴的地方是：它**不删任何符号**，所以不触发任何「符号消失」类告警，
  却让所有「看符号在不在」的检查集体失去区分度。
  判据很实用：**好的判据在被测对象处于两种状态时必须给出不同结果**；
  改完架构后两种状态报同一个值，它就是失效的探针 ——
  **失效的探针比没有探针更坏，因为它提供的是假的确定性。**

### D22. 改默认配置会静默打破 mock 型测试：切轨一次撞出两种形态（2026-09-25）

- **现象**：F1 把聊天检索的**默认轨道**从 seed 切成 chunk，全量测试红了 4 条：
  1. 3 条降级用例（`tests/test_chat_service_degrade.py`）失败 —— 它们 mock 了
     `retrieve_rag_items`，而默认轨道一变，那个 mock **根本不会被调用**，
     `degraded` / `retrieved_documents` 断言随之失败；
  2. 1 条冒烟用例（`tests/test_release_smoke_flow.py`）报
     `TypeError: get_answer_from_rag() takes 1 positional argument but 2 were given` ——
     路由改成把 `auth` 一起传下去，而该用例**伪造整个 `services.chat_service` 模块**，
     替身的签名不会自动跟着真身变。
- **根因**：测试对「实现路径」的假设是**隐式**的 ——
  mock 一个函数等于断言「它会被调用」；伪造一个模块等于**抄了一份签名契约的副本**；
  断言某个字段名等于绑定某个数据源的形状。
  改默认配置 / 改签名不动这些假设的**字面表述**，所以既不过类型检查也不报语法错，
  只在运行时以「跑了但测的不是原来那件事」或 `TypeError` 的形式炸出来。
- **解决**：① 给锁定降级语义的用例**显式锚定轨道**
  （`setUp` 里设 `RAG_CHAT_RETRIEVAL_PATH=seed`，并注释说明「本类测的是降级，与轨道无关」）；
  ② 替身签名与真实签名对齐；③ 新写的 `tests/test_chat_retrieval_track.py`
  把「默认值就是 chunk」本身变成断言，让默认值有测试盯着。
- **面试怎么讲**：「**切轨这类改动必须跑全量，不能只跑新写的测试。**」
  新测试只能证明「新路径能跑通」，证明不了「老路径的测试有没有被悄悄架空」。
  值得展开的是第 1 种的**两种失败模式**：红是显性的（这次确实是红），
  更怕的是**它变成绿的空壳** —— mock 被绕开后若断言恰好也满足，
  用例会继续绿着，却已经不再测任何东西。
  防御办法是本项目的一条既有纪律：**mock 型测试要显式声明它依赖的前置条件**
  （这里是轨道开关），而不是默默继承「当前默认值」。

### B19. 查询侧自己拼索引目录，漏了中间一层：索引建成功却加载不了（2026-09-25）

- **现象**：B 轨混合检索的索引重建**完全成功** —— 打出
  `生效版本 v4 · 9229 个 chunk`、`稀疏路：已构建`；紧接着同一脚本里调用检索层复核，
  报 `sparse_index_unavailable: manifest 声明了稀疏索引但文件不存在：
  data/faiss_store/document_chunks/v4/sparse.sqlite`。
  构建侧说文件写好了，查询侧说找不到。
- **根因**：真实布局是 `{root}/chunk_index/{index_name}/v{n}/`
  （由 `index_manifest.version_dir()` 定义），而我在 `load_sparse_index` 里
  手写成 `root / index_name / "v{n}" / filename` —— **漏掉了 `chunk_index/` 这一层**。
  构建侧用 `version_dir()` 所以天然正确，只有查询侧拼错了。
  关键在于：**这条路径拼接没触发任何类型/静态检查**，也不会在构建时报错，
  只会在"有人真的去加载"时失败。
- **解决**：不拼路径，**从指针推导** —— `load_active_manifest` 已经返回稠密索引文件的
  绝对路径，稀疏索引就在它的同级目录（`Path(index_file).parent / 文件名`）。
  并在 `scripts/rebuild_chunk_index.py` 里**加了构建后的检索层复核**：
  构建成功之后立刻调 `describe_sparse_index`，不可加载就非零退出 ——
  这道复核正是抓出这个 bug 的东西。
- **面试怎么讲**：两句话。①「**布局知识只应存在一处**，复制到第二个地方就一定会漂」——
  正确做法是让第二个使用方去**推导**（从指针/已有返回值算），而不是**复述**（照抄路径结构）。
  ② 更值得讲的是**为什么这个 bug 差点溜过去**：如果只看"构建成功"的日志，
  一切正常；是「构建后立刻用消费者视角复核一次」把它逼出来的。
  这类"生产者成功、消费者失败"的问题，**验收必须站在消费者一侧做**，
  不能拿生产者的自述当结论。

### B20. 假守卫：校验的左右两边来自同一个来源（2026-09-25）

- **现象**：写 `load_sparse_index` 时我加了一段"校验稀疏索引切词算法"的代码，
  形式上是：
  ```python
  if declared.get("gram_algorithm") != sparse_meta_from_manifest(manifest).get("gram_algorithm"):
      raise ...   # 索引需重建
  ```
  看起来很像一道守卫，实际**恒为假**：`declared` 就是
  `sparse_meta_from_manifest(manifest)` 的返回值，两边是同一个来源。
- **根因**：写的时候想着"要校验 manifest 声明与索引实际一致"，
  但**手上唯一的数据源就是 manifest**，于是写出了"manifest 与 manifest 比"。
  移上 `# pragma: no cover - 自比较` 这种注释更是雪上加霜 ——
  它把"这段代码永远不会触发"包装成了"这段代码无需覆盖"，
  等于给假守卫盖了章。
- **解决**：改成**读磁盘上那份索引自己的元数据表**再比对：
  `actual = dict(conn.execute("SELECT key, value FROM sparse_meta"))`，
  然后比 `gram_algorithm` / `row_id_checksum` / `schema_version` 三项。
  左右两边现在是**两个独立来源**（manifest 声明 vs 索引文件自述），
  才能真正抓住"文件与 manifest 错配"（备份恢复拷错目录、人工替换、上次构建残骸）。
  测试 `test_tampered_row_id_checksum_is_detected` 直接篡改文件里的校验和来锁定它。
- **面试怎么讲**：「**一道校验如果能通过，就只能是因为它真的比了两个不同的东西。**」
  判断方法很便宜：遮住断言的一边问自己"这一行删掉会怎样" ——
  如果删掉也不影响结果，那它从来没起过作用。
  这条和 D21（失效探针）是同一族问题的两个面：D21 是**探针在被测对象两种状态下给同一个值**，
  这里是**断言两侧本来就是同一个值**。共同点是都提供"假确定性"，
  而假确定性比没有检查更贵，因为它会让人停止检查。

### B21. 字段名撞车：A 轨的 `hybrid` 和 B 轨的 `hybrid` 不是一回事（2026-09-25）

- **现象**：给 B 轨检索端点（`POST /retrieval/search`）加检索模式时，
  最自然的写法是加一个 `mode` 字段。但同名撞车，连带撞出一个测试：
  `tests/test_retrieval_api.py::test_unknown_body_fields_do_not_break_the_request`
  传 `{"mode": "hybrid"}` 期望**被忽略**（它本来就在测"未知字段被忽略"）→ 变红。
- **根因**：两个独立问题叠在一起。
  ① **同名字段、不同语义**：A 轨（`search-demo`）的 `mode: "vector" | "hybrid"`
  指的是「纯向量 vs 向量 + 关键词加分」（`calculate_keyword_bonus` 那套**规则加权**，
  关键词只加不召回）；B 轨的 `hybrid` 是**双路召回 + RRF 融合**。
  同一个请求体在两个端点间复用时，`hybrid` 会静默改变含义，`vector` 在 B 轨直接 422。
  ② **原本是被忽略的未知字段**：B 轨端点从来没有 `mode`，
  把它变成实义字段等于**静默改变契约** —— 老调用方传什么都开始被当真。
  那条测试之所以红，是因为它在正确地警告我"契约变了"。
- **解决**：字段改名 `retrieval_mode`（不复用 `mode`）。这样 ①两个概念在 wire 层
  就分开了，②旧行为（`mode` 仍被忽略）保持不变，测试不用改也不用删。
  同时在 `schemas/retrieval_schema.py` 里把两个类型分开命名
  （`RetrievalMode` = A 轨 / `ChunkRetrievalMode` = B 轨）并写明区别，
  避免下一个人再踩。取值给 `None` 表示"跟随服务端默认"，
  **默认值只在 `routers/retrieval.py::DEFAULT_RETRIEVAL_MODE` 存一处** ——
  schema 与路由各写一个默认值，就是下一次"改了 A 忘了 B"的种子。
- **面试怎么讲**：「**加字段之前先查这个名字在不在这套 API 里已经被用过。**」
  同名字段跨端点复用，是最便宜也最难查的一类兼容性事故 ——
  它不改任何代码逻辑，只改语义，而语义没有任何工具会帮你检查。
  加分讲法是那条红掉的测试：**它不是障碍，它是守门人**。
  一个"未知字段被忽略"的用例在字段被转正时红掉，正是它该做的事；
  真正危险的处理是顺手把它改成"已知字段"，那样就没人记得契约被改过。

### D23. 评测口径把检索质量绑在了格式差异上：压平空白后 R@1 差 7 条（2026-09-25）

- **现象**：同一份索引、同一批金标，两套口径给出两个数：
  `dense-only R@1 = 0.7160`（探针）vs `0.6296`（生产评测脚本）。
  逐条对比后差异**全部**集中在一处：
  ```
  g003: 探针(压平文本)=第1名   探针(原始文本)=第3名   生产(原始文本)=第3名
  ```
  8 条 gold（7 条 title + 1 条 colloq）里，只有"文本压平"这一个变量在动。
- **根因**：语料里同一份 FAQ 常有 **md 与 html 两份孪生 chunk**
  （`data/corpus/` 下 185 个 html + 184 个 md，大量同源），内容相同但**换行位置不同**：
  md 里是 `\n`，html 抽出来后是空格。金标 span 抽自其中一份的原始文本，
  于是名次第 1 的孪生 chunk 因为 `\n` vs `" "` 被判成"未命中"，
  真正的原始那份排在第 3 —— **判据量的是排版，不是检索**。
- **解决**：评测侧加 `normalize()`（连续空白压成单个空格），
  命中判据统一为 `normalize(span) in normalize(text)`；
  两边同时压平，判定只关心"这段文字在不在里面"。
  并且**把这个口径差异量化写进报告**（`raw_text_match_baseline` 字段）——
  报告里同时给出"原始文本口径下 dense-only 是多少"，
  而不是把旧数字悄悄换掉。压平只会让判定更宽松，不会制造假命中
  （span 仍是原文片段，受影响的只有空白字符）。
- **面试怎么讲**：「**评测口径本身是要被审计的。**」
  这次差 7 条（占 8.6%），比大多数检索优化的收益都大 ——
  如果不去逐条归因，很容易把口径差异当成"混合检索带来的提升"或"退步"。
  可讲的细节是**归因过程**：不要停在"两个数不一样"，
  而是构造一个只改一个变量的对照（压平 vs 原始 × 同一批 id 序列），
  让差异**可数**。顺带一个副产品：这个坑解释了为什么金标用 **span** 而不是
  `chunk_id` —— 用 id 的话，孪生 chunk 里"哪个算命中"根本没法表达，
  而且重新切分后金标会静默过期。

### D24. FAISS 同分并列时，两条调用路径的返回顺序不一致（2026-09-25）

- **现象**：逐条对比"直连 `index.search(vec, 10)`"与"经由
  `search_chunk_index`（带 `IDSelectorBatch` 预过滤）"的 top-10 `row_id` 序列，
  81 条里 17 条序列不同。**但相似度数字完全一致**，差异只出现在第 9~10 名：
  ```
  探针 ids = [4451, 4450, 3240, 3239, 4449, 4448, 3238, 3237, 3246, 3245]
  生产 ids = [4451, 4450, 3240, 3239, 4449, 4448, 3238, 3237, 4457, 4456]
  scores   = [0.9179, 0.9179, 0.9179, 0.9179, 0.864, 0.864, 0.864, 0.864, 0.8332, 0.8332]
  ```
  成对同分（`4451/4450`、`3240/3239`…）—— 同一文档的 md/html 孪生 chunk 向量几乎相同。
  影响是实打实的：`c002` 在探针里命中第 9 名，在生产路里掉出 top-10（同分并列的边界）。
- **根因**：`IndexFlatIP` 上两条路径的实现不同：直连走 `IndexFlat::search`，
  带 selector 走 `search_with_parameters` → 内部的堆（heap）在**分数严格相等**时
  没有稳定排序保证，谁进谁出取决于扫描与堆调整顺序。
  这不是 bug，是"并列时顺序未定义"这一事实在不同 code path 上的显影。
- **解决**：**不去改 FAISS**，而是把这个不确定性记下来并控制它的影响范围：
  ① 评测报告里标注"top-k 边界处的同分并列可能使 ±1 条结果变动"，
  结论不建立在 0.01 级别的差异上（本次权重结论的差异是 0.0247~0.4000 量级，不受影响）；
  ② 同分并列的根源是**孪生 chunk 同时进了索引**（与踩坑 B17 同源：
  父子块 / md-html 双份都会造成重复命中），真正该修的是那一层，
  而不是让检索排序去背锅。
- **面试怎么讲**：「**向量检索在并列时没有稳定顺序，这不是实现缺陷，是算法的性质。**」
  能讲到"我去查了 top-k 序列在不同调用路径下是否一致，而不是只看命中率"
  就已经超过大多数人的深度。再补一句工程结论：
  **凡是建立在"第 k 名"上的结论，都要先确认第 k 名不是并列出来的**；
  以及"重复 chunk 应该在建索引/去重阶段解决，不该指望排序去挑"。

### D25. 隔离测试的假绿：夹具两个租户共享词表（2026-09-25）

- **现象**：我为稀疏路写的跨租户隔离测试第一版是这样：
  ```python
  hits = search_sparse_index(query_for("beta"), access=ChunkAccessFilter(tenant_id=TENANT_A))
  assert hits == []
  ```
  它**通过了**。但它通过的原因不是"隔离有效" —— 而是"这个词在 A 的语料里也命中"，
  一旦有泄漏它也会照样通过。真正暴露问题的是同一批测试里另一条失败的用例：
  夹具里两个租户的语料共享 `正文N` 这组词组
  （`markdown_body` 用 `prefix=f"{tag}正文"`，只有 ASCII tag 不同），
  所以任何含中文的查询在两边都能命中，**用它根本测不出跨租户泄漏**。
- **根因**：我复用了既有的 `query_for()` 辅助函数，
  而它产生的查询是**跨租户同构**的（这正是夹具为了让两个租户"结构相同、内容不同"
  而设计的）。测试想表达的是"仅 B 有"，实际拿到的是"两边都有"。
  两个断言之间没有关联，所以"应该为空"的断言在一个总能命中的查询上恒真。
- **解决**：改用**只存在于 B 的 ASCII 词** `beta`
  （它出现在 B 的**文件名/附录 salt** 里，那部分是 ASCII 片段，切词时整词保留，
  不参与 CJK bigram，因此不会被 A 的 `正文N` 命中），
  并**补一条配套反向断言**：
  ```python
  assert search_sparse_index("beta", access=tenant_B)  # 换身份必须能查到
  ```
  没有这一条，空结果断言依然可能是"查询本身无效"而非"隔离生效"。
- **面试怎么讲**：「**安全测试里，"应该为空"是全世界最弱的断言。**」
  空结果至少有三种成因：真的没权限、查询本身没有命中能力、索引里根本没有该内容 ——
  三者对安全的意义完全不同，但断言一视同仁。
  正确做法是**用正向断言给负向断言做担保**：同一查询换一个身份必须能查到，
  这才证明"空"是权限造成的。延伸一句：这类测试的**夹具设计**往往才是漏洞所在，
  夹具太"对称"（两个租户结构一致）会让隔离测试失去分辨力。

### E10. 交付前必须扫一遍自己留下的占位代码（2026-09-25）

- **现象**：写 B 轨测试时，我在两个地方留下了调试/占位残留：
  ```python
  shifted = [...] if False else [...]          # 两种写法二选一，前一种已经废弃
  chunks = list(session.execute.__self__.execute("SELECT 1")) if False else None
  assert chunks is None                        # 占位：下面用真实白名单
  ```
  另外在一个诊断脚本里留下 `print("...", capture := describe_...)` 这种顺手写的表达式。
  这些**都能跑、都不报错**，`ruff` 也只对其中一部分有意见。
- **根因**：改代码时"先留着、等下再删"的中间态，只要不被工具逼着，
  就会跟着提交进仓库。它们的危害不是"跑不了"，而是：
  ① 读代码的人要花时间判断它是不是有意义的兼容分支（`if False` 特别像"临时关掉的功能"）；
  ② 下一个人照着它的样子继续写；
  ③ 它让"这段代码有人认真看过"这个信号失真。
- **解决**：交付前固定做两件事：`ruff check`（能抓到一部分）+ **人肉 grep 关键字**：
  `if False`、`TODO`、`占位`、`FIXME`、`print(`（脚本外的）、`:=`。
  本次就是这么清出来的。
- **面试怎么讲**：「**代码的读者成本是交付质量的一部分。**」
  `if False else` 这种写法最坏的地方在于它**长得像有意的兼容分支**，
  比直接留一段死代码更误导。可以补一句自己定的纪律：
  凡是用"先留着"说服自己的东西，就在同一轮里删掉 ——
  "下一轮再清"等于把删除这件事外包给未来的自己，而未来那个自己不知道当初为什么留它。

### D26. 测试靶子取自「顺序不保证」的集合：一条随机变红的隔离测试（2026-09-25）

- **现象**：稀疏路的授权白名单测试第一版是这么写的 ——
  ```python
  target = ingested[TENANT_A].chunk_ids[0]        # 拿"入库结果的第一条"当靶子
  hits = search_sparse_index(query_for("alpha"),
                             access=ChunkAccessFilter(tenant_id=TENANT_A,
                                                      allowed_chunk_ids=frozenset({target})))
  assert hits                                      # 断言它必须能查到
  ```
  它**时红时绿**：同一个文件连跑 6 次，红了 2 次（整文件跑绿、单跑那个类红、再单跑又绿）。
  诊断输出显示原因是靶子变了 —— `chunk_ids[0]` 在不同进程里分别是
  `c_2a71f4f6…` / `c_3d3cf77b…` / `c_109e638e…`（**每次都不一样**），
  撞到"附录块"那一次就必然为空：
  ```
  target text = '附录 tenant-alpha-alpha.md\nsalttenant-alpha-alpha.md 补充说明'
  hits = []
  ```
- **根因**（两层，缺一层都不会红）：
  1. **顺序不保证**：`repository.list_chunks` 的排序是
     `created_at ASC, chunk_id ASC` —— 同一事务插入的 chunk `created_at` 相同，
     于是实际由 `chunk_id` 兜底；而 `chunk_id` 是**含随机 version uuid 的哈希**，
     所以"第一个 chunk 是谁"每个进程都不同。**排序键看起来是确定性的，实际上不是。**
  2. **切词器对纯 ASCII token 不对等**：`tokenize_grams` 对含 CJK 的 token 产出 bigram
     （`alpha正文1` → `al/lp/ph/ha/a正/正文/文1`），对**纯 ASCII token 走整词路径**
     （`salttenant-alpha-alpha.md` → `salttenant/alpha/md`）。
     "附录块"正文恰好是纯 ASCII，因此**它本来就检索不到中文查询** ——
     这不是 bug，是设计；但让"随便挑一个 chunk 当靶子"变成了掷骰子。
  3. 还有一层遮蔽：前两次全量跑**恰好都赢在掷骰子上**，
     于是这条测试一直被当成绿的 —— 直到它变红才被发现。
- **解决**：**不从"入库返回的集合"里挑靶子，从"真实命中"里挑**：
  ```python
  baseline = search_sparse_index(query_for("alpha"), access=...)   # 先不带白名单跑一次
  assert baseline
  target = baseline[0].chunk_id                                    # 拿真实命中的当靶子
  hits = search_sparse_index(..., allowed_chunk_ids=frozenset({target}))
  assert {h.chunk_id for h in hits} == {target}
  ```
  断言随之变强：从"这个 chunk 能查到"（依赖挑对了 chunk）变成
  **"白名单把结果收窄到它自己"**（不依赖任何顺序假设）。
  同一批的连带清理：夹具那个因此被加出来的第三元组 `ingested` 现在**没人用**了，
  一并退回二元组 —— 留着它就是把"顺序不可靠"这个教训重新埋回去（承踩坑 E10）。
- **面试怎么讲**：「**排序键看起来是确定性的，不代表结果顺序是确定性的。**」
  `ORDER BY created_at` 这种写法在"同一事务批量插入"时几乎必然是 tie，
  真正的顺序由兜底键决定；而兜底键如果是个**带随机 id 的哈希**，
  顺序就是每次进程随机的。可讲的三个层次：
  ① 现象层——用重复运行把"偶发红"变成"可复现的红"（我跑了 6 次，2 次红，并打印了靶子）；
  ② 归因层——把"顺序"和"内容"两个变量分开看，定位到"靶子撞上了一个本来就不该命中的块"；
  ③ 设计层——**测试的靶子应该来自被测逻辑自己的输出，而不是来自旁路的清单**。
  最后这句可以延伸成一条通用纪律：**凡是"取第一条"的断言，
  都要先问一句"这个第一条凭什么保证是它"**。

### F6. 检索延迟的瓶颈是「每次请求重读整份 manifest」，不是检索算法（2026-09-25）

- **现象**：三模式对比评测里，单条检索耗时（含加载）为
  dense **172.7ms** / sparse **185.7ms** / hybrid **355.7ms**
  （中位数 137.2 / 157.9 / 317.0，`reports/retrieval_hybrid/evaluation_20260925.txt`）。
  `hybrid ≈ dense + sparse` 这个**加法关系**是钥匙：它说明两路在**各自重复支付同一笔加载成本**。
  而 9229 条的 `IndexFlatIP` 内积检索本身是毫秒级 —— 170ms 花在了别的地方。
- **根因**：`load_active_manifest` **没有任何缓存**（全仓 `grep lru_cache` 零命中，见
  `services/ingestion/index_manifest.py`）—— 每次 `search_chunk_index` /
  `search_sparse_index` 都会重新读 `index_manifest.json`
  （**19,043,203 字节**，含 9229 条正文）并做 JSON 解析。
  也就是说：**延迟被"把数据搬进来"的 I/O 与反序列化主导，
  而被优化对象（召回算法）根本不是瓶颈。** 属于"能力已经建好、用它的方式把预算花在非目标上"。
  顺带一个同源观察：稀疏索引文件 **32.4MB**，比稠密索引（18.9MB）还大 ——
  bigram 的倒排本身就重，这也是"稀疏路不该被当成免费的第二路"的量化依据。
- **解决（本批只登记 + 定性，刻意不修）**：本批目标是"把混合检索做出来并给出可信数字"，
  而**改缓存会同时动到"索引版本切换后旧缓存必须失效"这条正确性线** ——
  回滚 / 重建之后若仍读到旧 manifest，就会出现"索引已回滚、检索却按旧版本算"的**静默错配**。
  正确修法是：键取 `(root, index_name, index_version)` 的缓存 + 版本切换时显式失效，
  并且要有一条测试证明"切版本后第一次检索就读到新的"。
  混在功能批里改，会让"混合检索的收益"和"缓存引入的 bug"搅在一起、分不清是谁造成的，
  所以**登记待办、不混批**。
- **面试怎么讲**：「**先确认瓶颈在哪一层，再决定优化什么。**」
  可讲的点：① 用"hybrid ≈ dense + sparse 的加法"这种**结构性证据**定位到
  "两路在重复付同一笔加载成本"，比盯单个数字更有说服力；
  ② 说清"为什么当时不改"—— 缓存必须跟索引版本切换的正确性绑在一起，
  这是个**取舍判断**，不是"没时间"；
  ③ 收成一句：**优化前先分清"算法成本"和"把数据搬进来的成本"**。

### B22. 「先写探针再改代码」的探针会覆盖掉自己的基线证据（2026-09-25）

- **现象**：B17 要修「Top-K 被同一段内容占满」，流程是**先写探针量出基线（2.14/3），再改代码**。
  探针跑完把结果写进 `reports/rag_ingestion_auth_review/b17_topk_diversity_20260925.json`，
  台账随即引用这个文件作为「接线前」的证据。
  改完代码重跑同一个探针 —— 它**原地覆盖**了同一个路径，
  文件内容变成「接线后 3.00/3」。**台账里引用的数字与文件内容当场对不上**，
  而且是**静默的**：没有任何报错，`git status` 也只显示一个 `??`（本来就是未跟踪文件）。
- **根因**：探针的输出路径是**硬编码常量**，写入方式是**覆盖写**，文件名里**没有状态标签**。
  根本问题是把「一次性的量测脚本」和「可复跑的对比证据」当成同一个东西了 ——
  对比证据天生有两个状态（改前 / 改后），而一个不区分状态的输出路径
  只能容纳其中一个。第二个更深的原因是**探针一直住在 `tmp/` 里**：
  `tmp/` 不进 git（所以没有历史可回溯）、随时可能被清（所以更想"赶紧跑一遍"），
  这两个性质都会推着人写出"跑一次就完事"的脚本。
- **解决**：① 探针从 `tmp/` 提升为 `scripts/audit_chat_evidence_diversity.py`（进 git、可复跑）；
  ② 加 `--label`（`before` / `after`）与 `--out`，**默认文件名带 label 与日期**；
  ③ **文件已存在时默认拒绝覆盖**（返回码 2，要 `--force` 才覆盖）——
  把"我是不是正要盖掉另一批数据"变成一次显式动作；
  ④ 接线后的数据改名隔离为 `B17_chat_evidence_diversity_after_20260925.json`；
  ⑤ **接线前的真实路径证据其实没丢** —— 这条纠正本批**最初**的错误判断：
  那个文件是**已被 git 跟踪**的（B8 批提交过），`git show HEAD:<path>` 就能原样取回。
  实测取回后 `wasted=6 / 平均 2.14/3`，与台账里的数字**逐位一致**。
  最初为什么判错：只看 `git status` 的 `??` 列表没看到它，就下结论"未跟踪、无法恢复"——
  而 `??` 恰恰意味着**它不在这里**，正确判据是 `git ls-files --error-unmatch <path>`
  （或 `git log --oneline -- <path>`）。**这条误判本身就是 D28 的又一个实例**
  （没验证的推测被当成结论写进了记录）。
- **面试怎么讲**：「**能重跑，和能重跑出"上一次那一份"，是两件事。**」
  可讲：① 我判断一个数据结论是否可信，标准之一是"能不能拿着当时的输入再跑一遍"——
  这正是我一开始把探针从 `tmp/` 挪进 `scripts/` 的原因；
  ② 但挪进仓库还不够：**对比类证据必须把"状态"编进文件名**，
  否则第二次运行就是在销毁第一次的结论，而且它不会报错；
  ③ 顺手讲防御式写法 —— 证据文件**默认不覆盖**，
  让"覆盖"成为一个需要显式参数的动作，比事后去 git 里捞要便宜得多；
  ④ 诚实交代"我以为丢了、其实没丢"这个全过程：**先按"它是否被 git 跟踪"去查**
  （`git ls-files`，而不是看 `git status` 的 `??`），再决定要不要"接受损失"。
  这里可讲的是**两层**教训 ——
  第一层：覆盖写会毁掉对比证据（所以加 `--label` 与防覆盖）；
  第二层：**"证据丢了"这个结论本身也要验证**，别用一个未经验证的判断去结案。

### D28. 写进正式文档的「疑似」会被下游当事实用：一条没人验证的猜测活了一个批次（2026-09-25）

  就出现了一条「口语化 7 条金标复核 → 判定是金标假阴性还是真的捞不到」——

- **根因**：把「观测到的现象」与「对现象的猜测」写进了同一行，

  丢掉限定条件（"未逐条复核"）。更深一层：**猜测一旦落进文档，

### D29. 前后对比类取证没有「对照列」："变快了"就无法归因（2026-09-25）

- **现象**：给 manifest 加缓存后重跑同一份取证脚本，端到端 hybrid 中位从 268.5 ms
  掉到 25.9 ms —— 数字很漂亮，但**这个数字本身不能证明是缓存带来的**：
  同一台机器、同一个进程、同一批 query，只要**运行顺序**或**页缓存热态**不同，
  耗时也会变。当时的诱惑是直接写"缓存让检索快了 10 倍"。
- **根因**：前后对比类取证里，"改动后的组"与"改动前的组"是**两次独立运行**，
  中间隔着的变量不止被改动的那个（机器负载、页缓存、模型预热状态、GC 时机）。
  没有一个**在两次运行里应当保持不变**的量作参照，"变化"就无法归因。
  这和 **B20**（假守卫：校验的左右两边来自同一个来源）是一体两面 ——
  B20 是"两边同源导致守卫永远通过"，D29 是"两边不同源却假装只差一个变量"。
- **解决**：在取证脚本里**刻意留一个绕过被改动代码的直调列**当对照：
  `audit_manifest_load_cost.py` 直接调 `read_manifest(path)`（**不经过
  `load_active_manifest` 的缓存**），它预期在 before / after 两轮里**耗时不变**。
  实测 121.5 → 125.5 ms（在散布内）—— 有了这一列，"其它列变快"才能归因到**缓存**；
  若对照列也跟着变了，说明变的是环境，前面所有结论都要作废。
  一般化：**对照列必须走"绕开本次改动"的路径**，且**预先声明它在两轮里应当不变**。
- **面试怎么讲**：「**没有对照的前后对比只是故事，不是证据。**」
  可讲：① 我做完优化后第一件事不是庆祝快了 10 倍，而是问"怎么证明是这次改动带来的" ——
  在探针里留一列绕过改动的直调，它在两轮里**必须不变**；
  ② 这一列还顺手纠正了一条定性：既然直调 `read_manifest` 耗时不变、
  而它读的是同一个 19MB 文件，那省下的就不可能是磁盘 I/O，
  只能是**反序列化与对象构造**——"快了"和"为什么快"是两个问题；
  ③ 这和"守卫的两边必须不同源"是同一类思维：**结论与它的证据之间要有独立的支点。**
