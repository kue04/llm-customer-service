## A. 环境与工具链

### A1. `git commit` 返回成功，但分支指针根本没前进

- **现象**：命令退出码为 0、输出也像成功了，但 `git log` 里找不到这条提交，
  `git status` 显示的状态与提交前一样。
- **根因**：git **不会自动创建嵌套 ref 目录**。当分支名含 `/`（如 `feature/rag`）而
  `refs/heads/feature/` 目录不存在时，写 ref 这一步会失败，但提交对象已经创建了 ——
  于是表现为「提交存在但没人指向它」。
- **解决**：任何 commit 之后**必须复核**：`git rev-parse HEAD` 看指针是否真的动了；
  异常时 `git rev-parse <commit>` 取回提交，并手工修复 ref。
- **面试怎么讲**：这是「退出码 0 ≠ 副作用已生效」的典型例子。
  我说得出为什么"验证副作用"比"看命令输出"重要 —— 在自动化流程里，
  一个静默失败的分支指针会让后续所有工作站在错误基线上。

> **2026-09-23 补记（规范落盘批次第 3 次复现）**：
> `git commit` 打印 `[optimize/interview-ready d2f43a0]`、文件数也对，
> 但 `git rev-parse HEAD` 返回 **`e5d5bc3`**（`packed-refs` 里的旧值）；
> 按本文姿势 `mkdir -p .git/refs/heads/optimize` + 写 40 位完整 SHA 后**立即恢复**。
> 三次复现（B1/B2、B3、本次）说明：**只要分支名含 `/` 就必然发生，不是偶发**。
> 因此「提交后必须 `git rev-parse HEAD` 复核」是硬动作，不是可选项。

### A2. 代理与直连都会间歇性抽风，`git push` 只能"探测 + 交替重试"

- **现象**：push 被拒。实测**重试 5 次才成功**（前 4 次直连与代理通道都被拒）。
- **根因**：本地网络环境不稳定，且代理与直连**不是互补关系** —— 两者都可能失败。
  最初记录（B1/B2 期间）以为"直连不行就用代理"，B3 期间的实测推翻了这个结论。
- **解决**：每次先探测可用通道，失败就换另一个交替重试；
  **以远端 SHA 为准**判断是否真的推送成功，不看命令输出。
- **面试怎么讲**：这体现了「结论要能被新证据推翻」。
  我把一条写进文档的旧结论（坑 2）明确标注为"实测修订"，
  而不是删掉重写 —— 保留推翻过程本身就是工程判断力的一部分。

### A3. 轻量 venv 缺源配置，`pip install` 必须显式指定镜像

- **现象**：装依赖直接失败。
- **根因**：本机 venv 在 B3 期间被破坏过一次，之后按"轻量口径"重建
  （不含 torch / transformers / datasets / trl / peft / sentence-transformers），
  源配置没有连带恢复。
- **解决**：`pip install --trusted-host mirrors.aliyun.com -i https://mirrors.aliyun.com/pypi/simple/`。
  并把「venv 是轻量版」写进交接文档，避免下一个窗口重复踩。
- **面试怎么讲**：环境即代码的一部分。我会把环境的**限制**（缺什么、为什么缺）
  写进交接文档，因为"某次能跑"和"别人能跑"是两件事。

### A4. Bash 与 PowerShell 两个通道能力不互补

- **现象**：同一条命令在一个通道能跑、在另一个通道报错；想用另一个"绕过"时发现它也不支持。
- **根因**：两个 shell 的可用命令集、路径语义、引号转义规则都不同，
  不存在"一个不行换另一个就行"的保证。
- **解决**：按命令能力**选通道**，不做互补假设；跨通道的产物（临时文件）用绝对路径传递。
- **面试怎么讲**：跨平台脚本要显式声明依赖哪个 shell，而不是"应该都能跑"。

### A5. 一轮里反复重跑全量测试，会把「绿」跑成「红」（2026-09-23）

- **现象**：为了取回转义被吞掉的 pytest 汇总行，在**同一轮**里连跑 5 次全量测试。
  第 4 次起出现 `1 failed, 789 passed` —— 失败的是一条**只做读写删**的对象存储用例
  （`LocalObjectStore.delete`）。看堆栈才发现异常是 `SystemExit` 而不是 `AssertionError`：

      object_store.py:234: path.unlink()
      → sitecustomize.py: _safe_path_unlink → _try_trash → _check_bulk_delete_guard
      → raise SystemExit(1)
      {"count":550,"threshold":50,"scope":"turn"}

- **根因**：**环境的批量删除保护是按「轮次」累计计数的**（本机阈值 50 个文件/轮）。
  每次全量 pytest 都会在临时目录创建/删除数百个文件，跑几次就必然越阈值；
  **一旦越阈值，本轮内后续所有删除都被拦下**，于是「唯一要删文件的用例」替所有用例背了锅。
  两个误导性特征让它特别像真 bug：① 失败在**测试末尾**（前面的断言都过了）；
  ② 前几次运行连汇总行都看不到（守卫在 sessionfinish 阶段 `SystemExit`，
  进程在打印汇总行之前退出，退出码 1）—— 很容易被判成"测试挂了"，其实**是绿跑完了**。
- **解决**：**一轮只跑一次全量测试**；需要多次取数时改成
  「一次运行 + 输出重定向到证据文件 + 从文件里读」，而不是反复重跑。
  判断"到底绿没绿"要看**进度输出里有没有 `F`／`E` 字符**，不要只看退出码和汇总行。
  另：`--basetemp=<项目内路径>` 可以让临时文件不落在用户 Temp 目录，
  但**不能**绕过按轮计数的保护 —— 那是环境级约束，不是路径问题。
- **面试怎么讲**：**测试结果的"红"也分真假，先看异常类型再谈原因** ——
  `SystemExit` / `PermissionError` / 断连 属于**环境**信号，`AssertionError` 才是**逻辑**信号。
  更深一层的通用教训：**当测试与被测系统共享同一个"会消耗的全局资源"时
  （删除配额、连接数、临时目录、端口），测试之间就不再独立** ——
  这正好是 D 节反复讲的"测试要可重复、无顺序依赖"的另一个化身。
  工程上还多一条：**不要为了"把日志看全"而反复重跑重任务**，
  一次落盘、多次读取，既省时间也避免自己把环境弄脏。

### A6. 环境删除守卫会把 pytest 的「绿」连同它的证据一起吃掉（2026-09-23）

- **现象**：B7 收尾跑全量，进度条全绿走到 `[100%]`、**一个 `F`/`E` 都没有**，
  然后**没有** `884 passed` 汇总行，退出码 1，末尾多出一行：

      [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":1542,"threshold":50,"scope":"turn",...}

  最危险的读法是「跑到最后挂了 → 一定有测试失败」；实际上**测试全部通过**。
- **根因**：pytest 的 `TempPathFactory.getbasetemp()` 在 session 收尾时会把
  `%TEMP%\pytest-of-kk\pytest-*` 的旧目录**批量搬进 `garbage-<uuid>/` 再整体删除**
  （本机累计 1542 个文件），命中环境的批量删除守卫（阈值 50），
  守卫抛 `SystemExit(1)`，进程在 `pytest_terminal_summary` 打印汇总行**之前**退出。
  也就是说：**守卫不针对你的测试，它针对 pytest 自己的临时目录清理**，
  但被杀的是「打印测试结果」这一步。
- **排查过程（两条死路，记下来省得再走）**：
  ① `--basetemp=<项目内路径>` 无效 —— pytest 对已存在的 basetemp 会**先删再重建**，照样触发守卫；
  ② `PYTEST_DEBUG_TEMPROOT=tmp/...` 直接**卡死**（3 分 48 秒没跑完，86% 处停住），手动终止。
- **解决（B7 起的固定口径）**：
  1. 全量测试改用 `--junitxml=<file>` 取数 —— XML 在**测试执行期**写入，
     不经 sessionfinish，不受守卫影响；`tests / failures / errors` 三个属性即权威计数；
  2. warning 条数用 `pytest --collect-only -q` 的 warnings summary 取
     （只收集不执行，不产生批量删除）；
  3. **判据 = 「输出里有没有 `F`／`E`」＋ JUnit XML**，不看退出码、不看汇总行；
  4. 一轮只跑一次全量（A5 的既有纪律）——守卫按**轮次**累计计数，重跑只会更糟。
- **与 A5 的关系**：同一个环境约束的两次现身，方向相反 ——
  A5 是环境噪声把「绿」**说成**「红」（多出一条 failed）；
  A6 是环境噪声把「绿」的**证据抹掉**（汇总行消失、退出码 1）。
  两次的应对是同一句话：**别拿退出码和汇总行当唯一真相源**。
- **面试怎么讲**：**"测试结果"和"测试结果的呈现"是两个东西，都可能被环境污染。**
  当 CI 或本地跑分出现"退出码非 0 但看不到失败详情"时，第一反应不该是改代码，
  而是找一个**不受呈现层影响**的权威数据源（这里是机器可读的 JUnit XML）。
  更深一层：**测试基础设施自己也依赖文件系统这类共享资源**，
  它和被测系统一样会遇到环境限制 —— 所以"为什么这条命令不可信"的答案，
  往往要到"它收尾时还做了什么"里找。

## B. 契约与职责边界

### B1. 解析器不能碰数据库：用 AST 守卫测试代替 code review

- **现象（设计约束）**：解析器是纯函数（`parse(source: bytes, filename: str)`），
  不接受 `tenant_id`、不写库 —— **签名被测试锁死**，因为多一个参数就会破坏可测试性与可复用性。
- **根因**：租户过滤、事务边界、落库都属于数据访问层，
  一旦解析器开始接收 `tenant_id`，它就从"纯函数"退化成"带环境的半成品"。
- **解决**：把约束写成**可执行断言**，而不是靠评审时人工看：
  - 源码扫描拒绝 `sqlalchemy` / `repository` / `db`；
  - AST 解析断言不出现 `parse_document(...)` 调用（见 D1）；
  - 断言解析器签名不含 `tenant_id` 参数。
- **面试怎么讲**：纪律会腐化，断言不会。把"我们约定不这么做"翻译成"CI 会拦住你"，
  是架构约束真正生效的唯一方式。

### B2.「算 hash」与「标 duplicate」被文档写在一段里，实际必须拆到两层

- **现象（认知陷阱）**：计划原文「每份原文件计算 SHA-256；重复文件标记 duplicate，
  不能创建第二份有效文档版本」把两件事写在同一段，读起来像"同一个任务里做完"。
- **根因**：**计算 hash** 只需文件字节（纯函数层就能做）；
  **判定 duplicate** 需要「同租户下是否已有同 hash 的版本」+ 当前 job 的 document_id + 事务边界，
  这些在纯函数里根本拿不到。
- **解决**：机制在解析层（`ParsedDocument.metadata["content_hash"]`，
  由 `REQUIRED_METADATA_KEYS` 保证必然存在），判定在流水线层
  （`find_version_by_content_hash` 命中则标 `duplicate`、不建新版本）；
  数据库层再用 `uq(tenant_id, content_hash)` 兜底 —— 即使流水线判漏，写入也会被拒。
- **面试怎么讲**：这是我主动识别并写进审查文档的"文档字面与架构现实不一致"。
  我没有照字面硬做，而是拆成两层并说明为什么，还补了数据库层的第二道防线。

### B3. 上传接口建版本会撞唯一约束

- **现象（推演出的必然故障）**：若上传时就创建 `document_version`：
  先传 `a.pdf`（hash `H1`）→ 文档 A、版本 1；再传**内容相同**但文件名不同的 `b.pdf`（hash 同为 `H1`）
  → `source_uri` 不同 → 新建文档 B → 创建版本时**必然撞** `uq(tenant_id, content_hash)`，
  抛 `IntegrityError`。
- **根因**：`document_versions` 上有 `uq(tenant_id, content_hash)`，
  而上传期还不知道 `parser_name` / `parser_version`（要解析后才知道）。
- **解决**：上传只建 `documents`（按需）+ `ingestion_jobs`，**不建版本**；
  版本由流水线在 `parsed` 阶段创建。`ingestion_jobs.document_version_id` 本身就是**可空列**，
  说明"建 job 时版本还不存在"是被 schema 预期的顺序。
- **面试怎么讲**：这是"从唯一约束反推职责边界"。
  我不需要在线上撞一次 `IntegrityError` 才知道，读 schema 就能推出来。

### B4. `source_uri` 与对象存储 key 必须分离

- **现象**：如果把「逻辑标识」和「物理路径」当成一个东西，"重传追加版本"就会坏掉 ——
  同一个文件重传时物理路径变了（含随机 document_id），就再也关联不回原来那条文档。
- **解决**：
  - `documents.source_uri = upload://<净化后的文件名>`：**稳定的逻辑标识**，
    同租户内同名 = 同一份文档（重传即追加版本）；
  - 对象 key = `rag/<tenant_id>/<document_id>/<净化文件名>`：**物理位置**（计划原文要求含租户路径与随机 ID）。
  - 并且 `source_uri` **由服务端派生、不接受客户端传入** —— 否则 KB-A 的成员
    可以传入 KB-B 文档的 URI 给别人的库追加版本，形成越权写入口。
- **面试怎么讲**：「逻辑标识 vs 物理位置」的分离在存储设计里是通用模式
  （数据库主键 vs 文件路径、UUID vs 自增 ID 同理）。这里的加分项是我同时想到了它的**安全含义**。

### B5. `source_uri` 唯一性粒度：用「可逆性」而不是「灵活性」做判据

- **背景**：初版把唯一约束写成 `uq(tenant_id, knowledge_base_id, source_uri)`（三列），
  看起来比两列更灵活（同一文件可分别归属多个知识库）。
- **现象（推演出的必然故障）**：`document_versions` 上有 `uq(tenant_id, content_hash)`，
  即租户内相同内容只允许一份版本。同一文件 F 上传到 KB1 后再上传到 KB2：
  三列约束**放行**新建文档 D2，但 D2 建版本时**必然撞** content_hash 唯一约束。
  结果只有两条坏路 —— 要么 `IntegrityError`，要么按「重复文件标 duplicate」
  生成一个**永远没有内容的僵尸文档**。
- **根因**：两条约束在**不同粒度**上表达同一个事实（"这份内容已经存在"），
  三列的写法让「文档层」可以绕过「版本层」的判定。
- **解决**：改为 `uq(tenant_id, source_uri)`（两列）。
- **决定性判据是「可逆性」而不是「灵活性」**：

  | 方案 | 以后要变更时的代价 |
  | --- | --- |
  | 两列（现选） | 要支持跨库共用，加 `knowledge_base_documents` 关联表 —— **纯增量，不动现有数据** |
  | 三列（原设计） | 要合并重复副本时，chunk / embedding / ACL / 审计已各自分叉，**无法判定该留哪份** |

  附带收益：两列给出**正确语义** —— `source_uri` 唯一标识「这份文件这个逻辑实体」，
  重传同一 URI 应**追加版本**而非新建文档，正好对上 `documents` / `document_versions` 的分层本意。
- **落地纪律**：修订 `0001` 而非追加 `0002`，依据是「`data/rag_metadata.db` 不存在、
  0001 从未落到任何正式库、尚未提交」，并显式写明
  **「若 0001 已被部署，则必须改为追加新迁移」**。
- **面试怎么讲**：两个方案在功能上都"能满足需求"，差别只在**以后要改的时候代价多大**。
  三列方案的"灵活性"是**假的** —— 真正的灵活性体现在**能不能平滑演进**。
  这条还附带一个可讲的细节：我明确标注了"修订 0001 的前提"，把对环境状态的依赖写出来了。

### B6. 解析失败：抛异常，而不是返回结构化错误对象

- **现象（有意偏离计划原文）**：计划 2.1 写的是「失败返回结构化错误，不能吞异常」。
  实现改成**抛 `ParserError`**（结构化、带稳定 `error_code`）。
- **根因**：做成**返回值**会留出「调用方忘记检查」的口子，
  而忘记检查的后果是**把空文档当成功结果送进索引** —— 这是**静默的数据损坏**，
  比一次显式失败严重得多。
- **解决**：
  - `ParserError` 携带 `error_code` / `message` / `parser_name` / `filename` / `detail`，
    可直接落 `ingestion_jobs.error_code` / `error_message`；
  - 未预期异常必须保留 `__cause__`（`raise ParserError(...) from exc`）——
    只包不链等于吞掉 traceback，有测试断言 `excinfo.value.__cause__` 是原始异常；
  - **产物自检前置**：模板返回前跑 `validation_errors()`
    （表格块必须有 `table_json`、图片块必须有 `image_ref`、`order` 必须从 0 连续），违反即抛 `parse_failed`。
- **面试怎么讲**：返回值与异常的区别，本质是**失败模式的可忽略程度**。
  返回值可以被忽略、异常默认中断。当「忽略失败的后果是数据损坏」时，
  必须选**不容易被忽略**的那个。关键在于这是个**权衡判断**而不是教条 ——
  所以我在决策记录里写明了"这是有意偏离计划原文"，并说明理由。

### B7. 解析产物自带身份，不依赖取出它的运行时环境

- **背景**：计划只列出 `ParsedDocument` 的四个字段（`title` / `blocks` / `metadata` / `warnings`），
  实现额外加了三个**自描述字段**：`parser_name` / `parser_version` / `source_type`。
- **根因**：`document_versions` 表需要落 `parser_name` / `parser_version`，
  而流水线在「解析成功」与「写库」之间可能**失败重试、可能换 worker 执行**。
  如果这两个值只挂在**解析器对象**上，重启后就必须靠 registry 再猜一次 ——
  而 **registry 是可被覆盖的**（测试里就换过）。
- **解决**：让**产物自带身份**，一条历史版本记录就能**脱离运行环境**被解释。
- **面试怎么讲**：原则是「**数据应当自描述，而不是依赖取出它的环境**」。
  反过来说：如果一个数据记录必须依赖"当时的代码版本/全局注册表"才能解释，
  那它就不可回溯 —— 而 RAG 系统**必须能回答"这份内容的解析结果是怎么来的"**。

### B8. 上传必须流式累计大小，不能全量读进内存

- **现象（容量风险）**：`await file.read()` 会把整个文件读进内存，
  50 MB 上限 × 并发请求会直接打爆内存。
- **解决**：分块读取、**超限立即中止**；上限做成模块级常量 + 环境变量可覆盖。
  测试覆盖三个边界值：「超一字节即 413」「**恰好等于上限放行**」「上限配置写错报 500」。
- **面试怎么讲**：边界测试最容易漏的是**「恰好等于」**那一档 ——
  超限与未超限两侧都会被测到，唯独等号处最容易被 `>` / `>=` 写反而不被发现。

### B9. OCR 引擎缺失时降级为**警告**，而不是让任务失败

- **现象**：扫描件需要 OCR，但本机默认不装真实引擎（`rapidocr-onnxruntime`）。
  如果这时抛错，用户会**反复重传一个必然失败的文件**。
- **解决**：四级行为分离，并用注入的假引擎全覆盖（测试不需要真装引擎）：

  | 场景 | 行为 |
  | --- | --- |
  | 文本层充足 | **不调用** OCR（对已能取到文字的页面做 OCR 只会引入识别错误） |
  | 文本层低于阈值且引擎可用 | 整页渲染 2 倍 PNG → OCR，`pdf_ocr_used=True`，无警告 |
  | 文本层低于阈值且**引擎不可用** | **不报错**，写 `no_text_layer` 警告（`detail.ocr_engine=None`） |
  | 引擎可用但识别为空 | 同样写 `no_text_layer` 警告 |

- **两个关键细节**：
  1. **文件已经存进对象存储了**，让任务失败只会让用户重传；
     正确做法是**入库成功 + 一条可查询的警告**。
  2. 触发条件是「**低于阈值**」（默认 32 字符）而非「**为空**」——
     只识别出页眉页脚的扫描件文本量很少但**非零**，只判空会**永远不触发**。
- **面试怎么讲**：① 失败要往「**可观测**」而不是「**中断流程**」的方向设计。
  ② 「阈值 vs 判空」是**真实数据形态驱动的细节** —— 扫描件的典型特征正是"有少量文字但不是正文"。

### B10. 超出计划原文的取舍必须标注方向（更严 / 更宽 / 更可测）

- **背景**：B4 完成后回头逐条比对「计划原文」与「实现」，
  发现**三处实现比文档更多/更宽/更严**，但此前只写在决策记录里，
  **没有点明「这是超出文档的加固」**。

  | # | 计划原文 | 实现取舍 | 方向 |
  | --- | --- | --- | --- |
  | 1 | 校验「成员身份」，无成员关系 403（**未区分角色**） | 写操作要求 owner/editor，reviewer/viewer 一律 403 | **更严** |
  | 2 | 「只在嗅探结果明确且与扩展名不一致时拒绝」，**未定义「明确」** | 物化为强特征（必拒）/ 弱特征（html 前缀命中不拒）/ 无魔数（放行）分级 | **更宽**且更可测 |
  | 3 | 用 `get_document_by_source_uri` 复用，**未规定 `source_uri` 来源** | 服务端从净化文件名派生，**忽略客户端传入** | **更严** |

- **为什么标注是必要的**：这些取舍若不写明，**下一位执行者会误以为它们是文档要求**，
  从而在「放宽写权限」「让前端传 `source_uri`」这类改动上以为**无需决策记录**。
- **面试怎么讲**：讲「**实现与规范的偏差管理**」。
  偏差本身不可怕（规范总有模糊处），可怕的是**偏差没有被记录、后来者把偏差当规范**。
  方向标签（更严/更宽/更可测）让对方一眼判断影响面。

### B11. 两条硬约束字面打架：用「不可变上下文对象」同时满足（2026-09-23）

- **现象**：计划里同时写着两条看起来互斥的要求 ——
  ①「切分器**不得接收 `tenant_id`**」（和解析器同一条纪律：不许把归属信息塞进函数参数）；
  ②「每个 chunk **必须带 `tenant_id` / `acl` / 页码 / `heading_path`**」。
  按 ① 的字面执行，② 就没法满足；按 ② 的字面执行，就得给切分器加一个
  `chunk_document(doc, tenant_id, acl, ...)` —— 那 ① 就形同虚设。
- **根因**：约束 ① 想禁止的其实是**「归属信息以裸标量散落在调用链上」**这种形状
  （每加一个字段就要改签名、漏传就退化成空租户），不是「知道归属信息」这件事本身。
  两条要求描述的是**不同的关注点**，被写在了同一段话说，于是显得矛盾。
- **解决**：引入**不可变上下文对象** `ChunkContext`
  （`frozen=True`，构造时校验非空 + 版本号 ≥ 1），把归属信息**整体**传进去，
  函数签名变成 `chunk_document(document, *, context: ChunkContext, config: ChunkConfig)`。
  于是 ① 满足（签名里没有任何裸 `tenant_id` / `acl` 形参），
  ② 也满足（`context.to_metadata()` 一次性带齐 tenant / acl / 来源 / 版本）。
  并补决策记录 `[D-9]`，写明**三个被否决的方案 + 否决理由**：
  裸参数（每加字段就改签名）、读全局/请求上下文（纯函数层不可测、并行不安全）、
  下游补字段（落库时才知道归属，等于把错误推迟到最不可见的地方）。
  **守卫用 AST 而不是字符串匹配**：逐个函数检查形参名，
  于是「换个名字绕过去」和「git 里有但没人调用」两类偷懒都被拦住。
- **面试怎么讲**：**需求里出现「两条要求打架」时，先别急着二选一，
  先问「这两条各自真正想禁止的是什么」。** 90% 的情况是它们在不同抽象层上说事，
  找一个能同时承载两侧关注点的**数据结构**，冲突就消失了 ——
  这比写一条"例外说明"然后留个 TODO 强得多（例外说明会被后来人当默认行为继承）。
  另外配一句加分项：**决策记录要写被否决的方案**，
  否则三个月后没人知道当时为什么不用更简单的那个，很容易被"简化"回去。

### B12. 硬上限与「不许截断」打架：选宽松但要留痕 + 统计可见（2026-09-23）

- **现象**：计划同时要求「代码块**不从内部截断**」和「chunk **不超过 700 tokens**」。
  一段 900 tokens 的代码块，两条只能满足一条。
- **根因**：两条约束的**优先级不同但计划里没排序** ——
  「不截断」是为了保住代码的可执行性（截断后语义直接坏掉），
  「不超上限」是控制 embedding 质量与成本的软目标。硬把代码切开会
  用「坏的输入」去换「好看的数字」。
- **解决**：**代码块整块保留**，允许它超过 `max_tokens`，但做三件事让它**可追溯**：
  ① 在 `ChunkingStats` 里记 `oversize_chunks`（有多少块超限）；
  ② 在 chunk 的 `metadata_json` 上打超额标记；
  ③ 在审查文件里**显式标注方向为「更宽」**（而不是假装没违反）。
  正文段落一侧**仍受硬上限约束**，不放宽。
- **面试怎么讲**：**当两条要求真的互斥时，回答不该是"我选了一条"，
  而该是"我按代价大小排了优先级 + 让违反变得可观测"。**
  "静默放宽"是最差的处理 —— 数字变好看了，但没人知道是什么换来的。
  可复用纪律：**任何「有意允许的例外」都必须能在统计里被数出来**，
  否则它在下一次排查时就是一个幽灵。
  （配套素材：`ChunkingStats` 的 17 个计数字段覆盖了每一处删除/妥协行为，
  回答"这份文档为什么少了一段"。）

### B13. 自引用复合外键下，`session.delete(row)` 循环 ≠ 一条批量 DELETE（2026-09-23）

- **现象**：B6 开工基线 `2 failed, 837 passed`，两条都挂在 `TestIdempotency`，
  且都是「任务**已经 succeeded** 之后再跑一次」。失败阶段固定在 `persisted`：

      sqlalchemy.exc.IntegrityError: FOREIGN KEY constraint failed
      [SQL: DELETE FROM document_chunks WHERE document_chunks.id = ?]
      [parameters: [('39f08807…',), ('440cf62c…',), … 共 6 行]]

  **首次执行全绿**，只有重跑才红 —— 所以正常链路用例一条都没发现它。
- **根因**：`document_chunks` 有一组**指向自己的复合外键**：

      ForeignKeyConstraint(["document_version_id", "parent_chunk_id"],
                           ["document_chunks.document_version_id", "document_chunks.chunk_id"])

  父 chunk 与子 chunk 同属一个版本，**删除时无论先删谁、只要对方还在就构成违规**。
  而 `delete_chunks` 当时写的是 `for row in rows: session.delete(row)` ——
  ORM 把它编译成 `DELETE ... WHERE id = ?` 的 **executemany，每行一条独立语句**。

  关键知识点：**SQLite 对即时（immediate）外键约束的检查发生在「每条语句结束时」**。
  于是"删掉父 chunk"这条语句结束时，子 chunk 仍然指着它 → 报错。
  「一条语句」与「N 条语句」在这里不是性能差异，而是**语义差异**。

  更值得记的是这个缺陷的形状：**函数自己的 docstring 写的正是正确做法**
  （「只要一次全量 delete 即可……逐条删反而会中途撞外键」），
  而代码用的恰是被它否定的做法 —— 注释与实现相反，code review 最容易漏的就是这种
  「读注释觉得没问题」的错。

- **解决**：把删除改成**一条**语句，让整个版本的行在同一个语句内一起消失，
  约束在语句结束时看到的已经是"全部删完"的一致状态：

      statement = (delete(models.DocumentChunk)
                   .where(DocumentChunk.tenant_id == tenant_id,
                          DocumentChunk.document_version_id == document_version_id)
                   .execution_options(synchronize_session="fetch"))
      result = session.execute(statement)

  于是**既不需要**「先删子再删父」的拓扑排序，**也不需要** `ON DELETE CASCADE`
  或 `PRAGMA defer_foreign_keys`。`synchronize_session="fetch"` 用来让 session 里
  已被删掉的 ORM 实例同步失效 —— 紧接着要写入的新行 `chunk_id` 与旧行相同（确定性哈希）、
  只有主键 `id` 不同，留着旧实例会让"到底删干净没有"变得不可信。
  验证：单文件 49 passed → 全量 **839 passed**。

- **面试怎么讲**：三句话。
  ① **"ORM 的 `session.delete()` 循环不等于批量 DELETE"** —— 它退化成 N 条独立语句，
  而这在有外键的方案里是**语义**差别：约束是每条语句结束时检查的（SQLite immediate FK），
  一条语句内整体消失才合法。
  ② **"这类缺陷只在重跑路径上暴露"** —— 首次执行时表里没有旧行，循环体根本没进去，
  代码看起来完好。所以**幂等性必须有专门的重跑用例**，不能指望正常链路顺带覆盖；
  这也解释了为什么它一直藏到基线才红。
  ③ **"注释与实现相反"是最隐蔽的一类错** —— 排查时先别信注释，去读真实 SQL
  （日志里那句 `DELETE ... WHERE id = ?` 就是全部答案）。
  通用纪律：**遇到「删除一批同表互相引用的行」，先问"这是几条语句"**。

### B14. 「按租户分片」还是「全局共用」没拍板，三个子系统各自选了一个（2026-09-23）

- **现象（红/绿双份证据：`B7_index_multitenant_RED.txt` / `_GREEN.txt`）**：
  1. A 租户上传并跑流水线 → 生效索引 `v1`，6 条（全 A 的 chunk）；
  2. B 租户上传并跑流水线 → **生效索引仍是 `v1`、仍是 6 条，但条目全部变成 B 的**；
  3. 此时 A 租户检索 → **0 条命中，且没有任何报错**。
  用户视角是「系统没找到资料」，而证据就在数据库里 —— **静默错误，比崩溃危险**。
- **根因（三处自相矛盾）**：

  | # | 位置 | 症状 |
  | --- | --- | --- |
  | ① | `index_builder.rebuild_index` | 只取**触发构建的那一个租户**的可索引 chunk |
  | ② | `repository.create_index_build` | 版本号按 `(tenant_id, index_name)` 计 → 两个租户**都拿到 v1**，`publish_build_directory` 切换时把另一个租户的 `v1/` 目录 `rmtree` 掉 |
  | ③ | `IndexManifest.verify()` | 要求 `entry.tenant_id == manifest.tenant_id` → 全局索引**永远无法通过校验** |

  三处单看都合理：① 是 B6 之前的检索口径、② 是"每个租户独立编号"、
  ③ 是"manifest 声明的租户要和条目一致"。**放在一起才炸** ——
  因为「索引是每租户一份还是全局一份」这个决定**从头到尾没有被显式拍板过**，
  于是每个子系统在写自己的时候各自选了一个。
  这不是编码错误，是**缺失决策（missing decision）**。
- **解决（4 处代码 + manifest 留痕）**：
  1. `repository.list_indexable_chunks(..., all_tenants=False)` —— `all_tenants=True` 去掉租户过滤；
  2. `repository.create_index_build(...)` —— 版本号查询去掉 `tenant_id` 条件
     （docstring 写明：版本号必须**全局**递增，否则两租户都拿 v1 会互删目录）；
  3. `repository.list_index_builds(..., all_tenants=False)` —— 跨租户降级 superseded 用；
  4. `index_builder.rebuild_index(..., all_tenants=True)` —— 取数用 `all_tenants`；
     manifest `extra` 增加 `"scope"` 与 `"tenants"` **留痕**；
  5. `IndexManifest.verify()` —— 放宽为「条目租户 ∈ **声明集合**」
     （`extra["tenants"]`，缺省退回旧语义 → **B6 老 manifest 仍能通过**，有意的向后兼容）。
  验证：A 入库 `v1`(6 条全 A) → B 入库后 **`v2` 含 12 条（B 6 + A 6）**，
  两租户各只命中自己的 6 条。
  回归守卫：`test_manifest_contains_both_tenants` +
  `test_own_tenant_can_still_retrieve_after_another_tenant_ingests`。
  **`search_chunk_index` 的契约一行未改** —— 修的是根因，不是在调用侧绕过。
- **面试怎么讲**：
  ① **为什么 B6 测试全绿却漏了它？** 因为三处各自都有测试、各自都过，
     唯独**「两个租户先后入库」这条跨子系统的组合场景没有用例** ——
     单模块测试验证不了子系统之间的**契约假设**。这正是 F1「接线」方法论的实证：
     B7 把检索 API 接上去的那一刻，这个缺陷才第一次有了暴露的机会。
  ② **为什么说它是"缺失决策"而不是"bug"？** 因为没有任何一行代码"写错了"——
     是三个模块对同一个未定义问题的答案不同。**架构约束如果只存在于人的脑子里，
     它就不是约束**；修完之后落成的可观测证据是 manifest `extra["scope"]` +
     `extra["tenants"]` + 响应字段 `tenant_count`（退化回分片时它会变成 1，测试立刻红）。
  ③ **「静默零命中」为什么比崩溃危险？** 崩溃会有人看日志；零命中只会有人抱怨
     "搜不到"，而且**没有任何报错可以让告警系统抓**。对策是给响应加
     `visible_chunk_count`，让"零命中"与"索引坏了"可区分 ——
     **把可观测性当作正确性的一部分来设计**。

### B15. 验收规范把「目标」和「现状」写在同一格 → 两边都不能用（2026-09-23）

- **现象**：拿到一份 515 行的企业级验收规范，指标定义和门槛都写得很细。
  想拿它当设计参考、又当验收基准，**两件都做不成**。逐条核对 13 项能力：

  | 规范里写的 | 项目实况 |
  | --- | --- |
  | §1「本次未收到源码，不能断言现有系统缺失某项实现」 | 源码早就在手，阶段 0~4 已落地并逐阶段审查 |
  | §6.2 方法矩阵含 XLSX / 扫描件 OCR / 图表视觉理解 | 只有 5 种格式，**OCR 仅接口** |
  | §7.3 要求三个状态字段 | 实现是**单一 `status` 枚举**，质量门禁整块没有 |
  | §10.5 `M10 Recall@5≥0.85` | 口径失真 + 无 gold 集，**这个数根本给不出** |

  结果分成两类：**3 处事实已过期**（当参考用会引到错结论）、
  **7 处「规范要求」与「项目实况」直接冲突**（当基准用会误报 NEEDS_WORK）。

- **根因**：表层是「规范自称非现有实现审计报告，却被当验收基准用」——**定位与用法不匹配**；
  深层是**表格结构**：门槛表只有「类别 / 起始目标 / 发布判定」三列，**没有一列写现状**。
  于是写的人按"应该做到什么"填，读的人按"我们做到了什么"读 ——
  **同一张表，两个人读出两种意思**。

- **解决**：三步，且**门槛数字一个都不改**（改门槛 = 把尺子锯短，规范当场作废）：
  ① **加「文档关系表」**：把本规范与 goal / 执行计划 / 路线图 / 台账的职责边界一次列清 ——
     列完它就自证「不是审计报告」；
  ② **把「目标」和「现状」拆成两列**：凡涉及现状的表格加「当前状态 + 证据」，
     取值只准 `已实现 / 部分实现 / 未实现`，另设受控标注 `已建未启用 / 未就绪 / 未演练`；
  ③ **执行层规则单开一节**（§17）：取数口径、结论状态机、证据落盘 ——
     它们不是「验收标准」而是「怎么执行验收」，混进正文会让标准与流程互相污染。
  收尾靠脚本做机械校验（`scripts/verify_acceptance_spec.py`，8 项），不靠通读。

- **面试怎么讲**：**让「目标」和「现状」不互相冒充，比把数字定高更难，也更值钱。**
  一条通用判据：**任何一列如果既可能被读成"要求"、又可能被读成"结果"，它就是设计缺陷。**
  这也解释了为什么「做不到就把标准改成做到的」是错的 —— 那是把尺子锯短，
  量出来的数好看，但没有任何决策价值。
  副产品更实在：改完之后这份规范自动变成差距分析文档的「按指标细化版」。

## C. 安全与鉴权

### C1. JWT 的 `sub` 不是 `users.id`：一个不报错的静默失效

- **现象**：测试里"拒绝非法扩展名"的用例期望 415，实际返回 **403** —— 300 行以外的错误码暴露了鉴权错了。
- **根因**：JWT 的 `sub` 是身份提供方的 `external_id`，
  而 `knowledge_base_members.user_id` 与 `documents.created_by` 都是指向 **`users.id`** 的外键。
  直接拿 `sub` 去比对成员关系，**永远匹配不上**。
- **解决**：新增 `_resolve_principal_user_id`，统一经 `get_user_by_external_id` 映射一次。
- **面试怎么讲**：这是最值得讲的一个坑，因为**它的失败方式是静默的** ——
  线上表现是"加了成员也永远没写权限"，不报错、不崩溃、日志也干净。
  是测试里一个**看起来不相关**的断言（415 用例）把它暴露出来的。
  结论：跨系统边界的 ID 映射必须有测试覆盖，因为错得最安静的地方往往最贵。

### C2. 通用脱敏规则会打碎结构化 ID

- **现象**：审计摘要写入后，`knowledge_base_id` / `job_id` 变成不可关联的乱码。
- **根因**：通用「手机号 / 订单号」脱敏规则会把 **32 位 hex 里的连续数字串**当成敏感数据打码。
- **解决**：脱敏范围收窄为**只对自由文本**（`filename` / `user_agent` / `error_message`）；
  结构化 ID 由服务端生成、不含个人信息，**必须保持原样**，否则审计失去可追溯性。
- **面试怎么讲**：这是由**断言不相等**逼出来的（而不是靠人工看日志）。
  脱敏的目标是"去掉个人信息"，不是"把所有像 ID 的东西都抹掉"——
  过度脱敏会静默破坏审计价值，而审计恰恰是出事时唯一能用的东西。

### C3. 跨租户与"不存在"必须不可区分

- **现象**：如果跨租户返回 403、资源不存在返回 404，攻击者就能用状态码差异
  **探测某个资源是否存在**（枚举租户/文档 ID）。
- **解决**：四类资源（知识库 / 文档 / 版本 / 任务）统一返回 **404**，
  且两种情况的响应体**逐字节相同**（各写一条断言）；`tenant_id` 全程只从令牌取，
  查询串里塞同名字段被忽略。
- **面试怎么讲**：多租户系统的存在性泄漏是很常见的疏漏，
  因为"403 更准确"在直觉上是对的。要讲清楚的是：**返回值的语义准确性和信息安全性会冲突，
  安全优先时选择更钝的响应**，并用断言把"逐字节相同"固定下来。

### C4. 内容嗅探的边界：宁可放过，也不错杀

- **现象**：要求"校验 MIME 与文件内容一致"，但 md / txt **没有魔数**，
  HTML 也只能靠 `<!DOCTYPE html` 前缀启发式判断。
- **根因**：硬校验会误杀正常文档 —— Markdown 里内嵌 HTML 是常见写法。
- **解决**：物化为**两级**：
  - 强特征（`%PDF-`、zip 内含 `word/`）：扩展名指向 pdf / docx 时**必须**匹配，否则 415；
  - 弱特征 / 无魔数（html / md / txt）：**一律放行**（"不确定即放行"）。
  另加一条独立验证：B3 的「扩展名优先于 MIME」继续成立
  （`report.pdf` + `Content-Type: text/html` + 真实 PDF 内容 → 正常受理）。
- **面试怎么讲**：准入策略要在「拦得住」和「不误杀」之间选边界。
  我的取舍是：**只在"确定不一致"时拒绝**，因为"正常文档传不上去"比"放过一个伪装文件"
  对用户的伤害更直接。同时用测试把两侧边界都钉住（正例 + 反例）。

### C5. 令牌自报的 `scopes` 必须忽略，否则任何持令牌者都能提权

- **现象（设计风险）**：计划只要求「校验 JWT」，**没有规定 token 里的角色与权限怎么用**。
  如果直接采信 token 里的 `scopes` / `permissions` claim，
  那么任何持有合法令牌的人（或任何签发配置宽松的 OIDC Provider）都能**自报权限提权**。
- **解决**：明确切分两件事 ——
  - token 里的 `roles` claim **被信任**（毕竟是我们自己签发的），
    但服务端只把它当作「**你是谁**」；
  - **权限（scopes）一律由服务端按 roles 推导**；
  - token 里若出现 `scopes` / `permissions` claim，**完全忽略**。
- **收益**：权限变更**不需要重新签发令牌**，也不必信任外部系统的权限声明。
- **固化**：负向测试 `test_token_supplied_scopes_are_ignored`（逻辑层）+
  `test_token_supplied_scopes_cannot_elevate_privileges`（HTTP 层）。
- **面试怎么讲**：一句话版本 —— **令牌证明「你是谁」，服务端决定「你能做什么」**。
  反向做法（信任令牌里的权限）在单体系统里"能用"，
  但一旦接入外部 IdP 就是提权洞，因为它把授权决策**外包给了令牌内容**。

### C6. `ROLE_SCOPES` 由授权表推导，不手工维护

- **现象（必然漂移）**：角色 → scope 的映射，如果既有一张「授权表」
  （`READ_OPERATION_ROLES` / `WRITE_OPERATION_ROLES` / `REVIEW_ACTION_ROLES`），
  又有一份手写的 `ROLE_SCOPES`，两份**必然漂移**。
- **解决**：`ROLE_SCOPES` 由三张授权表的 **inversion 自动生成**，
  并加断言 `test_role_scopes_is_exact_inversion_of_policy_tables` 锁住两者**严格同构**。
  新增接口只需加表项**一处**，权限视图自动同步。
- **面试怎么讲**：这是「**消除重复真源（single source of truth）**」的经典应用。
  关键在最后那半句：**推导还不够，必须加一条断言把推导结果和原表锁在一起** ——
  否则推导逻辑本身可能写错，而错误会以"权限莫名其妙不对"的形式出现，极难定位。

## D. 测试方法论

### D1. AST 守卫测试 > 源码字符串匹配

- **现象**：为了断言"代码里不调用 `parse_document(...)`"，
  最初用源码字符串匹配 `"parse_document("` —— 结果**误伤 docstring**
  （注释里提到这个函数名就报错）。
- **解决**：改用 `ast.parse` + `ast.walk`，分别检查 **import 节点**与 **Call 节点**。
- **面试怎么讲**：静态检查要在**语法树**层面做，而不是文本层面。
  文本匹配的假阳性会让人逐渐忽略这个测试，最后等于没有测试。

### D2. 权限矩阵要用真值表驱动，不能抽样

- **现象**：成员权限测试原本只采样三个点：`editor` 放行、`viewer` 403、无成员 403。
  但角色枚举有**四个**值 —— `owner`（写白名单的另一半）和 `reviewer` 完全没测。
- **后果**：如果实现把写白名单误写成 `{"editor"}`，**测试会全绿**，
  而线上必然出现"库主（owner）传不上自己的文件"。
- **解决**：参数化遍历 `KB_MEMBER_ROLES × KB_WRITE_MEMBER_ROLES` 两张真值表，
  另加纯集合断言守两个方向：白名单必须是合法角色的**真子集**
  （拼错角色名 → 静默变成"永远 403"；等于全集 → 分级失效）。
- **面试怎么讲**：抽样测试的盲区正好落在"新增枚举值"上，
  而枚举扩张是最高频的变更。**用集合/真值表驱动测试，让"新增一个值"自动获得覆盖**，
  这是我这批补的最有价值的一件事。

### D3. 用已废弃的状态码常量会引入新 warning

- **现象**：`HTTP_413_REQUEST_ENTITY_TOO_LARGE` 已被 starlette 标记废弃。
- **解决**：改用 `HTTP_413_CONTENT_TOO_LARGE`，保持 warning 数不增长
  （批次结束时 warning 稳定 5 条，且都不是本批引入的）。
- **面试怎么讲**：warning 基线是要守的。基线从 3 涨到 5 的**原因**必须能说清、
  且不能是自己引入的 —— 否则 warning 会逐渐失去信号价值。

### D4. 契约测试的「语义」和「描述」要分开对待

- **现象（冲突处理）**：契约测试 `test_reupload_same_source_uri_appends_version_not_new_document`
  的 docstring 把「命中就加版本」写成了**上传接口**的行为，
  与 B3「上传不建版本、由流水线建」的结论**直接冲突**。
- **根因**：契约的**语义**（同一 URI 只对应一份文档、版本号在文档内连续递增）**没有问题**，
  只是**描述**把责任分给了错误的一方。
- **解决**：**只改 docstring，断言与语义一字未动**，并明确「上传负责复用文档、流水线负责建版本」。
  这样它同时对上传接口（2.3）与流水线（3.3）成立。
- **为什么不能直接改测试**：契约测试是**上下游之间的接口契约**。
  改它的断言等于改契约，会影响已经在实现的调用方；而这里只是**措辞旧了**。
- **面试怎么讲**：区分「**测试的语义**」和「**测试的描述**」——
  断言 = 语义，docstring / 命名 = 描述。
  改描述是低风险的文档修复，改断言是契约变更。
  把两者混为一谈，就会在"只是措辞旧了"时误改契约，或在"契约真变了"时只改注释。

### D5. 二进制 fixture 要换成可复现的生成脚本

- **现象（测试资产问题）**：计划只要求「新增四个 fixture 文件」。
  但样本一旦提交为**二进制**，就没人知道里面是什么、也**没法重新生成** ——
  而 PDF 的字号、DOCX 的样式名**都是断言依据**。
- **解决**：改为「**内容写死在生成脚本里 + 脚本生成样本**」（`scripts/make_parser_fixtures.py`）。
  好处：样本可复现、断言依据**人可读**、脚本末尾校验体积不超过 1 MB（与 CI 门槛同源）。
  并加测试 `test_text_fixtures_match_the_generator_script` 断言文本样本与脚本常量一致，
  **防止有人手工改样本后被重新生成覆盖、让断言悄悄失效**。
- **面试怎么讲**：「**测试资产的可复现性**」。
  二进制 fixture 是"黑盒证据"，脚本生成的 fixture 是"可读证据"。
  当断言依赖文件**内部结构**（字号 / 样式名）时，这个区别是决定性的。

### D6. `.gitattributes` 锁行尾，避免断言以无关原因失败

- **现象（跨机器失效）**：本机 `core.autocrlf=true`，
  `tests/fixtures/` 里的文本样本在别人机器上会被检出成 **CRLF**，
  届时「与生成脚本**逐字节**一致」的断言会以一个
  **和它想守的东西（内容是否被改过）毫无关系的原因**失败。
- **解决**：新增 `.gitattributes`，把两个**文本**样本的 `eol` 锁成 **LF**
  （二进制样本 docx / pdf 不受影响）。
- **面试怎么讲**：一个断言如果在不同机器上有不同结果，
  那它守的**不是行为，而是环境**。这条最能体现"想过别人怎么跑这套测试"。

### D7. 测试数据被自己实现的清洗规则吃掉：比「断言失败」更危险的「前提不成立」（2026-09-23）

- **现象**：写一条「重叠内容应出现在下一块」的用例，
  造了两段各 20 词的段落（都调同一个 `words(20)` 辅助函数），
  结果 `overlap_skipped == 0`、断言失败。第一反应是**重叠逻辑写错了**。
- **根因**：两段文本**逐字符完全相同**，而本批刚实现的清洗规则里有一条
  「**完全重复的相邻段落只保留一份**」—— 测试数据在进入切分逻辑之前，
  就被**自己刚写的清洗层**删掉了一段。于是用例想测的「两段相邻内容之间的重叠」
  这个**前提本身就不成立了**；断言失败只是这个更深问题的**下游症状**。
- **解决**：把第二段改成不同文本（`words(20, start=100)`），
  并在用例里**显式断言前提**（如 `assert len(bodies(result)) >= 2`）。
  顺带获得一个额外收益：这条用例**反过来证明了清洗规则真的生效** ——
  一个"失败"同时验证了两块逻辑。
- **面试怎么讲**：**测试失败时，第一问不是"哪里写错了"，而是"这个用例的前提还成立吗"。**
  尤其当被测系统本身会**修改/丢弃输入**时（清洗、去重、规范化、限流、缓存），
  「造数据」和「被测逻辑」之间就多了一层会吃掉数据的处理 ——
  这类失败的症状（断言值不对）和病因（前提被改）**隔了两层**，最容易误改实现。
  可复用纪律：**关键用例必须把前提写成断言**，
  否则你无法区分"功能坏了"和"数据没到"。同源素材见 D4（语义与描述分开）。

### D8. 度量口径的字符集错配：给 CJK 文本按空白切词计 token，量出来的是错的（2026-09-23）

- **现象**：验证「默认配置下确实产生了 80 tokens 重叠」这条用例，
  实测重叠量算出 **27**，远小于 80，看起来像重叠功能没生效。
- **根因**：**度量工具和被测量对象说的不是同一种「词」。**
  测试里的 `junction_overlap` 辅助函数用 `text.split()` 按空白切词计数，
  而实测文本是**中文** —— 中文句子之间没有空格，整句被算成 **1 个 token**。
  于是「27」这个数字既不是重叠量、也不是 bug，**它什么都不是**。
  另一层坑：文本用「重复句子」生成时，找"公共接缝"会出现**歧义**
  （公共前缀/后缀可以匹配到多个位置），度量结果甚至不唯一。
- **解决**：把度量口径对齐到**被测系统真正使用的口径** ——
  改成**字符级**找最长公共接缝，再**交给 `HeuristicTokenCounter().count()` 计 token**；
  测试数据改成每句各不相同的 200 句，消除接缝歧义；
  并**给度量工具本身补两条自检用例**（先证明"尺子是准的"，再量东西）。
- **面试怎么讲**：**"数字不对"有两种可能：被测对象错了，或者尺子错了。**
  测量辅助函数是测试代码里**唯一不受断言保护的部分**，却决定了所有断言的基准 ——
  它出错时不会报错，只会给你一个"看起来合理的错数"（27 比 80 小，很像个真 bug）。
  可复用纪律：① 度量的口径**必须与被测系统同源**（同一套 tokenizer / 同一个规范化函数），
  不要另写一套"差不多的"；② **测试基础设施本身也要有测试**；
  ③ 造数据时避开"自重复"，否则任何"最长公共子串/接缝"类度量都会退化成多解。

### D9. 用 `importlib.reload` 验证「导入期失败」会污染同进程内其他测试（2026-09-23）

- **现象**：要验证「配置越界时模块在 import 期就崩（fail fast）」，
  自然写法是设好坏环境变量 → `importlib.reload(config.chunking_config)` → 断言抛错。
  单跑这条用例是过的。
- **根因**：`reload` 会让模块里的**类对象被重新创建** ——
  于是「其他测试手上的 `ChunkConfig`」和「模块内的 `ChunkConfig`」
  变成了**两个不同的类**，`isinstance` / `==` / pytest 收集全部悄悄改变行为。
  这是个**顺序依赖**的坑：它只在"这条用例先跑过"时才发作，
  表现出来是**别的用例时绿时红**，排查成本极高。
- **解决**：改成**子进程**验证 ——
  `subprocess.run([sys.executable, "-c", "import config.chunking_config"], env=坏环境)`，
  断言返回码非 0 且 stderr 含关键字段名。子进程天然隔离，
  而且**比 reload 更接近真实场景**（生产里"起不来"本来就是进程级的事）。
  附带修正：原先还断言了 `error_code` 字符串，实际异常 `__str__` 里并不含它 ——
  只断言 stderr 里**确实会出现**的东西（`ChunkConfigError` / `max_tokens` / 坏值）。
- **面试怎么讲**：**"在同一个进程里模拟进程级行为"是测试里的常见错位。**
  进程启动、全局单例、环境变量、模块级副作用 —— 这类行为在进程内模拟时，
  要么模拟不真（reload 出来的类不是同一个类），要么留下污染。
  遇到这类需求，**优先选真隔离**（子进程 / 独立解释器），成本是一个进程启动时间，
  换到的是"这个断言不会给别的用例埋雷"。
  也是 D 节一贯的主题：**测试要可重复、无顺序依赖**。

### D10. 测不到的分支等于没测：硬切逻辑需要「字符级 tokenizer」才触发得了（2026-09-23）

- **现象**：写了一条「超长段落按 token 硬切时**不能丢字符**」的用例
  （拼接所有 chunk 后应能还原原文），跑起来"过"了。
- **根因**：**它根本没走到硬切分支。** 用例用的是 `mock-word-v1`
  （按空白切词），而造的中文长串**没有空格** → 整串被算成 **1 个 token**，
  永远不可能"超长"，于是硬切逻辑一行都没执行。
  用例是"绿的"，但它验证的是一个**从未被触发的分支** ——
  比失败更有欺骗性，因为它**给出的是虚假的信心**。
- **解决**：改用 `mock-char-v1`（字符级计数）让中文长串真的超长、
  强制触发硬切，并**显式断言分支被走到**
  （`assert len(result.children) >= 5`）—— "走到分支"本身要成为断言的一部分。
- **面试怎么讲**：**"代码覆盖率"和"分支被执行"是两回事，
  而"分支被执行"和"断言真的检查了它"又是两回事。** 这条坑的价值在于它很难发现：
  测试全绿、覆盖率不低、逻辑也没错，只是**没有一次运行真正进入这条路径**。
  可复用纪律：**关键的分支/边界用例，除了断言结果，还要断言"前提成立"** ——
  因为 `assert` 在前提不成立时经常**恒真**（比如空列表上的 `all(...)`、
  从未发生的异常、没进过的循环）。同源素材见 D7、D11。

### D11. 测试红了先别改测试：列表缩进那个案子，错的是实现（2026-09-23）

- **现象**：`test_continuation_lines_stay_with_their_item` 失败 ——
  列表项的续行（原本有缩进）在切分后**丢掉了缩进**。
  直觉反应是"用例造的数据/期望写得太严"，想直接放过。
- **根因**：**是实现的问题，不是测试的问题。** 块级清洗里的 `normalize_text`
  按行 `strip()`，把续行缩进当成"多余空白"去掉了；
  但缩进在列表里**是语义**（嵌套层级），不是排版噪声。
  如果当时按直觉改测试，就会**把真 bug 固化成"期望行为"**。
- **解决**：改**实现** —— 新增
  `INDENT_PRESERVING_BLOCK_TYPES = (BLOCK_CODE, BLOCK_LIST)`，
  对代码块和列表**保留缩进**，其余文本块才做逐行去空白。
  顺带确立一条规则：**清洗规则必须是「按块类型分档」的**，
  不能用一套统一的空白处理打天下。
- **面试怎么讲**：**"测试失败"是一个中性的信号，它只说"两边不一致"，
  没说哪边错。** 改测试让灯变绿是最快的路径，也是**最贵的捷径** ——
  它把缺陷永久化成契约。判断方法：**问"这个断言想守的是什么语义"**，
  如果它守的是真实语义（缩进表达层级），那就是实现错；
  如果它守的是实现细节（某个中间变量），那才该改测试。
  同源素材见 D4（语义 vs 描述）、D7（前提 vs 断言）。

### D12. 拿到一个 failed，先看「异常类型 + 抛出点」再决定动不动代码（2026-09-23）

- **现象**：B6 一批里前后见到两次全量测试变红，**都是 failed，处置却完全相反**：

      B5 收尾：1 failed, 789 passed
        → SystemExit，抛出点 sitecustomize.py（运行环境注入的批量删除守卫）
        → 判定：**环境噪声**，不改任何代码（见 A5）

      B6 开工基线：2 failed, 837 passed
        → IntegrityError，抛出点 sqlalchemy 执行"项目自己写的" DELETE 语句
        → 判定：**真缺陷**，修 `delete_chunks`（见 B13）

- **根因**：项目里已经有一条"环境噪声"的先例（A5），这条先例本身很危险 ——
  **它会变成下一次"看到红就说噪声"的借口**。两次的 failed 数量在同一量级（1 条 vs 2 条），
  失败位置也都在"看起来无关的用例"上，靠"像不像上次"是分不出来的。
  真正能分开它们的是三个可核对的事实，而不是印象：

  | 判据 | 噪声（A5） | 真缺陷（B13） |
  | --- | --- | --- |
  | 异常类型 | `SystemExit`（进程被杀） | `IntegrityError`（业务约束） |
  | 抛出点 | 环境注入的 `sitecustomize.py` | 项目自己的 SQL / ORM |
  | 与本次改动的关联 | 与本批改动无关（纯文档改动） | 落在本批新交付的代码路径上 |
  | 是否可复现 | 换个"轮次"就消失 | **稳定复现**（单文件重跑必红） |

- **解决**：把上面那张表固化成动作 ——
  ① **先看异常类型**：`AssertionError` / 业务异常 = 逻辑信号；`SystemExit` /
  `PermissionError` / 断连 = 环境信号；
  ② **再看抛出点**：在项目代码里 = 真；在运行环境注入的模块里 = 多半是噪声；
  ③ **最后单独复跑那一条**（而不是重跑全量）：能稳定复现的就是真缺陷。
  B6 这条正是靠"单独跑 `TestIdempotency` 稳定红"确认的。
  顺带一条纪律：**"问题现场"的证据文件要留着** ——
  本项目同时保留了 `B6_baseline_test.txt`（红的那次）与 `B6_full_test-output.txt`（修好后），
  只留后者会让"这里红过、为什么红、怎么修的"整段历史消失。

- **面试怎么讲**：**"测试红了"和"测试错了"是两件事，判据要可核对，不能靠印象。**
  要讲清的是：**"环境噪声"这个结论本身是有成本的** —— 每用一次，
  下一次真缺陷被当成噪声放过的概率就上升一点。所以它必须有**客观判据**
  （异常类型 / 抛出点 / 可复现性），并且**写进团队的坑记录里**，
  让它成为"可查的规则"而不是"某个人的经验"。
  延伸素材：A5（噪声的画像）、D11（红的是实现不是测试）、D7（断言失败 vs 前提不成立）——
  四条合起来就是一套"测试信号分级"的方法论。

### D13. 列表项内缩进的代码围栏会被吞成行内代码（2026-09-23）

- **现象**：给 737 行的规范文档写交付前校验脚本，8 项检查里报「代码块数不对」：
  `fences=4 blocks=1`（4 个围栏应等于 2 个代码块，实际只渲染出 1 个）。
  定位到规范 §17.3：那段 bash 示例写在列表项里、缩进 2 空格，
  渲染成一个**行内 `<code>` 元素**（内容以 `bash` 开头），**代码块消失**，
  围栏标识符落进了正文。实测：缩进 **2 空格、4 空格都不行**，
  只有**取消缩进**才能渲染成代码块（代价是打断列表）。
  **同一批还在本文件里查出两处同类旧缺陷**（B11、F2 的旧版）—— 已顺手修掉。

- **根因**：列表项内的 fenced code 要按「列表内容缩进 + 4 空格」解析，
  而 Python-Markdown 在本项目的扩展组合（`extra` + `sane_lists` + `fenced_code`）下
  两种缩进都没被识别，退化成行内代码。
  真正危险的是它**同时骗过两道防线**：
  ① 源文件用编辑器看完全正常（围栏成对、缩进整齐）；
  ② 全文围栏总数是**偶数** —— 只数总数的校验会认为「围栏没问题」。
  **另注（不要混记）**：本文件里还有用**缩进式**代码块（不带围栏）的段落，
  表现也不一致 —— B13 那个渲染成了代码块，D12 那个退化成普通段落（换行保留但无 `<pre>`）。
  两者机制不同（indented code block vs fenced code）；本条只钉死**围栏**这一条，
  缩进式那条结论**不确定**，所以本文件的示例一律改用「围栏 + 取消缩进」。

- **解决**：① 列表项内不放围栏代码块：单行示例改用行内代码，多行示例取消缩进；
  ② 校验脚本增加「**按 h2 章节统计围栏，每段必须偶数**」这一项 ——
     代码块不跨章节，所以每段都该是偶数，**奇数的那一段就是问题所在**；
  ③ 经验回写 `markdown-longdoc-verify` skill（校验清单五项 → 六项）。

- **面试怎么讲**：**「源文件看起来对」和「渲染出来对」是两件事。**
  这类静默故障不报错、不留痕，只能靠程序校验发现。
  更值得讲的衍生结论：**校验项本身要按「故障模式」设计** ——
  只查「围栏总数是偶数」，这个 bug 会完整漏过；改成「按章节查」，它立刻暴露。
  同一个校验目标，**粒度不同，捕获能力差一个数量级**。

### D14. 交付前校验器会假报警：先校准口径，再判定被校验对象（2026-09-23）

- **现象**：同一轮校验里，**两条假报警和一条真报警长得一模一样**：

  - `[codeblocks] fences=4 blocks=1` → **真**：列表内缩进围栏被吞（见 D13）；
  - `[tables] md=21 html=24` → **假**：我的正则不认引用块内的表格（行首是 `>` 再接竖线）；
  - `<div class="codehilite"` 计数漏块 → **假**：无语言 / 未高亮的代码块不计入。

- **根因**：校验脚本是**新写的**（口径从未被验证），被校验的文档是**刚手工改过的**。
  **新写的校验器 + 新改的文档 = 谁也证明不了谁** —— 报警无法直接归因。

- **解决**：① 报警后**先单独验证校验器的口径**：拿「已知答案」探针测它 ——
  手写一个含引用块表格、含无语言围栏的小样例，看它认不认；
  ② 计数改口径：代码块用 `html.count("<pre")`，表格正则改 `^[> \t]*\|`，
     数列数前先排除转义竖线；
  ③ 脚本入库（`scripts/verify_acceptance_spec.py`）并过 `ruff` ——
     顺手清掉 `l` 这类变量名告警，因为**告警堆多了会掩盖真问题**。

- **面试怎么讲**：这条和 D12 是**同一套方法论的另一半**：
  D12 是「拿到 failed 先看异常类型 + 抛出点」，分的是「环境 vs 代码」；
  这条分的是「**校验器的错 vs 被校验对象的错**」。
  通用规则：**任何新写的检查工具，必须先用「已知答案」跑一遍**，
  否则它的输出只是噪声 —— 这也是「评测器自身也要评测」在工具层的同一个道理。

### D15. 证据文件名承诺了内容却没兑现：`*_collectonly_warnings.txt` 里没有 warning（2026-09-23）

- **现象**：核 warning 条数时，去翻 B7 留下的 `B7_collectonly_warnings.txt`，
  想看基线是几条 —— 打开发现文件里**只有测试清单**（末尾是 `880 tests collected`），
  **没有任何 warning 汇总**。而 B7 记的"warning 5 条"确实存在（它来自全量运行的 stdout）。
  实测确认：`pytest --collect-only -q` **不执行测试**，因此不产生 warning summary。

- **根因**：**证据文件名是一次"接口承诺"** —— 名字说里面有 warnings，读的人就不会去别处找。
  更要命的是这条口径被写进了项目笔记（"warning 条数用 `--collect-only` 取"），
  于是它**看起来有据可依**，实际上从没人验证过。
  **「有一个没验证过的口径」比「没有口径」更危险**：后者会去查，前者不会。

- **解决**：① 明确分工并写死：
  `--collect-only` → **取测试数**（880 / 889）与确认收集期无错误；
  **warning 条数 → 取全量运行的 stdout**（`889 passed, 5 warnings, ...`）；
  ② 本批证据文件改用名副其实的名字 **`B8_collectonly_tests.txt`**；
  ③ 同步修正 `MEMORY.md` 第 8 节的口径条目；
  ④ 连带现象：全量 stdout 的汇总行**可能被环境守卫吞掉**（见 A6）——
  那种情况下 **warning 就取不到**，结论里要写「N/A（汇总行被守卫吞）」，
  **不许估算、不许沿用上一次的数字**。

- **面试怎么讲**：**命名是接口的一部分。**
  一个文件 / 函数 / 字段的名字，就是它对使用者的承诺；承诺与内容不符时，
  错误不会立刻暴露，而是在**别人照着名字去用**的那一刻才爆发。
  更值得讲的是那条元教训：**写在文档里的"操作口径"必须有一条实测记录支撑** ——
  否则它会以"权威"的姿态传播，比口头经验更难纠正。
  可延伸：D3（用废弃常量引入新 warning）说明 warning 本身要管，
  这条说明**"数 warning 的方式"也得管**。

### D16. 接线守卫会静默变成空：目标改名后断言照样「全绿」（2026-09-23）

- **现象**：B8 给 B7 的检索接线补 AST 守卫（`tests/test_wiring_guards.py`）时意识到一件事：
  这类守卫的断言都长成 `assert "retrieve_chunk_items" in names`。
  如果**目标本身消失**（函数被改名、文件被挪走、`routers/*.py` 的 glob 返回空），
  "在某集合里找 X"这类断言会失败，但
  **"集合里不该有 X"（`assert not offending`）或 parametrize 到空列表**这两种写法，
  会**必然通过**。也就是说：**守卫可能因为"没东西可守"而变成装饰。**

- **根因**：守卫是对**约束**的断言，而约束的**主体**（文件、函数）在断言里是**隐式**的 ——
  写的人假定它在，读的人也假定它在。只有它消失的时候才暴露，
  而那时测试往往**不是红，而是绿**（空集合 / 空 parametrize 的**假绿**）。
  **假绿比假红危险得多**：假红会被追查到底，假绿会被当成"守卫正在工作"。

- **解决**：三条一起做 ——
  ① **取不到就报错**：`_function_def` 找不到函数时抛 AssertionError（消息写明"守卫已失效"），
     **不返回 None**；
  ② **健全性检查**：显式断言目标文件存在、`len(ROUTER_FILES) >= 10`
     —— 防 parametrize 拿到空列表而整组静默通过；
  ③ **反向验证**：用**临时文件构造违规样例**（`access=None` 的签名、`import jwt`、
     被改名的函数），确认守卫**真的会红**。这条最重要 ——
     它是唯一能证明"守卫不是装饰"的证据。

- **面试怎么讲**：**测试也需要被测试，守卫也需要被守卫。**
  常见的说法是"没有断言的测试没有价值"；这条要更狠一点：
  **「有断言、但断言对象可能不存在」的测试，比没有测试更糟** ——
  它占用了"这里有覆盖"的信用，却不提供任何保护。
  可延伸：D10（测不到的分支等于没测）、D14（校验器本身要先校准口径）——
  三条合起来是一套「**检查者的自检**」方法论。

### D17. 构造「坏输入」要先搞清它会被哪一层拦下（2026-09-23）

- **现象**：写四格式端到端时，要造一份"失败可见、可重试"的坏文件。
  第一版随手写了 `b"PK\x03\x04" + b"\x00" * 512`（zip 魔数 + 垃圾），
  以为"这样 python-docx 就会解析失败" —— 结果上传接口直接返回 **415**：
  「文件内容与扩展名 .docx 不一致（docx 需要对应的文件头特征）」。
  测试在**根本没走到解析阶段**的地方就红了。

- **根因**：**「坏」是可分层级的，而每一层由不同的代码负责。** 这里至少三层：
  ① **准入层**（magic bytes / `content_sniff`）；② **解析层**（python-docx）；
  ③ **流水线层**（错误码与状态落库）。
  `PK\x03\x04` 只说明"像 zip"，而准入还要求能**打开**这个 zip 并看到 `word/` 条目 ——
  **我以为在构造"解析失败"，实际构造的是"准入拒绝"。**

- **解决**：按**目标层**构造输入 —— 要触发**解析失败**，就得先**满足准入**：
  用 `zipfile` 造一个**合法** zip，放入 `[Content_Types].xml` 与
  `word/document.xml`（后者内容为非法 XML）。这样准入看得过去（有 `word/` 条目），
  而 python-docx 一解析就炸 —— 正是我们要的那一层失败。
  **副产品**：那次 415 不算白跑，它是"准入校验确实在工作"的一条正面证据。

- **面试怎么讲**：**测试输入要针对"你要验证的那一层"来构造。**
  随手拿个"看起来坏"的东西当坏输入，测出来的往往是**上一层**的行为 ——
  你以为在测解析容错，实际在测准入策略，而且**红的时候会误导你改错地方**。
  通用做法：先画清楚"这段输入会依次经过哪几层、每层认什么"，再决定在哪一层下手。
  可延伸：B9（OCR 缺失降级为警告，而 embedding 缺失必须失败）正是同一件事的另一面 ——
  **先分清"这是哪一层的失败"，再决定它该被降级还是该被抛出。**

## E. 工程协作

### E1. 对同一文件的多个编辑并行执行会静默丢改动

- **现象**：把两个编辑操作放在同一条消息里并行发出，
  两个都返回"成功"，但**后写的覆盖了先写的** —— 一处改动凭空消失。
  （本次实际发生 5 处，靠事后 `grep` 关键标记才发现。）
- **根因**：读-改-写竞态。两个编辑各自读到同一份旧内容，
  各自修改后写回，最后一次写入丢掉了另一次的修改。
- **解决**：**同一文件的多个编辑必须串行**；不同文件才可并行。
  改完用 `grep` 检查关键标记（如新写入的小节号、数字）确认真的落盘。
- **面试怎么讲**：这是并发写同一个资源时的经典丢失更新问题，
  只不过发生在"我的工具调用"这一层。教训是通用的：
  **并行化的前提是资源不冲突**；以及**改完要验证，不能相信返回状态**（与 A1 同源）。

### E2. 同一工作区存在并行会话 → `git add docs/` 会把别人的中间产物一锅端（2026-09-23）

- **现象**：本批开工时工作区是**干净的**（`git status --porcelain` 0 行）；
  落盘过程中再查，冒出 6 个不属于本次任务的未提交文件 ——
  `docs/FRONTEND_HANDOFF_AND_ALIGNMENT.md`、`docs/FRONTEND_AI_HANDOFF_PROMPT.md`、
  `docs/frontend/`、`scripts/{export_frontend_contract,mint_dev_token,seed_dev_tenant}.py`，
  文件时间戳就在几分钟内；同一份 append-only 的记忆文件里也被追加了两条。
  即：**另一个会话正在同一个仓库里做前端交接的活**。

- **根因**：**文件系统是共享的，但「工作区干净」这个判断只有瞬时意义。**
  按习惯写 `git add docs/ scripts/`，就会把对方**没写完的中间产物**一起提交 ——
  对方可能正在改其中某个文件，提交出去的是半成品，而它自己还不知情。

- **解决**：① **`git add` 一律用精确路径**，提交前 `git status --short` 复核暂存区，
  再确认 `git diff --cached --stat` 的文件数就是预期数；
  ② 改 append-only 文件（台账 / 踩坑 / 记忆）时用**末尾锚点追加**，不覆盖整段 ——
  对方的追加可能就发生在你读与写之间；
  ③ 工作区出现来路不明的新文件时，**先查时间戳与内容**再决定动不动它。

- **面试怎么讲**：这是 E1（同一文件的多次编辑并行丢改动）的**上一层**：
  E1 是「我的两次调用」抢一个文件，这条是「**两个会话 / 两个人**」抢一个工作区。
  教训一致且通用：**共享可变状态下，「看起来没问题」不等于「没有并发」**；
  所以**提交要窄（精确路径）、验证要宽（复核暂存区）**。

### E3. 两套编号体系并存且撞车，引用必须带前缀（2026-09-23）

- **现象**：验收规范用 `I01~I04 / Q01~Q06 / O01` 标阶段、`§7.x` 标小节；
  项目用 `B1~B8` / `阶段 0~7`（`阶段 7.1~7.4` 是发布门禁判据）。
  两套编号在仓库里**零交叉引用**（`grep "I01\|Q01"` 全无），
  而且**规范的 §7.x 与执行计划的「阶段 7.x」编号完全相同、内容完全不同**：

  | 位置 | 规范 §7.x | 执行计划 阶段 7.x |
  | --- | --- | --- |
  | 7.3 | 状态与原子发布 | 安全审查 |
  | 7.4 | 删除、撤权和缓存 | 阶段完成条件（含索引原子切换 / 回滚判据） |

- **根因**：两份文档独立演进，都没觉得自己需要给对方让路。
  后果不是「看不懂」，而是**看懂的人对错了**：写「§7.4 判据未通过」时，
  读者可能去翻规范的 §7.4（删除与撤权），而作者指的是执行计划的阶段 7.4。

- **解决**：① 在规范里加**编号映射表**（规范 ID ↔ 项目批次 / 阶段），
  并写明「引用时必须同时写出两边」；② 把「§7.x 与阶段 7.x 撞车」
  写成**显式陷阱提示**，引用一律带前缀（如「执行计划 阶段 7.4」）；
  ③ 本报告与审查文件内所有引用按此执行。

- **面试怎么讲**：**编号是接口。** 两套编号并存不是问题，**没有对照表才是问题** ——
  这和「两个子系统各自测试全绿、接起来就坏」（B14 / F1）是同一类：
  **各自内部自洽，缺的是那一层显式的映射**。
  可延伸的点：**凡是需要「人肉翻译」的地方，就应该固化成一张表或一个常量**，
  否则错误会在第 N 次引用时才暴露，且极难追溯。

## F. 尚未修复的已知缺口（2026-09-23 全仓复核发现）

> 与 A~E 的区别：**A~E 是已解决的坑；F 是尚未修复的问题**，全部由一次系统性复核发现。
> 详细分析与路线图见 `docs/RAG_GAP_ANALYSIS_AND_ROADMAP.md`。
> **保留这一节的意义**：这几个问题的发现过程本身，就是本项目最值得讲的工程反思 ——
> 它们都属于「**测试全绿、但功能/安全并没有真正生效**」这一类静默失效。

### F1. 双轨制：新建的 ingestion 子系统与线上检索链路完全没有接上

- **现象（实测）**：
  - 线上检索读的是 `data/takeout_customer_service_seed.jsonl`（**781 条手工 FAQ**），
    经 `utils/retriever.iter_knowledge_items()` 加载；
  - `utils/vector_retriever.py`（901 行）的 `retrieve_*` 函数签名里
    **连 `tenant` / `acl` 都没有**（`grep -n "tenant\|acl"` **零命中**）；
  - `services/ingestion/repository.py` **只被 `routers/documents.py`（上传）引用**，
    没有任何查询路径消费它；
  - `data/rag_metadata.db` **不存在** → 迁移从未落到开发库。
- **「已建未启用」资产清单**——以下函数都已实现、都被测试覆盖，
  但**生产代码路径上没有任何调用点**：

  | 资产 | 定义位置 | 生产调用点 | 测试调用点 |
  | --- | --- | --- | --- |
  | `create_document_version()` | `repository.py:279` | 无 | 有 |
  | `find_version_by_content_hash()` | `repository.py:314` | 无 | 有 |
  | `grant_document_acl()` | `repository.py:370` | 无 | 有 |
  | `insert_chunks()` | `repository.py:506` | 无 | **无** |
  | `index_builds.manifest_uri` | `models.py:430` | 无读写 | 有 |
  | `queue.publish()` | `queue.py` | **有** | 有 |
  | `queue` 消费端（`xreadgroup`） | — | **未实现** | — |

- **后果**：用户上传的文档进了对象存储和数据库，**永远进不了 FAISS，检索不到**。
  已建的租户 / ACL / 版本 / chunk 数据全部是「已建模、未启用」状态。
- **归属**：B5（chunker）+ B6（pipeline / worker / manifest）就是为它准备的。
- **面试怎么讲**：见下方「Q1」。这是回答「你遇到的最大困难」的最佳素材。

### F2. 检索评测口径失真：intent 命中率冒充 retrieval recall

- **现象（实测）**：`scripts/evaluate_retrieval_metrics.py:85` 的判定函数是：

```python
def is_relevant(candidate, expected_intents):
    intent = candidate.get("source", {}).get("intent", "")
    return intent in expected_intents
```

- 也就是说，「相关」的判定 = **召回条目的 `intent` 字段是否等于标注的 `expected_intent`**。
- **后果**：
  1. 报出的 **recall@1 = 0.9667** 是「**意图分类命中率**」，
     不是「检索到正确文档 / Chunk 的比例」。语料 781 条、意图只有**个位数个枚举值**，
     **只要召回任意一条同意图 FAQ 就算命中** —— 门槛比真正的 retrieval 低一个量级。
  2. 用例集 `data/chat_grounding_cases.jsonl` 与语料由同一批人按**同一套意图体系**手工构造，
     存在**构造性重叠（近似 train/test leakage）**。
  3. 因此「Recall@5 = 98.89%」**不能用来证明检索质量**，而 `README.md` 已引用它。
- **修正方向**：金标从「意图」升级为「**文档 ID + Chunk ID**」；
  引入**真实长文档**评测集；intent 命中率保留为辅助指标（`Intent Hit Rate`）
  但与 recall **分开命名、分开统计**；补充负样本集以计算**拒答准确率**。
- **面试怎么讲**：见下方「Q3」。**主动指出自己评测口径的缺陷，比报一个漂亮数字可信得多。**

### F3. 隔离测试守的是数据层，检索层裸奔

- **现象（实测）**：`tests/test_tenant_isolation.py` 有 14 条用例、**全部通过**，
  但逐条看都是在测**数据层 CRUD**（`test_cannot_read_other_tenants_document`、
  `test_document_list_only_returns_own_tenant`、`test_body_tenant_id_does_not_widen_scope` …）。
- **后果**：**测试全绿，但检索层没有任何 tenant / ACL 过滤**。
  它守的是 B4 上传 / 查询接口，而真正会把 A 租户文档喂给 B 租户的那条路径
  （`retrieve_rag_items`）**没有被覆盖**。
- **修正方向**：新增 `tests/test_retrieval_isolation.py` ——
  负向验证「被过滤文档的标题、分数、数量、引用和 trace 均不泄漏」。
- **面试怎么讲**：**「绿灯」不等于「安全」**。
  测试覆盖的是**你写的地方**，不是你**漏的地方**。
  这条对 F1/F3 是同一个教训的两个面，也是我把"接线"提升为最高优先级的直接原因。
- **修复于 B7（2026-09-23）**：新增 `tests/test_retrieval_isolation.py`（**23** 条，6 个测试类，
  覆盖规程最低要求 5 条 + **正向对照** 3 条 + 预过滤判决 2 条），
  并在 `tests/test_tenant_isolation.py` 增加 `TestAclOnRealRoutes`（**7** 条，
  走真实 `documents` / `knowledge` / `retrieval` 三路由）；
  `tests/test_retrieval_api.py` 新增 `TestChunkRetrievalApi`（**9** 条，API 出口层）。
  隔离测试**数据层与检索层各写一套**，且新增了「B 入库后 A 仍能检索到自己的 chunk」的
  **正向对照** —— 只写负向断言会退化成"空结果也算通过"。原记录保留，不改写。

### F4. README 与实测脱节

- **现象（实测）**：
  - README 第 6 行 badge 写的是 `tests-332 passed`，**实际是 555**；
  - 第 1 节快速验证也写「实测：332 passed」；
  - 架构图与「混合检索」描述未区分于**真正的 BM25 混合**
    （现实现是 FAISS + `calculate_keyword_bonus` / `calculate_direction_penalty` 规则加权）。
- **后果**：面试官一跑测试就发现数字不符；「混合检索」这个说法会被追问到实现细节。
- **修正方向**：数字同步 + 补充「已建未启用」的诚实说明 + 明确检索实现形态。

### F5. 任务队列有投递端、无消费端

- **现象（实测）**：`services/ingestion/queue.py` 的 `publish` 已就绪
  （Redis Stream + 内存降级），但 `xreadgroup` / `xack` / 消费者组创建
  **全部留给 worker（B6，尚未实现）**。因此上传后 **job 会永远停在 `pending`**。
- **为什么当时这样拆**：避免过早把「消息被谁读走」的语义固定下来。
- **必须登记的理由**：否则「上传接口实现了」会被误读成「上传到入库闭环完成了」。

### F 节的方法论小结（最值得讲的一条）

F1~F3 是**同一类失效**：**代码全部写对了，测试全部通过了，但功能/安全并没有真正生效。**
它们的共同原因是「**验证了组件，没有验证组件之间的连接**」。

由此得出的可复用纪律（建议纳入后续每批的门禁）：

1. **每个新模块必须登记「生产调用点」**——
   定义在、测试在，但没人调用 = 未完成；
2. **权限隔离测试必须分层**：数据层与检索层各写一套，不允许用前者代替后者；
3. **指标命名必须精确**——`intent_hit_rate` 不能叫 `recall`，
   否则数字会被自己（和读者）误解为它不代表的含义。

### 六个「长答」骨架（推荐背这几条）

**Q1「你这个项目遇到的最大困难是什么？」**
> 不要答具体 bug，答**方法论层面的困难**：最大的困难是**判断"什么时候该停下来把地基补好"**。
> 项目一开始是「一份手工 FAQ + FAISS 向量检索」，能跑、评测数字也好看。
> 按企业级目标改造做到第 4 批时我发现：**新建的解析器 / 数据模型 / 租户 ACL / 上传接口，
> 和线上真正在跑的检索链路是完全断开的** —— 线上检索读的还是手工 FAQ，
> 检索函数签名里连 `tenant_id` 都没有。更麻烦的是，隔离测试 14 条全绿，
> 但测的是数据层 CRUD，**检索层没有任何权限过滤**。
> 于是我决定把「让两条链路接上」提升为最高优先级，而不是继续加新功能 ——
> 因为这个缺口卡住了所有下游能力。
> 这件事让我意识到：**"绿灯"不等于"安全"，测试覆盖的是你写的地方，不是你漏的地方。**

**Q2「你怎么保证代码质量和纪律？」**
六条，每条配一个已有证据：① 能用测试固化的纪律就不写在文档里（`B1` / `D1`）；
② 枚举类权限用真值表驱动不抽样（`D2`）；③ 权限测试**正负成对**
（踩过"只有负向用例导致 C1 完整穿过测试"）；④ **基线零失败**纪律
（每批记录起点测试数，任何失败不得归因历史遗留）；
⑤ **warning 数量作为门禁指标**（稳定 5 条，新增立刻发现，`D3`）；
⑥ 每个取舍写决策记录，含**被否决的方案 + 可逆性对比**（`B5`）。

**Q3「你这个 RAG 系统的检索是怎么做的？」**（诚实答法）
> 现在的实现是 **FAISS 向量召回 + CrossEncoder 精排 + 规则式加权**
> （`calculate_keyword_bonus` 关键词加权、`calculate_direction_penalty` 方向惩罚）。
> 它是"混合"的**简化形态**，**没有真正的 BM25 稀疏检索**，也没有 RRF 融合。
> 我知道正确做法是 dense + sparse 双路召回 + RRF，但我把它排在**权限过滤之后** ——
> 因为先有权限再谈召回质量：如果检索结果会跨租户泄漏，召回率再高也没有意义。
> 另外我复核时发现**现在的评测口径有问题**：报出的 recall@1 是按"意图是否命中"算的，
> 不是按"文档/Chunk 是否命中"算的，语料和用例还是同一套意图体系手工构造的。
> 所以这个数字**不能当作检索能力的证据**，我把它列为 P0 修正项。

**Q4「多轮对话怎么做的？」**
> 有**结构化会话状态**（不只是历史拼接）：`conversation_store` 存 `facts`（已确认事实）、
> `summary`（会话摘要）、`user_memory`（长期记忆），并有 `redis_context_cache` 缓存意图与风险态。
> 但**没有 query rewrite，也没有多跳分解** —— 现在是 `build_query_with_intent_hint`
> 在 query 后追加意图提示，属于**规则拼接而非改写**。
> 计划里的 query rewrite 我**有意排在后面**：没有 chunk 级检索和证据定位，
> 改写了也定位不到证据，改了等于没改。

**Q5「生产级要考虑什么？」**
> 按失败处理分层答，**明确区分已做到与未做到**：
> **已做到** —— 上传期拒绝（415/413/401/403 各有明确错误码）、解析失败抛结构化错误（`B6`）、
> OCR 引擎缺失降级为**可查询的警告**（`B9`）、审计脱敏按语义分档（`C2`）、
> fail-closed 鉴权（缺密钥返回 500 而非静默放行）。
> **未做到**（诚实说）—— 索引原子切换与回滚、超时/取消/重试、
> 完整降级链（重试→缩上下文→模板→规则→转人工）、流式输出的"校验后发送"。
> 其中最想讲的一条取舍：**高风险流式回复不能先把未经验证的 token 发出去再事后检查，
> 因为已发送的 token 无法撤回** ——
> 正确策略是先流式发**状态事件**，正文按句/按声明**缓冲**，核验通过后再放。

**Q6「如果重来一次，你会怎么改？」**
> ① **先收敛双轨再扩功能** —— 应该在做解析器之前先把「上传 → chunk → 索引 → 检索」
> 这条最小闭环打通，再往上加能力；现在的顺序导致建了一堆"未启用资产"（`F1`）。
> ② **评测口径先行** —— 检索与权限的评测金标应该在写检索代码之前定好
> （文档 ID + Chunk ID），否则会像现在这样，数字漂亮但不可信（`F2`）。
> ③ **`utils/vector_retriever.py` 一开始就拆模块** —— 901 行、4 类职责、无权限参数，
> 现在要在它上面塞 manifest 和 filter，风险很高。
> ④ **权限测试和数据层测试分开组织** —— 混在一起会掩盖「数据层挡住了、检索层没挡」（`F3`）。
